# Security and Authorization Contract

상태: **Phase 0에서 확정한 목표 계약**
적용 범위: 이후 Front·Back 작업, 자동 권한 행렬 테스트 및 배포 설정의 단일 기준
비고: 이 문서는 현재 구현이 이미 계약을 만족한다는 주장이 아니다. Phase 1 이후의
작업은 이 계약과 현재 코드의 차이를 테스트로 드러내고 해소한다.

## 1. 공통 인증·응답 규칙

- 역할은 `viewer`와 `admin` 두 가지다. 비활성 사용자는 어떤 보호 자원도 사용할 수
  없다.
- 보호 REST API는 `Authorization: Bearer <access-token>`을 사용한다. 서버는 매 요청에
  토큰의 유효성, 사용자 존재·활성 상태 및 현재 역할을 확인한다.
- 인증 정보가 없거나 유효하지 않거나 사용자가 비활성화된 경우 **401**을 반환한다.
  인증된 사용자가 역할·소유권·허용 범위를 벗어나면 **403**을 반환한다.
- 존재하지 않는 리소스는 **404**, 형식이 맞지 않는 요청은 **422**, 서버·운영체제
  수집 실패는 성공의 빈/0 값으로 숨기지 않고 안전한 오류 응답으로 구분한다.
- 응답 본문·로그·브라우저 콘솔·URL query/path에는 access token, WebSocket ticket,
  session ID, 비밀번호, 비밀번호 해시 또는 비밀 설정값을 기록하지 않는다.
- 프론트엔드는 이 표를 UI 표시에만 사용한다. 허용 여부는 반드시 서버가 강제하며,
  401이면 세션을 정리하고 로그인 상태로 전환하고, 403이면 권한 부족으로 표시한다.

## 2. REST 권한 행렬

`허용`은 인증·활성 상태·입력 검증을 통과한 경우만 뜻한다. 모든 행은 후속 자동
테스트에서 미인증, viewer, admin 세 경우를 검증한다.

| 기능 | 대표 자원/경로군 | 미인증 | viewer | admin | 추가 계약 |
| --- | --- | ---: | ---: | ---: | --- |
| CPU·메모리·디스크·프로세스 조회 | `/api/monitor/cpu`, `/memory`, `/disks`, `/disk`, `/processes` | 401 | 허용 | 허용 | 시스템 메트릭은 로그인 사용자에게만 제공 |
| 히스토리 조회 | `/api/history/*` | 401 | 허용 | 허용 | 원본·집계 응답 모두 같은 인증 기준 적용 |
| 네트워크 인터페이스·트래픽·패킷 | `/api/network/interfaces`, `/traffic`, `/packets` | 401 | 허용 | 허용 | 교육용 시뮬레이션 여부는 응답/UI에서 명확히 표시 |
| 네트워크 연결·PID 조회 | `/api/network/connections` | 401 | 403 | 허용 | 연결 식별자·PID는 admin 전용 |
| 프로세스 종료 | `POST /api/monitor/processes/{pid}/kill` | 401 | 403 | 조건부 허용 | 아래 DEC-03 범위만 허용 |
| 사용자·감사 로그 관리 | `/api/admin/users*`, `/api/admin/audit` | 401 | 403 | 허용 | DEC-02 전역 관리자 정책과 마지막 활성 관리자 보호 적용 |
| 모니터링 ticket 발급 | `POST /api/auth/ws-tickets/monitor` | 401 | 허용 | 허용 | 아래 ticket 계약 적용 |
| 셸 ticket 발급 | `POST /api/auth/ws-tickets/shell` | 401 | 403 | 허용 | 아래 ticket·세션 계약 적용 |
| 셸 파일 탐색·초기화 | `/api/shell/fs`, `/api/shell/reset` | 401 | 403 | 본인 세션만 허용 | 세션 소유자와 격리 경계를 서버가 확인 |
| 셸 세션 목록 | `/api/shell/sessions` | 401 | 403 | 본인 세션만 허용 | 셸이 admin 전용이므로 같은 기준을 적용한다. 다른 사용자의 세션은 응답에 포함하지 않는다 |

현재 코드의 일부 경로명·인증 방식은 위 목표 계약과 다를 수 있다. 후속 Back 작업은
호환성 영향이 없는 경우 위 경로군에 맞추고, 불가피한 공개 경로 변경은 구현 전에
이 문서와 관련 Front 범위를 함께 갱신한다.

## 3. WebSocket ticket 계약 (DEC-04)

### 발급

- 위의 두 ticket 발급 REST API는 bearer 인증과 권한 행렬을 먼저 적용한다.
- 성공 응답은 `ticket`과 `expires_in_seconds`를 포함한다. `expires_in_seconds`는
  60 이하의 양의 정수다. 응답에는 `Cache-Control: no-store`를 사용한다.
- ticket은 무작위·서버 검증 가능·단일 사용자·단일 용도(`monitor` 또는 `shell`)
  에 바인딩한다. 재사용, 다른 용도 사용, 만료 사용은 거부한다.

### 연결

- 모니터링은 `/ws/monitor`, 셸은 `/ws/shell`을 사용한다.
- ticket은 URL query string이나 로그가 남기 쉬운 경로에 넣지 않는다. WebSocket
  연결 후 첫 클라이언트 메시지로만 전달한다: `{ "type": "authenticate", "ticket": "…" }`.
  문서·테스트·로그에는 실제 ticket 값을 쓰지 않는다.
- 서버는 제한 시간 안에 인증 메시지를 받기 전까지 데이터·셸 입력을 처리하지 않는다.
  ticket 검증 시 사용자 존재·활성 상태와 현재 역할·용도를 재확인하고, 성공 시 즉시
  ticket을 소비한다. 실패·만료·재사용 시 연결을 닫고 민감한 이유를 노출하지 않는다.
- 인증된 모니터링 연결은 DEC-07의 일반 모니터링 범위만 구독한다. 인증된 셸 연결은
  admin의 본인 셸 세션만 사용할 수 있다.

## 4. 정책 결정의 구현 기준

| ID | 확정 정책 | 구현·테스트 기준 |
| --- | --- | --- |
| DEC-01 | 사용자 식별자 컬럼은 `username` | ORM, migration, 인증 DTO와 테스트 fixture가 동일한 컬럼명을 사용 |
| DEC-02 | 전역 관리자; `created_by`는 감사 정보 | 모든 admin이 사용자·감사 로그 관리 권한을 가지며 `created_by`로 권한을 축소하지 않음 |
| DEC-03 | admin만 교육용 `demo-*` 자식 프로세스 종료 | viewer는 항상 403; admin도 allowlist 밖·비자식·보호 PID는 403, 없는 PID는 404 |
| DEC-04 | 60초 이하 일회성 WebSocket ticket | 위 발급·연결·재사용 거부 규칙 |
| DEC-05 | 운영 TLS fail-closed, HTTP는 개발만 | 운영 프로필은 인증서 부재 시 시작 실패; backend 직접 공개를 허용하지 않음 |
| DEC-06 | 셸 네트워크 기본 `none` | 별도 개발 설정 외에는 외부 네트워크 접근 불가 |
| DEC-07 | 일반 모니터링은 로그인 사용자, 연결 목록은 admin | REST·WebSocket 구독 모두 위 행렬 적용 |
| DEC-08 | 원본 스냅샷 7일 후 삭제 | 보존 작업은 원본만 대상으로 하며 삭제 시점·결과를 안전하게 관찰 가능 |

## 5. 데이터·소유권 경계

- `username`은 식별자이며, 사용자 응답은 필요 최소 필드만 반환한다. `created_by`는
  감사 정보로 보존하되 관리자 권한 predicate에는 사용하지 않는다.
- 셸 세션은 소유 사용자와 연결하고, admin이라도 다른 사용자의 셸 세션·파일 영역을
  열람·초기화하지 않는다. 전역 관리자 정책은 사용자 관리 API에만 적용된다.
- 파일 탐색은 사용자 허용 루트 밖으로 resolve되지 않으며 심볼릭 링크·재귀 깊이·항목
  수·응답 크기 제한을 적용한다. 이 제한은 SHELL-01의 구현·테스트 대상이다.
- 모니터링 원본 스냅샷은 DEC-08을 따르고, 인증·감사 데이터와 실사용자 데이터는
  테스트 fixture 또는 문서 예시로 복사하지 않는다.

## 6. 후속 검증 의무

- `QA-01`과 `QA-02`는 이 계약을 읽을 수 있는 자동 테스트 기반을 만든다.
- 인증·인가 구현 작업은 각 행에 대해 미인증 401, viewer 결과, admin 결과를 자동화한다.
- ticket 작업은 만료·재사용·용도 교차·비활성 사용자·URL/로그 비노출을 검증한다.
- 배포·셸·데이터 작업은 DEC-05, DEC-06, DEC-08을 각각 독립 테스트로 검증한다.
