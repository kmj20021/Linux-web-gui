## 1. 프로젝트 개요

### 1.1 한 줄 정의

복잡한 실습 환경 구축 없이 **웹 브라우저만으로** 서버 자원 상태를 관찰하고, 실제 환경에서는
위험한 명령까지 안전하게 반복 실습하며, 생성형 AI에게 즉시 질문할 수 있는
**Linux 운영 학습 지원 시스템**이다.

### 1.2 왜 이 시스템이 필요한가

Linux는 서버·클라우드·정보보안 분야의 필수 기술이지만, 입문 학습자는 세 가지 벽에 부딪힌다.

| # | 문제 | 구체적으로 |
|---|---|---|
| 1 | **결과를 해석할 기준이 없다** | CLI로 시스템을 제어해야 하는데, 화면에 뜬 출력이 정상인지 오류인지 판단할 기준이 아직 없다. 오타·권한 문제·경로 오류·서비스 구성 오류의 원인을 구별하지 못한다 |
| 2 | **실습 환경 구축이 학습보다 먼저 무너뜨린다** | 가상머신 설치, 네트워크 설정 같은 사전 작업이 진입 장벽이 된다. 제한된 수업 시간은 대부분 여기서 소모되고, 실제 실습은 기본 명령어 몇 개를 쳐 보는 수준에 그친다 |
| 3 | **정작 중요한 명령일수록 실습에서 빠진다** | 서비스 중지, 방화벽 규칙 변경처럼 반복 연습이 가장 필요한 위험한 명령은, 초보자가 잘못 실행하면 환경을 복구해야 하므로 실습 대상에서 제외되기 쉽다 |

서버 운영 학습은 명령어 암기가 아니다. **상태를 확인하고 → 출력을 해석하고 → 원인을 추론하고
→ 명령을 선택**하는 과정이다. 웹 서버가 뜨지 않을 때 프로세스·서비스 상태·포트·방화벽·로그를
단계적으로 확인해야 하며, 이는 여러 명령과 구성요소의 관계를 종합적으로 이해해야 가능하다.

> 근거: `docs/thlesis-tocs/1장-4.md` §1.1

### 1.3 기존 도구로 해결되지 않는 이유

웹 기반 서버 모니터링 도구는 이미 여럿 있다. 그러나 **그 도구들이 상정하는 사용자는 서버를
운영하는 전문가**이고, 이 프로젝트가 상정하는 사용자는 Linux 운영을 처음 배우는 사람이다.
대상이 다르기 때문에 학습자는 화면의 숫자를 봐도 그것이 정상 부하인지 문제 상황인지 판단하지
못하고, 무엇을 연습해야 하는지와 자기 시도가 옳았는지를 확인할 방법이 없다.
**기존 도구의 결함이 아니라 설계 목적의 차이다.**

생성형 AI를 그냥 붙이는 것도 답이 아니다. 대규모 언어모델은 사실과 다른 내용을 그럴듯하게
만들어내는데, **학습자는 그 설명이 맞는지 판별할 능력이 아직 없다.** 틀린 설명이 걸러지지 않고
그대로 전달되면 학습에 해가 된다.

> 근거: `docs/thlesis-tocs/1장-4.md` §1.2, §1.3

### 1.4 이번 학기에 완성할 시스템의 세 요소

| 요소 | 내용 | 대응 문제 |
|---|---|---|
| **관찰** | 실제 동작 중인 서버의 자원 사용량을 주기적으로 수집해 웹 화면에 제공한다. 서버를 소유하지 않아도 CPU·메모리·프로세스 변화를 관찰할 수 있다 | 문제 2 |
| **가상 실습** | 입력한 명령을 실제로 실행하지 않고 **서버가 보관하는 가상 Linux 상태를 전이**시킨다. 실패해도 복구할 것이 없어 서비스 중지·방화벽 차단 같은 위험한 명령까지 학습 소재가 된다 | 문제 3 |
| **AI 설명** (판정과 설명의 분리) | 명령 결과와 성취 판정 같은 **사실 확정은 결정론적 규칙**이 맡고, 생성형 AI는 **확정된 사실을 설명하는 일만** 담당한다 | 문제 1 + LLM 환각 |

세 번째 요소가 이 프로젝트의 핵심 주장이다. 채점은 "정답 명령어와 문자열이 같은가"가 아니라
**"최종 가상 상태가 목표 상태에 도달했는가"** 로 판정한다. 순서나 명령이 달라도 같은 상태에
도달하면 정답이며, 학습자가 익히는 것은 문법 암기가 아니라 **명령과 상태 변화의 대응 관계**다.

AI에게 질문할 때 시스템이 현재 가상 상태와 확정된 판정을 함께 입력으로 넘기므로, 학습자가 자기
상황을 다시 설명할 필요가 없고 **AI가 실행 결과를 지어내거나 합격 여부를 뒤집을 수 없다.**

### 1.5 사용자

| 구분 | 대상 | 시스템에서 하는 일 |
|---|---|---|
| 학습자 (viewer) | Linux 입문 단계의 대학생, 서버 운영 초급자 | 대시보드 열람, 웹터미널 실습, AI 튜터 시나리오 수행 |
| 관리자 (admin) | 시스템 운영자 | 위 전부 + 사용자 관리, 감사 로그 열람, 네트워크 연결 목록, 교육용 프로세스 종료 |

### 1.6 이번 학기 과제의 성격

이 프로젝트는 이전 학기에 **모니터링·웹터미널 중심의 초기 구현**까지 만들어 둔 상태다.
이번 학기 과제는 두 갈래다.

1. **리팩토링** — 초기 구현에서 드러난 보안·구조·성능 결함을 제거해 운영 가능한 수준으로 만든다.
2. **AI 학습 기능 신규 구현** — 위 세 요소 중 아직 없는 **가상 실습과 AI 설명**을 만들어,
   AI 튜터링이 실제로 동작하는 시스템으로 완성한다.

두 갈래 중 **AI 기능을 먼저 동작시키는 것을 1차 목표(10-12)** 로 둔다. 리팩토링은 그 이후에도
계속되지만, "AI 튜터링이 동작하는 프로젝트"라는 결과물의 정체성이 먼저 서야 나머지 작업의
우선순위를 판단할 수 있기 때문이다.

## 3. 문제점 및 리팩토링 필요성

각 항목은 `현상 → 왜 문제인가 → 근거` 순으로 적는다. 근거는 전부 실제 파일과 줄 번호다.

### P1. 인증 기반 자체가 무너져 있다 — 최우선

- **현상:** 환경변수가 없으면 **공개된 문자열을 JWT 서명 키로 사용**하고(`backend/core/security.py:26`), 서버 시작 시 **`admin/admin1234` 계정을 자동 생성**한다(`backend/main.py:80`).
- **왜 문제인가:** 서명 키를 아는 사람은 **관리자 토큰을 위조**할 수 있다. 그 토큰으로 Docker 터미널까지 접근되므로 영향 범위가 시스템 전체다.
- **근거:** `docs/evaluation.md` §5 보안

### P2. 토큰이 로그와 URL에 그대로 남는다

- **현상:** 모니터링 WebSocket이 **JWT 전체와 쿼리 문자열을 로그에 기록**하고(`backend/routers/websocket.py:147`), 브라우저도 토큰이 포함된 URL을 콘솔에 출력한다(`frontend/src/api/client.js:210`). Nginx access log에도 쿼리 문자열이 들어갈 수 있다(`frontend/nginx.conf:14`). 토큰 유효기간은 배포 설정에서 **24시간**이다(`docker-compose.yml:42`).
- **왜 문제인가:** 로그를 볼 수 있는 사람이 **하루 동안 유효한 관리자 토큰을 그대로 얻는다.** P1과 겹치면 위조와 탈취가 동시에 가능하다.
- **근거:** `docs/evaluation.md` §5 보안

### P3. 시스템 API 대부분에 인증이 없다

- **현상:** 모니터링 REST API 대부분에 인증 의존성이 없다. 특히 **활성 연결 목록과 프로세스 목록**은 시스템 내부 정보를 그대로 노출한다. 프론트의 `ProtectedRoute`는 화면 이동만 막을 뿐 API 경계가 아니다.
- **왜 문제인가:** 로그인하지 않아도 서버 내부 상태를 조회할 수 있다. 프로세스 종료 권한도 README는 관리자 전용이라 설명하지만 실제로는 로그인 여부만 확인한다.
- **근거:** `docs/evaluation.md` §5 정확성과 안정성, 보안

### P4. Docker 소켓을 백엔드에 그대로 마운트한다

- **현상:** `docker-compose.yml:47`에서 호스트 Docker 소켓을 백엔드 컨테이너에 직접 마운트한다. `privileged: false`가 설정되어 있다.
- **왜 문제인가:** **Docker 소켓 접근 권한은 사실상 호스트 관리자 권한이다.** `privileged: false`만으로 격리됐다고 볼 수 없다. 백엔드가 뚫리면 호스트가 뚫린다.
- **근거:** `docs/evaluation.md` §5 보안

### P5. 데이터 계층이 신뢰할 수 없다

- **현상:** 마이그레이션이 현재 ORM 모델과 **반대 방향**이다. 모델은 `username`을 쓰는데 마이그레이션은 `login_id`로 바꾼다. 또 CPU·메모리·네트워크 라우터가 넓은 `except Exception` 뒤에 **0이나 빈 배열을 반환**한다.
- **왜 문제인가:** 마이그레이션을 실행하면 애플리케이션 쿼리가 깨진다. 그리고 수집 실패가 "사용률 0%"로 보여 **운영자가 장애를 정상으로 오인한다.** Windows 검증에서 `mem.buffers`가 없어 실제로 수집이 실패했지만 0으로 채워져 정상으로 판정됐다.
- **근거:** `docs/evaluation.md` §5 정확성과 안정성

### P6. 이벤트 루프를 막고, 연결마다 같은 일을 반복한다

- **현상:** `async def` 안에서 `psutil.cpu_percent(interval=...)`를 직접 호출해 이벤트 루프를 막는다(`backend/routers/cpu.py:25`, `routers/websocket.py:55`). WebSocket **연결마다 별도로** 전체 프로세스를 순회하고 CPU를 수집한다(`routers/websocket.py:163`). 주석은 "브로드캐스트"라고 하지만 실제로는 연결별 수집·전송이다.
- **왜 문제인가:** 접속자가 늘수록 같은 작업이 그대로 배수로 늘어난다. 셸 시작·정리의 `subprocess` 호출도 동기라 지연이 생기면 **다른 요청까지 함께 멈춘다.**
- **근거:** `docs/evaluation.md` §5 성능과 자원 효율

### P7. 프론트 대형 파일과 중복 처리

- **현상:** `Filesystem.jsx` 약 **950줄**, `NetworkDiagnostics.jsx` 약 **600줄**, `Users.jsx` 약 **500줄**이 상태·도메인 로직·모달·렌더링을 한 파일에서 담당한다. API 오류 처리가 여러 페이지에 반복된다. `axios`, `chart.js`, `react-chartjs-2`는 선언만 되고 쓰이지 않는다.
- **왜 문제인가:** 한 곳을 고치면 영향 범위를 예측할 수 없고 테스트 대상을 좁힐 수 없다. AI 화면을 새로 붙일 때 같은 실수를 반복하게 된다.
- **근거:** `docs/evaluation.md` §5 구조와 유지보수성

### P8. 검증 수단이 없다

- **현상:** `backend/tests/`도 프론트 테스트도 CI 워크플로도 없다. 기존 검증 스크립트는 **거짓 양성**이 있고 현재 코드와 불일치한다. 저장소에 `backend/.venv/`와 실행 DB가 추적되고 있다.
- **왜 문제인가:** 리팩토링은 **"고쳤는데 다른 데가 깨지지 않았다"를 증명할 수단**이 있어야 시작할 수 있다. 지금은 그 수단이 없으므로, 테스트 기반 구축이 다른 모든 작업의 선행 조건이다.
- **근거:** `docs/evaluation.md` §3 테스트와 관측 가능성

### P9. AI 학습 지원 기능이 없다 — 이번 학기 핵심 과제

- **현상:** §1.4의 세 요소 중 **관찰만 구현되어 있고, 가상 실습과 AI 설명은 존재하지 않는다.**
- **왜 문제인가:** 현재 상태는 "학습용으로 만든 모니터링 도구"이지 학습 지원 시스템이 아니다. 학습자는 여전히 화면의 숫자가 정상인지 판단할 수 없고(문제 1), 위험한 명령을 연습할 곳도 없다(문제 3).
- **근거:** `backend/routers/`에 해당 라우터 없음, `frontend/src/pages/`에 해당 화면 없음

### 문제 우선순위

| 우선순위 | 항목 | 근거 |
|---|---|---|
| P0 | P8 | 검증 수단 없이 고치면 고쳤는지 알 수 없다. 모든 작업의 선행 조건 |
| P0 | P1, P2 | 토큰 위조·탈취가 동시에 가능한 상태. AI 기능을 붙이기 전에 막아야 한다 |

### 6.2 AI 요청 흐름 (신규 구현 대상)

```
학습자가 명령 입력
   |
   v
명령 실행 요청  ->  가상 상태 엔진 (services/virtual_linux.py)     <- AI 호출 없음
   |               상태 전이 + 시도 기록
   |
   +- 지원 명령           -> 상태 갱신, 터미널에 결과 표시
   +- 미지원/위험 문법     -> 상태 변경 없이 거부
          |
          v (선택적, 실패해도 학습에 영향 없음)
      AI 설명 요청 (services/bedrock.py)
          |  호출량 제한 통과 확인
          |  실패 -> degraded 표시, 규칙 기반 안내로 대체
          v
      AI 도우미 패널에 설명 추가

학습자가 채점 요청
   |
   v
채점 요청  ->  규칙 기반 채점기 (services/task_grader.py)          <- AI 호출 없음
   |          최종 가상 상태 vs 목표 상태 대조
   v
성공 / 부분 성공 / 실패  +  다음 문제 진도
```

**핵심 설계:** 상태 전이와 채점은 AI를 거치지 않는다. AI는 설명·힌트만 담당한다.
따라서 AI가 실패해도 학습 진행 자체는 결정론적으로 계속된다(§1.4 세 번째 요소).

### 9.2 작업 완료 게이트

각 작업은 아래를 **전부** 통과해야 완료로 표시한다.

```
1. 실패 테스트를 먼저 작성했고, 구현 전에 실제로 실패하는 것을 확인했다
2. 해당 작업의 focused 테스트 통과
3. backend 전체 테스트 통과
4. frontend 전체 테스트 + lint 통과
5. 보안 스캐너 검출 0건
6. docker compose 설정 검증 통과
7. 문서를 함께 갱신했다 (코드만 바꾸고 문서를 두지 않는다)
```

**1번이 핵심이다.** 실패를 먼저 재현하지 않으면 "고쳤다"를 증명할 수 없다.

### 9.3 M3 최종 수동 검증

| # | 항목 | 통과 기준 |
|---|---|---|
| 1 | 권한 전수 검증 | 전 경로가 계약대로 401/403/200 |
| 2 | 토큰 비노출 | 실제 발급 토큰 원문을 서버·Nginx·브라우저 로그에서 grep → 0건 |
| 3 | 셸 격리 | 셸 컨테이너에서 네트워크·Docker 소켓 접근 불가 |
| 4 | 비활성 사용자 차단 | 계정 비활성화 즉시 차단 |
| 5 | 기동 거부 | 환경변수 없거나 placeholder면 서버가 시작하지 않음 |
| 6 | AI 실호출 | 6문제 완주, `degraded=false` 확인 |
| 7 | **AI 실패 내성** | 자격증명을 일부러 무효화 → 서비스가 죽지 않고 규칙 기반으로 계속 진행 |
| 8 | AI 안전성 | 미지원·위험 문법 입력에 **실행된 것처럼 보이는 응답이 나오지 않음** |
| 9 | 수집 실패 구분 | 수집 실패가 0값이 아니라 503으로 반환 |
| 10 | 재기동 | 배포 서버 재기동 후 전 기능 정상 |

**7번을 반드시 한다.** AI 실패가 조용히 흡수되는 것이 이 시스템의 가장 큰 위험이므로,
"실패해도 안 죽는다"와 "실패했는지 알 수 있다"를 둘 다 확인해야 한다.

## 10. 완료 기준 및 기대 효과

### 10.1 완료 정의 (Definition of Done)

- [ ] 배포된 서버에서 AI 학습 시나리오 6문제를 처음부터 끝까지 완주할 수 있다
- [ ] AI 응답이 실제 모델 호출로 반환되고, 그 사실을 응답 필드로 확인할 수 있다
- [ ] AI가 실패해도 규칙 기반 대체로 학습이 계속된다
- [ ] 환경변수가 없거나 placeholder면 서버가 시작을 거부한다
- [ ] 토큰이 서버·Nginx·브라우저 로그 어디에도 남지 않는다
- [ ] 보호 경로 전체가 권한 계약대로 응답한다
- [ ] 백엔드가 호스트 Docker 소켓에 직접 접근하지 않는다
- [ ] 수집 실패가 0값으로 위장되지 않는다
- [ ] CI가 테스트·lint·빌드·보안 스캔을 상시 통과한다
- [ ] `docs/evaluation.md`와 동일 기준의 재평가 점수를 확보했다
- [ ] 해결하지 못한 한계가 목록으로 문서화되어 있고, 각각 개선 방향이 적혀 있다
- [ ] 30초/1분/3분 설명과 시연 스크립트가 준비되어 있고 리허설 2회를 마쳤다

### 10.2 기대 효과

| 관점 | 효과 | 근거 |
|---|---|---|
| 학습자 | 실제 서버를 망가뜨릴 위험 없이 서비스 복구·권한 설정·방화벽 진단을 연습한다. **명령 문자열이 아니라 최종 상태로 채점**되므로 다른 순서·다른 명령으로 목표에 도달해도 인정된다 | §1.4 가상 실습, AI-03 |
| 학습자 | 미지원 명령을 입력해도 "왜 안 되는지" 설명을 받는다. 막힌 지점에서 학습이 끊기지 않는다 | AI-04, AI-05 |
| 학습자 | 환경 구축 없이 브라우저만으로 시작한다 | §1.2 문제 2 |
| 시스템 | AI 장애가 학습 진행을 막지 않는다. 상태·채점이 AI와 분리되어 있기 때문이다 | §6.2, 검증 9.3-7 |
| 시스템 | 토큰 위조·탈취 경로가 닫히고, 백엔드가 뚫려도 호스트로 넘어가지 않는다 | SECRET-01/02, SHELL-02 |
| 공학적 | 문제 → 원인 → 실패 재현 → 수정 → 검증의 절차가 저장소에 기록으로 남는다 | §9.2 완료 게이트 |

### 10.3 완료 후에도 남는 한계 (숨기지 않고 기록한다)

| 한계 | 왜 남기는가 | 개선 방향 |
|---|---|---|
| 모니터링 지표를 AI에게 질의하는 기능 없음 | 관찰과 AI 실습이 한 시스템에 있지만 아직 연결되지 않았다. 이번 학기 범위 밖 | 지표 스냅샷을 AI 입력에 포함시키는 경로 신설 |
| 로그아웃이 토큰을 무효화하지 않음 | 서버 측 토큰 상태 저장이 필요해 범위 밖 | 토큰 블랙리스트 또는 refresh 토큰 구조 |
| 배포 환경에 도메인이 없어 HTTPS 미적용 가능성 | 도메인 확보가 통제 밖. IP에는 인증서를 발급받을 수 없다 | 도메인 확보 시 운영 프로필로 전환 |
| AI 호출 제한이 단일 프로세스 가정 | 규모상 분산 저장이 과설계 | 워커 증설 시 DB 기반 제한으로 전환 |
| AI 응답 품질의 정량 비교 없음 | 비교 실험은 이 과제 범위 밖 | 설계·구현의 타당성으로 서술하고, 비교는 향후 과제 |

**이 표를 발표 자료에 그대로 넣는다.** 한계를 먼저 말하는 쪽이 질의응답에서 유리하다.
