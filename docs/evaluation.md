# Linux Web GUI 프로젝트 평가

평가일: 2026-07-29  
평가 대상: 현재 작업 디렉터리의 소스 코드, 설정, 테스트 및 문서

## 1. 평가 개요와 검토 범위

이 평가는 시니어 개발자와 초보 학습자의 관점에서 프로젝트의 코드 품질,
운영 가능성 및 교육적 가치를 검토한 결과다.

다음 항목을 확인했다.

- `backend/`의 FastAPI 라우터, 인증·권한, SQLAlchemy 모델, 스케줄러,
  WebSocket 및 Docker 터미널 코드
- `frontend/src/`의 React 페이지, 공통 컴포넌트, 인증 상태, API 및
  WebSocket 클라이언트
- Dockerfile, Docker Compose, Nginx, Vite 및 의존성 선언
- 백엔드 테스트 스크립트와 테스트 결과 문서
- README와 학습 기록
- 저장소 추적 상태와 SQLite 스키마

다음 항목은 내용 전체를 코드처럼 평가하지 않았다.

- `node_modules/`, 가상 환경 패키지, 캐시 및 생성 파일
- PPTX와 SQLite의 실제 레코드 값
- 사용자가 평가 전에 만들어 둔 커밋되지 않은 변경의 작성 의도

SQLite는 테이블 구조만 확인했고 사용자명, 비밀번호 해시 등 실제 값은
평가 문서에 기록하지 않았다.

## 2. 프로젝트 및 핵심 흐름 요약

이 프로젝트는 React SPA가 Nginx를 통해 FastAPI에 REST와 WebSocket 요청을
보내고, FastAPI가 `psutil`로 수집한 시스템 정보를 SQLite에 저장하는 구조다.
관리자는 Docker 컨테이너로 격리된 웹 터미널도 사용할 수 있다.

핵심 흐름은 다음과 같다.

1. 사용자가 로그인하면 FastAPI가 JWT를 발급한다.
2. 프론트엔드는 JWT를 `localStorage`에 저장한다.
3. REST 요청은 `Authorization` 헤더, WebSocket은 쿼리 문자열로 JWT를 전달한다.
4. 대시보드는 5초마다 WebSocket으로 CPU, 메모리 및 프로세스 정보를 받는다.
5. 스케줄러는 1분마다 모니터링 스냅샷을 SQLite에 저장한다.
6. 관리자는 Docker 기반 셸과 사용자 관리 기능을 사용한다.
7. 파일시스템 학습 페이지와 네트워크 진단 페이지는 브라우저 내부 시뮬레이션이다.

계층 구분과 기능 범위는 학습 프로젝트로서 의미가 크다. 다만 JWT, 권한 검사,
Docker 소켓 및 프로세스 종료 기능이 한 시스템 안에 결합되어 있으므로 일반적인
CRUD 프로젝트보다 훨씬 엄격한 보안 경계가 필요하다.

## 4. 잘된 점

### 기능별 계층 구분

`backend/routers`, `backend/core`, `backend/schemas`, `backend/services`로 책임을
나누고 프론트엔드도 페이지, 컴포넌트, API 클라이언트 및 인증 Context를
분리했다. 초보자가 요청이 어느 계층을 통과하는지 추적하기 좋은 출발점이다.

### 실제 시스템 개념의 통합

단순 게시판을 넘어 다음 개념이 실제 사용자 흐름으로 연결되어 있다.

- FastAPI와 Pydantic 응답 모델
- SQLAlchemy 비동기 세션과 주기적 스냅샷
- JWT 인증과 역할 구분
- REST와 WebSocket의 차이
- `psutil` 기반 시스템 모니터링
- Nginx 리버스 프록시, TLS 및 WebSocket Upgrade
- Docker 컨테이너 자원 제한과 PTY

학습 주제의 폭과 연결성은 이 프로젝트의 가장 큰 장점이다.

### 방어 코드를 고려한 흔적

- 마지막 활성 관리자 보호 로직이 있다
  (`backend/routers/admin.py:208`).
- 셸 컨테이너에 메모리, CPU 및 PID 제한을 둔다
  (`backend/routers/shell.py:64`).
- WebSocket과 PTY 종료 시 작업과 컨테이너를 정리하려 한다
  (`backend/routers/shell.py:301`).
- 네트워크 트래픽 캐시를 Lock으로 보호한다
  (`backend/routers/network.py:15`).
- Nginx에 TLS 버전, HSTS, 프레임 차단, MIME 스니핑 차단 및 요청 제한을
  설정했다 (`frontend/nginx.conf:65`).

완전하지는 않지만 위험을 인식하고 코드로 다루려는 방향은 좋다.

### 학습 기록의 깊이

`docs/LEARNING_LOG.md`는 단순 작업 일지가 아니라 “무엇”과 “왜”를 구분하고,
Nginx, TLS, WebSocket 및 rate limit을 자기 말로 설명하도록 구성되어 있다.
면접 준비와 복습에 유용한 방식이다.

### 프론트엔드 사용자 경험

로딩, 오류, 연결 상태, 정렬, 확인 대화상자, 클립보드 복사 및 터미널 크기 조절
등 실제 관리 도구에 필요한 상호작용을 폭넓게 구현했다. React 상태와 Effect를
학습하기 좋은 예제가 많다.

## 5. 시니어 개발자 관점의 상세 평가

### 정확성과 안정성

라우터와 스키마의 기본 구조는 명확하지만, 코드와 정책이 불일치한다.
README는 프로세스 종료를 관리자 전용이라고 설명하지만 실제 엔드포인트는
로그인 사용자 여부만 확인한다. 사용자 관리 목록은 “본인과 본인이 만든 계정”으로
제한하면서 수정·삭제는 동일한 소유 범위를 검사하지 않는다.

마이그레이션도 현재 ORM 모델과 반대 방향이다. 모델은 계속 `username`을 사용하지만
마이그레이션은 이를 `login_id`로 바꾼다. 현재 DB 스키마도 `username`이므로 해당
스크립트를 실행하면 애플리케이션 쿼리가 깨진다.

CPU, 메모리 및 네트워크 라우터는 넓은 `except Exception` 뒤에 0 또는 빈 배열을
반환한다. 서비스 장애를 정상적인 “사용률 0%”로 보이게 하므로 운영자가 문제를
오인할 수 있다. 실제 Windows 검증에서도 `mem.buffers`가 없어 수집이 실패했지만
테스트는 0으로 채운 메시지를 정상으로 판정했다.

### 보안

현재 상태에서 가장 취약한 부분이다.

- 환경변수가 없으면 공개된 문자열을 JWT 서명 키로 사용한다
  (`backend/core/security.py:26`).
- 서버 시작 시 `admin/admin1234` 계정을 자동 생성한다
  (`backend/main.py:80`).
- 모니터링 WebSocket이 JWT 전체와 쿼리 문자열을 로그에 남긴다
  (`backend/routers/websocket.py:147`).
- 브라우저도 토큰이 포함된 WebSocket URL을 콘솔에 출력한다
  (`frontend/src/api/client.js:210`).
- Nginx의 `$request` 기반 access log에도 쿼리 문자열이 들어갈 수 있다
  (`frontend/nginx.conf:14`).
- 토큰 유효기간은 배포 설정에서 24시간이다
  (`docker-compose.yml:42`).

즉, 로그에 접근한 사람이 장시간 유효한 관리자 JWT를 얻을 수 있고, 기본 서명 키가
사용되면 토큰 자체를 위조할 수 있다. 그 토큰으로 Docker 터미널에 접근할 수 있어
영향 범위가 크다.

또한 모니터링 REST API 대부분은 인증 의존성이 없다. 특히 활성 연결과 프로세스
목록은 시스템 내부 정보를 노출한다. 브라우저의 `ProtectedRoute`는 UI 이동만
막을 뿐 API 보안 경계가 아니다.

Docker Compose는 `privileged: false`를 사용하지만 Docker 소켓을 백엔드에 그대로
마운트한다 (`docker-compose.yml:47`). Docker 소켓 접근 권한은 사실상 호스트
관리 권한에 가깝기 때문에 `privileged: false`만으로 격리됐다고 볼 수 없다.

### 구조와 유지보수성

백엔드의 기능별 라우터 분리는 좋다. 반면 다음 파일은 한 파일이 상태, 도메인 로직,
모달, 렌더링을 모두 담당한다.

- `frontend/src/pages/Filesystem.jsx`: 약 950줄
- `frontend/src/pages/NetworkDiagnostics.jsx`: 약 600줄
- `frontend/src/pages/Users.jsx`: 약 500줄

API 오류 처리도 여러 페이지에 반복된다. 공통 fetch 래퍼, 도메인 Hook 및 작은
프레젠테이션 컴포넌트로 나누면 변경 영향과 테스트 범위를 줄일 수 있다.

`axios`, `chart.js`, `react-chartjs-2`는 선언되어 있지만 현재 소스에서 사용되지
않는다 (`frontend/package.json:13`). `Users.css`, `PlaceholderPage.css`와 일부
import도 사용되지 않는다. 데모 프로세스 세 개는 환경 구분 없이 서버 시작 때마다
실행되어 운영 코드와 교육용 코드의 경계를 흐린다 (`backend/main.py:198`).

### 성능과 자원 효율

`async def` 내부에서 `psutil.cpu_percent(interval=...)`를 직접 호출해 이벤트 루프를
막는다 (`backend/routers/cpu.py:25`, `backend/routers/websocket.py:55`).
WebSocket 연결마다 별도로 전체 프로세스를 순회하고 CPU 메트릭을 수집하므로
사용자가 늘수록 같은 작업이 반복된다 (`backend/routers/websocket.py:163`).
주석은 “브로드캐스트”라고 하지만 실제로는 연결별 수집·전송이다.

셸 시작과 정리의 `subprocess.Popen`, `wait`, `docker rm`도 이벤트 루프에서 동기
실행된다. 소수 사용자 실습에는 동작할 수 있지만 지연이 발생하면 다른 요청도
함께 멈출 수 있다.

히스토리 집계는 기간의 모든 행을 Python 메모리로 읽어 그룹화한다. 7일 데이터는
작은 규모에서 괜찮지만 장기 보관이나 수집 주기 단축 시 DB 집계 또는 다운샘플링이
필요하다. 오래된 스냅샷 삭제 함수는 존재하지만 스케줄러에 등록되지 않았다
(`backend/services/scheduler.py:89`).

### 테스트와 관측 가능성

현재 `backend/test` 파일은 pytest 테스트가 아니라 실행형 출력 스크립트다.
프로젝트 루트 또는 백엔드에서 그대로 실행하면 잘못된 `sys.path` 설정 때문에
import 단계에서 실패한다 (`backend/test/test_endpoints.py:7`).

`PYTHONPATH`를 보정해 실행하면 세 스크립트의 종료 코드는 모두 0이었지만,
WebSocket 테스트는 `test-token`, `demo-token` 검증 실패를 `❌`로 출력하고도
마지막에 “모든 검증 통과”라고 출력했다
(`backend/test/test_websocket.py:40`, `backend/test/test_websocket.py:164`).
토큰 검증 뒤에 `all_valid`를 갱신하지 않기 때문이다.

현재 코드는 5초 주기 JWT 방식인데 테스트와 보고서는 정적 토큰과 1초 주기를
계속 설명한다. 따라서 테스트 문서의 “모든 테스트 통과”를 현재 품질 근거로
사용할 수 없다.

로그는 풍부하지만 JWT 전체를 남기는 등 관측 가능성과 보안의 경계가 지켜지지
않는다. 반대로 메트릭 수집 실패는 빈 배열이나 0으로 숨겨져 원인 추적이 어렵다.

### 문서와 배포

README는 아키텍처와 API를 이해하는 데 도움이 되지만 실제 상태와 다른 부분이 있다.

- 존재하지 않는 루트 `nginx/` 디렉터리를 구조도에 표시한다
  (`README.md:87`).
- 프로세스 종료를 관리자 전용이라고 설명하지만 코드와 다르다
  (`README.md:164`).
- `privileged: false`를 “호스트 접근 최소화” 근거로 들지만 Docker 소켓과
  `/home/webterm`을 쓰기 가능으로 마운트한다 (`README.md:212`).
- Nginx rate limit과 TLS를 강조하지만 백엔드 8000 포트를 호스트에 직접 공개하여
  Nginx를 우회할 수 있다 (`docker-compose.yml:37`).
- 인증서가 없으면 HTTP 모드로 실행되어 JWT와 터미널 트래픽이 평문으로 전송될 수
  있지만 운영 주의가 충분하지 않다 (`frontend/start.sh:19`).

Docker Compose 문법 검사는 통과했으나 `version` 속성이 더 이상 사용되지 않는다는
경고가 발생했다. 프론트 Dockerfile은 lockfile이 있는데도 `npm ci`가 아닌
`npm install`을 사용해 재현성을 낮춘다.

## 6. 학습자 관점의 상세 평가

### 시작 가능성

Docker 빠른 시작은 간단하지만 다음 내용이 빠져 있다.

- 프론트엔드와 백엔드의 로컬 개발 실행 순서
- Windows, Linux 및 Raspberry Pi에서 달라지는 `psutil` 필드
- 테스트 실행 명령과 기대 결과
- 기본 관리자 계정의 안전한 최초 설정 절차
- Docker 소켓과 프로세스 종료 기능의 위험성
- 실패했을 때 확인할 로그와 대표 오류

아무것도 모르는 학습자가 README만 보고 안전하게 실행하기에는 부족하다.

### 코드 이해 가능성

라우터와 스키마가 기능별로 나뉘어 있어 REST 흐름을 따라가기 쉽다. Pydantic 모델과
한글 주석도 입문자에게 도움이 된다. 반면 주석이 코드 줄마다 번역하듯 붙은 곳과
이유를 설명하는 곳이 섞여 있다. 일부 주석은 현재 코드와 맞지 않아 잘못된 개념을
학습시킬 수 있다.

프론트엔드의 대형 페이지는 한 번에 너무 많은 상태 변경 규칙을 읽어야 한다.
작은 Hook과 컴포넌트로 분리하고 각 단위에 테스트를 붙이면 학습 순서가 더
명확해진다.

### 학습 효과

학습 소재 자체는 매우 좋다. 로그인부터 실시간 모니터링, 데이터 저장, 리버스
프록시와 컨테이너 터미널까지 하나의 제품 흐름으로 경험할 수 있다. 특히
`docs/LEARNING_LOG.md` 방식은 기술 선택의 이유를 말로 설명하는 연습에 효과적이다.

다만 네트워크 진단 페이지는 실제 명령을 실행하는 것처럼 표시하면서 결과는
고정값과 난수로 생성한다 (`frontend/src/pages/NetworkDiagnostics.jsx:55`).
파일시스템 페이지는 로그에서 교육용 가상 환경이라고 밝히지만, 네트워크 진단은
화면에서 시뮬레이션임을 명확히 알리지 않는다. 학습자가 실제 네트워크 결과라고
오해할 수 있다.

### 안전한 실습과 확장

실습용 셸을 별도 컨테이너에서 실행하고 자원 제한을 둔 점은 좋다. 하지만 백엔드가
Docker 소켓을 직접 소유하고, 기본 관리자와 기본 JWT 키가 있으며, viewer도
프로세스를 종료할 수 있어 초보자의 실수를 흡수할 안전장치가 충분하지 않다.

셸 파일 트리는 심볼릭 링크를 구분하지 않고 재귀 탐색한다
(`backend/routers/shell.py:367`). 컨테이너 사용자가 홈 디렉터리에 호스트 절대
경로를 가리키는 링크를 만들면 백엔드 기준 경로를 따라갈 가능성이 있다.
최소한 루트 경로 검증, 심볼릭 링크 미추적, 깊이·항목 수 제한이 필요하다.

단계별 연습 문제와 자동 채점 테스트도 없다. “CPU API에 인증 추가”, “viewer의
kill 요청은 403”, “WebSocket 토큰을 로그에 남기지 않기” 같은 과제를 테스트와
연결하면 학습 효과가 크게 높아진다.

## 7. 우선순위별 개선점

### 7.1 기본 자격 증명과 JWT 노출 제거

1. **코드 위치**: `backend/core/security.py:26`, `backend/main.py:80`,
   `backend/routers/websocket.py:147`, `frontend/src/api/client.js:210`,
   `frontend/nginx.conf:14`
2. **우선순위**: P0
3. **현재 상태**: 기본 JWT 키와 `admin/admin1234`가 코드에 있고, JWT가 서버,
   브라우저 및 프록시 로그에 노출될 수 있다.
4. **이유와 영향**: 관리자 토큰 위조 또는 탈취가 Docker 터미널 접근으로 이어질
   수 있다. 현재 배포 설정에서는 토큰이 24시간 유효하다.
5. **개선 방향**: 운영 시작 시 강한 `SECRET_KEY`가 없으면 즉시 실패하게 하고,
   기본 관리자 자동 생성을 제거한다. 최초 관리자 생성용 일회성 CLI 또는
   만료되는 초기화 토큰을 제공한다. 모든 로그에서 토큰과 쿼리 문자열을
   마스킹하고 WebSocket 인증용 짧은 수명의 일회성 티켓을 도입한다.
6. **검증 방법**: 키가 없을 때 서버 시작 실패, 로그 검색 시 JWT 패턴 0건,
   기본 관리자 로그인 실패, 일회성 티켓 재사용 실패를 자동 테스트한다.

### 7.2 프로세스 종료 권한을 백엔드에서 강제

1. **코드 위치**: `backend/routers/process.py:61`,
   `frontend/src/App.jsx:85`, `frontend/src/pages/Processes.jsx:228`,
   `README.md:164`
2. **우선순위**: P0
3. **현재 상태**: 종료 API는 `get_current_user`만 사용하고 role을 검사하지 않으며,
   viewer 화면에도 Kill 버튼이 표시된다.
4. **이유와 영향**: 일반 사용자가 서비스 프로세스를 종료해 장애를 만들 수 있고
   문서의 권한 정책과 실제 보안 경계가 다르다.
5. **개선 방향**: 엔드포인트 의존성을 `get_current_admin`으로 변경하고, 프론트도
   관리자에게만 버튼을 표시한다. 종료 가능한 PID 또는 프로세스 범위를
   allowlist로 제한하고 감사 로그를 남긴다.
6. **검증 방법**: 미인증 401, viewer 403, admin 허용, PID 1·백엔드·허용 외
   프로세스 403을 통합 테스트한다.

### 7.3 모든 시스템 정보 API에 일관된 인증 적용

1. **코드 위치**: `backend/routers/cpu.py:16`,
   `backend/routers/memory.py:15`, `backend/routers/network.py:169`,
   `backend/routers/history.py:26`, `backend/routers/websocket.py:31`
2. **우선순위**: P1
3. **현재 상태**: 대부분의 REST 모니터링 API는 인증이 없고, WebSocket은 JWT의
   서명과 `sub`만 확인해 비활성화·삭제된 사용자를 DB에서 재검증하지 않는다.
4. **이유와 영향**: 내부 프로세스, 네트워크 연결 및 이력 정보가 직접 노출된다.
   계정 비활성화 뒤에도 기존 토큰이 만료될 때까지 WebSocket을 사용할 수 있다.
5. **개선 방향**: 라우터 수준에 `get_current_user`를 적용하고 민감도에 따라
   admin 전용 API를 나눈다. WebSocket 연결 시 DB에서 활성 사용자와 현재 role을
   확인하고 토큰에 `jti` 또는 세션 버전을 넣어 폐기 가능하게 한다.
6. **검증 방법**: 모든 보호 API와 두 WebSocket에 대해 미인증, 비활성 사용자,
   viewer, admin 행렬 테스트를 작성한다.

### 7.4 Docker 터미널의 호스트 권한 경계 축소

1. **코드 위치**: `docker-compose.yml:37`, `docker-compose.yml:47`,
   `backend/routers/shell.py:64`, `frontend/start.sh:19`
2. **우선순위**: P1
3. **현재 상태**: 백엔드 포트가 직접 공개되고 Docker 소켓을 백엔드에 마운트한다.
   셸 컨테이너는 bridge 네트워크를 사용하며 인증서가 없으면 전체 서비스가
   HTTP로 실행된다.
4. **이유와 영향**: Nginx의 TLS와 rate limit을 우회할 수 있고, 백엔드 침해가
   Docker 제어권과 호스트 침해로 확대될 수 있다.
5. **개선 방향**: 백엔드 포트는 Compose 내부에만 `expose`하고 Nginx만 공개한다.
   Docker 소켓 프록시 또는 별도 최소 권한 실행 서비스를 두고 허용 명령을
   제한한다. 셸 컨테이너는 필요 없으면 `--network none`, read-only rootfs,
   capability drop, seccomp/AppArmor 및 사용자별 동시 세션 제한을 적용한다.
   운영 프로필은 인증서 없을 때 시작을 거부한다.
6. **검증 방법**: 호스트에서 8000 직접 접속 실패, 셸에서 외부 네트워크 차단,
   허용되지 않은 Docker API 거부 및 컨테이너 탈출 시나리오를 확인한다.

### 7.5 셸 파일 트리의 경로 탈출과 무제한 재귀 방지

1. **코드 위치**: `backend/routers/shell.py:367`
2. **우선순위**: P1
3. **현재 상태**: `Path.is_dir()`와 `iterdir()`로 심볼릭 링크를 따라가며 깊이,
   항목 수 및 전체 응답 크기 제한 없이 전체 트리를 3초마다 만든다.
4. **이유와 영향**: 호스트 경로 메타데이터 노출, 순환 링크, 매우 큰 디렉터리로
   인한 CPU·메모리 고갈 및 이벤트 루프 정지가 가능하다.
5. **개선 방향**: 링크는 `lstat`으로 구분해 따라가지 않고, 모든 resolved path가
   사용자 홈 아래인지 확인한다. 지연 로딩 API, 최대 깊이·항목 수·응답 크기 및
   요청 간 캐시를 도입한다.
6. **검증 방법**: `/`, 상위 경로 및 순환 링크를 가리키는 심볼릭 링크가 트리를
   벗어나지 않는지, 대형 디렉터리 응답이 제한되는지 테스트한다.

### 7.6 테스트를 자동화하고 거짓 양성을 제거

3. **현재 상태**: 전체 추적 파일 4,842개 중 4,717개가 `backend/.venv` 또는

6. **검증 방법**: `git ls-files` 결과에 venv, pyc 및 실행 DB가 0건이고,

### 7.9 블로킹 수집을 공유 백그라운드 작업으로 변경

1. **코드 위치**: `backend/routers/cpu.py:25`,
   `backend/routers/websocket.py:48`, `backend/routers/websocket.py:163`,
   `backend/routers/shell.py:54`
2. **우선순위**: P2
3. **현재 상태**: 동기 `psutil`과 subprocess 호출을 이벤트 루프에서 실행하고
   WebSocket 연결별로 같은 메트릭을 다시 수집한다.
4. **이유와 영향**: 느린 시스템 호출 하나가 다른 API와 WebSocket을 지연시키고,
   접속자 수에 비례해 프로세스 순회 비용이 증가한다.
5. **개선 방향**: `asyncio.to_thread` 또는 전용 executor를 사용하고, 한 개의
   수집 태스크가 만든 불변 스냅샷을 모든 연결에 fan-out한다. 셸 시작·정리에도
   timeout과 비동기 경계를 적용한다.
6. **검증 방법**: 1, 10, 50개 동시 연결에서 수집 횟수, 이벤트 루프 지연,
   CPU 사용량 및 p95 응답 시간을 비교한다.

### 7.10 오류와 데이터 보존 정책을 명시

1. **코드 위치**: `backend/routers/network.py:87`,
   `backend/routers/memory.py:37`, `backend/services/scheduler.py:89`
2. **우선순위**: P2
3. **현재 상태**: 광범위한 예외를 빈 데이터로 바꾸고, 오래된 스냅샷 삭제 함수는
   실제 스케줄에 등록되지 않았다.
4. **이유와 영향**: 장애와 정상 0값을 구분할 수 없고 DB가 계속 증가한다.
5. **개선 방향**: 예상 가능한 OS별 예외만 처리하고 구조화된 오류 응답과
   원인 로그를 사용한다. 메트릭에 stale/error 상태를 포함하고 보존 기간과
   집계 정책을 환경변수로 설정한다. 삭제는 행 단위 반복 대신 SQL DELETE를 쓴다.

## 8. 빠르게 적용할 수 있는 개선 사항

기능 구조를 크게 바꾸지 않고 먼저 적용할 수 있는 작업은 다음과 같다.

1. WebSocket과 브라우저 콘솔에서 JWT 출력 제거
2. 프로세스 종료 API를 `get_current_admin`으로 변경
3. 기본 JWT 키와 기본 관리자 생성 제거
4. 백엔드 8000 호스트 포트 공개 제거
5. 테스트의 `sys.path` 조작 제거 및 실패 시 non-zero 반환
6. README의 경로, 5초 주기 및 권한 표 수정
7. 네트워크 진단 화면에 “교육용 시뮬레이션” 표시
8. 미사용 프론트엔드 의존성과 CSS 제거
9. Dockerfile의 `npm install`을 `npm ci`로 변경
10. Compose의 obsolete `version` 키 제거

이 중 1~4는 운영 배포 전에 반드시 처리해야 한다.

## 11. 평가 한계 및 확인하지 못한 사항

- 실행 중인 Linux 또는 Raspberry Pi 호스트에서 실제 시스템 지표를 검증하지 않았다.
- Docker 이미지 전체 빌드와 실제 컨테이너 셸 탈출 테스트는 수행하지 않았다.
- 유효한 운영 JWT와 실행 서버가 필요한 `test_websocket_live.py`는 실행하지 않았다.
  해당 스크립트는 현재 코드에서 유효하지 않은 정적 `test-token`과 1초 주기를
  전제로 하므로 먼저 수정해야 한다.
- TLS 인증서 발급·갱신과 실제 도메인의 HTTPS 동작은 검증하지 않았다.
- PPTX와 SQLite 실제 데이터 값은 개인정보·바이너리 제외 원칙에 따라 평가하지 않았다.
- 현재 작업 디렉터리에 평가 전부터 존재한 삭제·미추적 파일은 되돌리거나 수정하지 않았다.

## 12. 최종 결론

### 이 프로젝트는 전반적으로 잘 설계되었는가?

기능 분리와 학습 주제 선정은 좋지만 현재 상태를 “잘 설계된 운영 가능한
프로젝트”라고 평가하기는 어렵다. 특히 인증·권한 정책이 백엔드에서 일관되게
강제되지 않고, JWT와 Docker 소켓이 결합된 보안 위험이 크다.

### 현재 상태로 운영 환경에 사용해도 되는가?

아니다. 기본 관리자와 기본 JWT 키, 토큰 로그 노출, viewer의 프로세스 종료,
백엔드 직접 공개 및 Docker 소켓 경계를 먼저 해결해야 한다. P0와 P1 항목이
해결되고 자동 보안 회귀 테스트가 생기기 전에는 외부 네트워크에 배포하지 않는
것이 안전하다.

### 초보 학습자에게 적합하며 실제 학습 효과가 있는가?

지도자가 함께 보안 위험과 시뮬레이션을 설명한다면 학습 효과가 있다. React,
FastAPI, WebSocket, DB, Nginx와 Docker가 연결되는 모습을 배울 수 있다는 점은
매우 좋다. 그러나 아무것도 모르는 학습자가 현재 코드를 모범 답안으로 그대로
받아들이면 잘못된 권한 검사, 비밀 관리 및 테스트 습관까지 학습할 수 있다.
P0/P1 개선 후 단계별 과제와 테스트를 추가하면 좋은 중급 풀스택·서버 학습
프로젝트가 될 가능성이 충분하다.

### 가장 먼저 개선해야 할 세 가지

1. 기본 비밀·기본 관리자와 모든 JWT 로그 노출을 제거한다.
2. 프로세스 종료, 시스템 정보 및 셸의 권한을 백엔드에서 다시 설계하고 Docker
   소켓 경계를 축소한다.
3. 거짓 양성이 없는 자동 테스트와 clean build를 구성하고, 마이그레이션·README·
   시뮬레이션 설명을 실제 코드와 일치시킨다.
