# 4. 시스템 구현

본 장에서는 3장에서 기술한 설계를 실제로 구현한 결과를 기능 단위로 설명하고, 구현이
설계대로 동작하는지 실행해 확인한 결과를 정리한다.

서술 대상은 서버와 연동되는 기능으로 한정한다. 파일 조작 명령을 연습하는 화면과 네트워크 진단 명령의 출력 형태를 보여 주는 화면은 서버 API를 호출하지 않고 브라우저 내부에서 결과를 생성하는 보조 학습 화면이므로 본 장에서는 다루지 않는다. 4.4절의 가상 파일 탐색기는 이 화면들과 달리 실제 셸 세션의 홈 디렉터리를 읽는 기능이다.

## 4.1 사용자 인증 및 권한 관리

회원가입 과정에서는 사용자명 형식, 비밀번호 길이 및 비밀번호 확인 입력의 일치 여부를 검증한 후 계정을 생성한다. 회원가입을 통해 생성되는 계정의 역할은 항상 일반 사용자로 설정하며, 비밀번호는 해시 형태로만 저장한다.

로그인 과정에서는 사용자 조회, 비밀번호 검증 및 계정 활성 상태 확인을 순서대로 수행한다. 이 세 가지 경우에 대한 실패 응답은 모두 동일하게 처리한다. 비활성 계정에 대해서만 별도의 응답을 반환할 경우, 올바른 비밀번호를 입력한 사용자가 해당 응답을 통해 자격 증명의 유효성을 확인할 수 있기 때문이다. 인증에 성공하면 만료 시간이 포함된 토큰을 발급하고 로그인 이력을 기록한다.

권한 판정은 서버에서 수행한다. 보호된 요청이 전달될 때마다 토큰을 검증한 후 데이터베이스에서 사용자를 다시 조회하여 현재 활성 상태와 역할을 확인한다. 따라서 토큰이 발급된 이후 계정이 비활성화되거나 역할이 변경되더라도 해당 변경 사항이 즉시 반영된다. 인증 자체에 실패한 경우와 인증은 성공했지만 역할이 부족한 경우는 서로 다른 오류 응답 코드로 구분한다. 프론트엔드에서 메뉴 노출이나 화면 접근을 제한하는 기능은 화면 표시를 위한 것이며, 실제 권한 판정의 근거로 사용하지 않는다.

관리자는 계정 목록 조회, 계정 생성, 역할 및 활성 상태 변경, 계정 삭제, 로그인 이력 조회 기능을 사용할 수 있다. 다만 관리자가 자신의 역할이나 활성 상태를 변경하거나 자신의 계정을 삭제하는 것은 허용하지 않는다. 또한 활성 상태인 관리자가 한 명만 남아 있는 경우에는 해당 계정을 일반 사용자로 변경하거나 비활성화 또는 삭제하는 요청을 거부한다. 이 과정에서는 조회와 변경 사이에 다른 요청이 개입하지 않도록 변경 요청을 직렬화한 후 조건을 검사한다.

## 4.2 실시간 서버 자원 모니터링

실시간 서버 자원 모니터링은 하나의 백그라운드 수집기를 중심으로 동작한다. 수집기는 5초 간격으로 하나의 서버 상태 스냅샷을 생성한다. 각각의 WebSocket 연결은 서버 자원을 직접 수집하지 않고, 수집기가 생성한 공유 스냅샷을 기다린 후 이를 사용자에게 전송한다. 따라서 접속자 수가 증가하더라도 서버 자원 수집 횟수는 증가하지 않는다.

서버 자원 수집 과정에는 일정 시간 동안 처리가 중단되는 블로킹 호출이 포함될 수 있으므로, 이러한 호출은 별도의 스레드에서 실행한다. 수집 과정에서 오류가 발생하면 기본값으로 구성된 스냅샷을 반환하고 다음 수집 주기를 계속 진행한다. 이를 통해 일시적인 수집 실패가 전체 모니터링 기능의 중단으로 이어지지 않도록 하였다.

스냅샷에는 전체 CPU 사용률, 코어별 CPU 사용률, 부하 평균, 메모리 사용량 및 자원 사용량이 높은 프로세스 목록이 포함된다. 메모리 정보는 버퍼와 캐시를 합산하지 않고 별도의 항목으로 유지한다. 수집 단계에서 해당 값을 합산하면 이후 어떤 계층에서도 캐시가 점유한 메모리와 실제 사용 중인 메모리를 구분할 수 없기 때문이다.

실시간으로 갱신되는 데이터는 WebSocket을 통해 제공하며, 특정 시점의 값이나 조회 조건이 필요한 데이터는 REST API를 통해 제공한다. WebSocket 연결 주소에는 인증 정보를 포함하지 않는다. 사용자는 별도로 발급받은 일회용 티켓을 WebSocket 연결 후 첫 번째 메시지로 전달하며, 서버는 해당 티켓을 한 번만 사용한 후 사용자의 현재 상태를 다시 확인한다. 이 인증 절차가 완료되기 전에는 사용자에게 어떠한 데이터도 전송하지 않는다.

REST API를 통해서는 CPU, 메모리, 디스크, 프로세스 정보와 네트워크 인터페이스, 트래픽, 패킷 및 연결 상태를 조회할 수 있다. 네트워크 트래픽은 누적값과 함께 직전 호출과의 차이를 이용해 계산한 초당 전송량을 제공한다. 연결 상태 정보는 특정 프로세스가 어느 주소와 통신하고 있는지를 보여줄 수 있으므로 관리자만 조회할 수 있도록 제한하였다.

서버 자원 수집에 실패한 경우에는 빈 목록이나 0을 반환하지 않고, 수집에 실패한 자원을 명시한 오류로 응답한다. 실제 자원 사용률이 0인 경우와 자원 정보 수집에 실패한 경우를 프론트엔드에서 구분할 수 있어야 하기 때문이다.

프로세스 종료 기능은 관리자만 사용할 수 있다. 다만 서버의 모든 프로세스를 임의로 종료할 수 있는 것은 아니며, 본 시스템이 직접 실행하고 관리하는 학습용 프로세스만 종료 대상으로 제한하였다.

프론트엔드는 WebSocket 연결이 중단되면 새로운 일회용 티켓을 발급받아 일정한 간격으로 재연결을 시도한다. 또한 현재 연결 상태를 화면에 항상 표시한다. WebSocket 연결 자체가 유지되고 있더라도 일정 시간 이상 새로운 데이터가 도착하지 않으면 응답 없음 상태로 표시한다. 이는 화면에 남아 있는 마지막 수신 값을 학습자가 현재 서버 상태로 오인하는 것을 방지하기 위한 것이다.

## 4.3 모니터링 이력 조회

모니터링 이력은 스케줄러가 1분 간격으로 최신 서버 상태 스냅샷을 데이터베이스에 저장하는 방식으로 구성하였다. 이 과정에서도 서버 자원을 새로 수집하지 않고 백그라운드 수집기가 생성한 공유 스냅샷을 재사용한다. 따라서 이력 저장 기능이 추가되더라도 서버 자원 수집 횟수는 증가하지 않는다.

이력으로 저장하는 대상은 CPU 사용량, 메모리 사용량 및 자원 사용량이 높은 프로세스 정보이다. 디스크와 네트워크 정보는 데이터베이스에 저장하지 않고 실시간 조회 기능으로만 제공한다.

모니터링 이력 조회 기능은 세 가지 방식으로 제공한다. 첫 번째는 기간과 간격을 지정하는 집계 조회이다. 집계 조회에서는 각 구간에 대한 CPU 및 메모리 사용량의 평균값, 최솟값, 최댓값과 함께 해당 구간에 포함된 표본 수를 반환한다. 동일한 평균값이라도 몇 개의 측정값을 기반으로 계산되었는지에 따라 결과의 해석이 달라질 수 있으므로 표본 수를 함께 제공한다.

두 번째는 저장된 원본 스냅샷을 시간순으로 조회하는 기능이며, 세 번째는 지정한 시간 범위의 백분위수를 포함한 통계 정보를 반환하는 기능이다.

다만 이 세 가지는 API로만 제공하며, 이를 호출하는 화면은 구현하지 않았다. 대시보드에 표시되는 시계열 그래프는 저장된 이력을 조회한 결과가 아니라 WebSocket으로 수신한 값을 화면에서 누적한 것이므로, 화면을 다시 열면 이전 값은 남지 않는다.

원본 스냅샷은 시간이 지날수록 계속 증가하므로 별도의 보존 기간을 설정하였다. 주기적으로 실행되는 정리 작업은 보존 기간이 지난 스냅샷을 하나의 질의를 통해 일괄 삭제한다. 자동 삭제 대상은 모니터링 스냅샷으로 한정하며, 사용자 정보, 인증 기록 및 학습 관련 기록에는 자동 삭제 정책을 적용하지 않는다.

## 4.4 웹 터미널 기반 실습 환경

웹 터미널은 브라우저에 표시되는 터미널 화면과 서버에서 생성한 컨테이너 내부의 셸을 연결하는 방식으로 구현하였다. 접속 인증에는 모니터링 기능과 동일한 일회용 티켓 방식을 사용하지만, 티켓의 용도는 서로 구분한다. 웹 터미널용 티켓을 발급받기 위해서는 관리자 권한이 필요하며, WebSocket 연결 이후에도 사용자의 활성 상태와 현재 역할을 다시 확인한다.

한 명의 사용자는 동시에 하나의 웹 터미널 세션만 사용할 수 있으며, 시스템 전체에서 동시에 실행할 수 있는 세션 수에도 상한을 설정하였다.

셸은 호스트 시스템에서 직접 실행하지 않고 사용자 세션마다 새로 생성되는 컨테이너에서 실행한다. 해당 컨테이너에는 네트워크 차단, 읽기 전용 루트 파일시스템, 모든 커널 권한 제거, 권한 상승 금지, 비특권 사용자 실행, 임시 영역에서의 실행 금지, 메모리·CPU·프로세스 수 제한을 적용한다.

컨테이너에서 쓰기가 가능한 영역은 사용자별 홈 디렉터리 하나로 제한하며, 세션이 종료되면 해당 컨테이너를 제거한다. 또한 백엔드는 호스트의 Docker 소켓에 직접 접근하지 않고, 필요한 기능만 제한적으로 제공하는 프록시를 통해 Docker 기능을 사용한다.

가상 파일 탐색기는 사용자가 자신의 홈 디렉터리를 웹 화면에서 탐색할 수 있도록 구현하였다. 한 번의 요청에서는 하나의 디렉터리와 해당 디렉터리의 직계 하위 항목만 반환한다. 심볼릭 링크는 따라가지 않으며, 탐색 깊이, 항목 수, 응답 크기 및 처리 시간에 각각 상한을 설정하였다. 사용자는 자신의 세션에 포함된 파일에만 접근할 수 있다.

실습 환경 초기화 기능은 해당 사용자의 현재 세션을 먼저 정리한 후, 사용자 홈 디렉터리의 내용을 삭제하고 새로운 홈 디렉터리를 생성하는 방식으로 동작한다.

## 4.5 가상 Linux 상태 기반 학습 시나리오

가상 Linux 학습은 세션 단위로 진행한다. 학습자가 문제를 선택하면 해당 문제에 정의된 초기 상태를 현재 학습 세션으로 복사한다. 이후 학습자가 입력한 명령은 실제 시스템에서 실행되지 않고, 세션에 저장된 가상 상태를 변경하는 입력으로만 사용된다.

명령 처리 과정에서는 언어모델을 호출하지 않는다. 명령을 입력했을 때 표시되는 결과 또한 언어모델이 생성하는 것이 아니라, 동일한 입력에 대해 항상 동일한 결과를 반환하는 결정적 시뮬레이터가 생성한다.

입력된 명령은 먼저 구문 검사를 거친다. 명령 연결, 파이프, 명령 치환 및 리다이렉션과 같은 셸 메타문자가 포함된 입력은 이 단계에서 거부한다. 구문 검사를 통과한 입력은 셸을 통해 실행하지 않고 토큰 단위로 분리한 후 허용 목록과 비교한다. 허용된 명령이라도 사용 가능한 인자의 형태를 각각 검증한다.

명령 검증에 금지 목록이 아닌 허용 목록을 사용한 이유는 새로운 우회 표현에 대응하기 위해서이다. 금지 목록 방식은 새로운 우회 표현이 발견될 때마다 항목을 계속 추가해야 하지만, 허용 목록 방식에서는 사전에 정의되지 않은 입력을 모두 거부할 수 있다.

가상 상태의 변경은 원본 상태가 아닌 복사본에서 수행한다. 지원하지 않는 문법이 입력되거나 해당 명령에 적용할 수 있는 상태 전이 규칙이 없으면, 변경 이전의 상태를 그대로 반환한다. 따라서 잘못된 명령으로 인해 진행 중인 학습 상태가 손상되지 않는다.

가상 상태에는 서비스 실행 여부와 자동 시작 설정, 사용자 생성과 비밀번호 설정, 파일 소유권과 권한, 방화벽 규칙, 패키지 설치 상태 등이 포함된다. 서비스 상태나 방화벽 규칙이 변경되면 원격 접속 가능 여부도 함께 다시 계산한다. 이를 통해 학습자는 서비스와 방화벽의 두 조건이 모두 충족되어야 원격 접속이 가능하다는 점을 상태 변화를 통해 확인할 수 있다.

학습 내용은 프로그램 코드에 직접 작성하지 않고 별도의 외부 정의 파일로 관리한다. 학습 시나리오는 서비스 장애 복구, 계정 및 파일 권한 구성, 방화벽과 원격 접속 장애의 세 가지로 구성되며, 각 시나리오에는 두 개의 문제가 포함된다. 각각의 문제에는 초기 상태, 목표 상태, 채점 규칙, 단계별 힌트 및 정답 예시가 함께 정의되어 있다. 전체 커리큘럼의 마지막 단계에서는 앞서 해결한 문제를 다시 제시하는 복습 라운드를 제공한다.

채점 과정에서는 성공, 부분 성공, 실패 순서로 규칙을 확인하고, 가장 먼저 일치하는 결과를 최종 판정으로 사용한다. 판정 기준은 학습자가 어떤 명령어를 입력했는지가 아니라, 명령 처리 이후의 최종 가상 상태가 목표 상태를 충족했는지 여부이다. 따라서 서로 다른 명령어를 사용하더라도 동일한 목표 상태에 도달한 경우에는 모두 정답으로 인정한다.

예를 들어 중지된 서비스를 시작하는 문제에서는 서비스 시작 명령과 서비스 재시작 명령을 모두 성공으로 판정한다. 반면 서비스의 자동 시작만 설정하고 현재 서비스를 실행하지 않은 경우에는 부분 성공으로 판정한다. 이를 통해 학습 방향은 올바르지만 아직 하나의 조건이 충족되지 않았다는 점을 학습자에게 안내한다.

학습자는 채점 결과가 성공일 때만 다음 문제로 이동할 수 있으며, 부분 성공이나 실패로 판정된 경우에는 현재 문제에 계속 머무른다.

## 4.6 생성형 AI 질의응답 및 설명 생성

언어모델을 호출하는 기능은 학습자의 질문 처리와 힌트 요청의 두 가지 경우로 제한하였다. 두 경우 모두 서버가 먼저 현재 가상 상태를 규칙에 따라 채점하고 판정 결과를 확정한 후, 해당 판정과 상태 정보를 포함한 입력을 생성하여 언어모델을 호출한다. 즉 판정이 먼저 수행되고 설명이 이후에 생성되며, 이 순서는 변경되지 않는다.

언어모델에 전달하는 정보에는 학습자 수준, 문제 정의, 현재 가상 상태, 서버에서 확정한 판정 결과, 학습자의 입력, 최근 대화 및 해당 세션의 최근 채점 이력이 포함된다. 실제 서버의 자원 사용량은 언어모델 입력에 포함하지 않는다. 생성형 AI가 설명하는 대상은 가상 실습 상태와 채점 결과이며, 실제 서버의 자원 사용량은 모니터링 화면에서 수치와 그래프로 제공한다.

프롬프트는 데이터를 자연어 문장에 직접 삽입하는 방식이 아니라 구조화된 형태로 구성한다. 학습자의 입력과 이전 대화처럼 신뢰할 수 없는 텍스트는 별도의 영역에 배치하고, 해당 내용을 시스템 지시가 아니라 인용된 데이터로 처리하도록 명시한다.

현재 가상 상태와 서버에서 확정한 판정 결과는 변경할 수 없는 사실임을 프롬프트에 명시한다. 또한 언어모델이 서버의 판정을 변경하거나 명령을 실제로 실행했다고 주장하지 못하도록 제한한다. 각 입력 항목과 전체 프롬프트에는 길이 상한을 설정하여 지나치게 긴 입력이 전달되지 않도록 하였다.

언어모델이 생성한 응답은 그대로 화면에 전달하지 않고 사전에 정의한 형식에 따라 검증한다. 화면 표시에 필요한 네 가지 항목만 허용하며, 정의되지 않은 항목이 응답에 포함되면 전체 응답을 거부한다. 형식에 맞지 않는 응답을 임의로 해석하면 본래의 의미가 왜곡된 상태로 학습자에게 전달될 수 있기 때문이다.

응답 검증에 실패하거나 언어모델 호출 자체가 실패한 경우에는 오류를 그대로 화면에 표시하지 않는다. 대신 생성형 AI 설명을 규칙 기반 안내로 대체하였음을 명시한 응답을 반환한다. 따라서 언어모델을 사용할 수 없는 상황에서도 문제 제시, 명령 처리, 채점 및 규칙 기반 힌트 기능은 계속 동작한다.

언어모델 호출의 재시도 여부는 발생한 오류의 종류를 분류한 후 결정한다. 다시 시도할 가치가 있는 오류에 대해서만 한 번 추가로 호출하며, 재시도해도 동일한 결과가 예상되는 오류는 즉시 중단한다.

언어모델 호출량은 사용자 단위로 제한하여 동시에 여러 요청을 보내거나 짧은 시간 동안 연속적으로 호출하는 것을 방지한다. 제한에 해당하는 요청에는 다시 요청할 수 있는 시점을 함께 안내한다.

언어모델 호출 기록에는 프롬프트 본문, 모델 응답 원문 및 학습자의 입력을 저장하지 않는다. 대신 프롬프트를 해시한 식별자와 응답 지연 시간, 시도 횟수 및 실패 사유만 기록한다.

학습 화면은 명령 실행 결과를 표시하는 터미널 영역과 언어모델의 응답을 표시하는 학습 도우미 영역으로 구분한다. 언어모델 응답 대신 대체 응답이 표시되는 경우에는 해당 내용이 규칙 기반 안내라는 점을 화면에 함께 표시한다.

## 4.7 학습자 맞춤형 피드백

학습 힌트는 개념, 명령 계열 및 구문의 세 단계로 구성한다. 학습자가 힌트를 요청할 때마다 한 단계씩 추가로 공개하며, 설정된 최대 단계를 초과하지 않는다. 이미 성공한 문제에는 힌트를 제공하지 않는다.

각 단계에서 제공하는 기본 힌트 문구는 외부 정의 파일에 고정되어 있다. 언어모델은 힌트의 내용을 직접 생성하지 않고, 서버에서 확정한 힌트 문구에 대한 부연 설명만 생성한다. 화면에서는 규칙 기반 힌트와 언어모델이 생성한 부연 설명을 구분하여 표시한다.

학습 이력은 세 가지 형태로 저장한다. 학습자가 명령을 입력할 때마다 명령 문자열, 결과 코드, 출력 결과 및 실행 전후의 상태를 기록한다. 채점과 힌트 제공 내역은 별도의 학습 상호작용 기록으로 저장하며, 학습자의 질문과 생성형 AI의 응답은 대화 기록으로 저장한다. 현재 문제에 대한 시도 횟수와 힌트 단계는 이러한 기록을 기반으로 계산하여 화면에 학습 진행 상황으로 표시한다.

다음 문제 선택은 결정적인 규칙에 따라 이루어진다. 채점 결과가 성공인 경우에만 다음 순서의 문제로 이동하며, 성공하지 못한 경우에는 현재 문제에 계속 머무른다. 문제 선택 과정에는 무작위 방식이나 언어모델의 판단이 개입하지 않는다.

전체 커리큘럼의 마지막 단계는 복습 라운드로 구성한다. 복습 라운드에서는 학습자가 이전에 완료한 문제 가운데 하나를 다시 제시한다. 복습 문제는 세션 식별자를 기준으로 선택하므로 동일한 세션에서는 반복해서 조회하더라도 같은 문제가 유지된다. 또한 복습 문제에는 원래 문제와 구분되는 별도의 식별자를 사용하여 복습 이력과 기존 학습 진도가 서로 섞이지 않도록 하였다.

동일한 문제에서 반복적으로 실패하는 학습자에게는 설명의 방식과 깊이를 조정한다. 이를 위해 질문이나 힌트 요청 시 해당 세션의 최근 채점 결과를 프롬프트에 포함한다. 해당 이력은 설명의 깊이와 어조를 조정하는 목적으로만 사용하며, 기존 판정 결과를 변경하는 데에는 사용하지 않도록 명시한다.

다만 학습자가 어떤 개념을 반복적으로 틀렸는지를 서버에서 직접 분류하는 기능은 구현하지 않았다. 서버는 문제별 판정 이력이라는 구조화된 사실만 제공하며, 해당 이력을 바탕으로 학습자가 부족한 부분을 파악하여 설명하는 과정은 언어모델이 수행한다.

## 4.8 구현 검증

구현된 기능이 설계한 방식대로 동작하는지 실제로 실행하여 확인한 결과는 다음과 같다.

첫째, 권한 판정이 서버에서 수행되는지를 확인하였다. 인증 의존성을 별도로 대체하지 않은 상태에서 전체 애플리케이션을 실행하고, 격리된 데이터베이스에 합성 계정을 생성하여 실제 토큰을 발급하였다. 이후 보안 계약에 정의된 21개 경로를 미인증 사용자, 일반 사용자, 관리자 및 비활성 사용자 조건으로 호출하였다. 로그인 응답이 계정 상태를 노출하지 않는지 확인하는 검사를 포함하여 총 86건의 검사가 모두 통과하였다.

둘째, 실제 서버 프로세스를 대상으로 모니터링 WebSocket의 동시 연결을 측정하였다. 50개의 연결이 모두 정상적으로 수립되었으며, 첫 번째 데이터를 수신하기까지 5.2초가 소요되었다. 동일한 실행 과정에서 티켓 응답의 캐시 금지, 티켓의 일회성 사용, 재사용 거부, 서로 다른 용도의 티켓 사용 거부 및 인증 이전에 데이터가 전송되지 않는 것도 확인하였다. 다만 해당 측정은 개발용 호스트에서 수행하였으므로 배포 대상 하드웨어의 성능 수치로 사용할 수는 없다.

셋째, 가상 상태 전이와 채점 기능이 같은 입력에 대해 항상 동일한 결과를 반환하는지 확인하였다. 이를 위해 규칙 엔진을 300회 반복 실행하였으며, 결정성은 1.0으로 측정되었다. 이 검증 과정에서는 언어모델을 사용하지 않고 규칙 엔진만 실행하였다.

넷째, 인증 정보가 로그에 남지 않는지를 확인하였다. 단순히 인증 정보와 유사한 문자열 패턴을 검색하는 방식이 아니라, 실제로 발급된 토큰과 티켓의 원문 문자열을 서버 로그 및 프록시 접근 로그와 직접 비교하였다. 그 결과 인증 정보가 로그에 노출되지 않았음을 확인하였다.

다섯째, 웹 터미널의 셸 격리 기능을 두 가지 방식으로 확인하였다. 파일 탐색 경로 검증에서는 실제 파일시스템에 심볼릭 링크를 생성한 후 허용된 범위 밖을 가리키는 링크와 순환 링크가 차단되는지를 확인하였다. 컨테이너 격리 검증에서는 실제 시스템과 동일한 실행 옵션으로 컨테이너를 생성한 후 외부 통신 차단, Docker 접근 차단, 시스템 영역 쓰기 거부, 임시 영역에서의 실행 금지, 커널 권한 제거 및 자원 상한 적용 여부를 직접 확인하였다.

한편 실제 브라우저 화면을 사람이 직접 조작하는 방식의 검사는 수행하지 않았으며, 성능 수치 역시 실제 배포 대상 하드웨어에서 측정하지 않았다. 또한 본 절에서 확인한 내용은 시스템이 설계한 방식대로 동작하는지에 관한 것으로, 언어모델 응답의 품질이나 실제 학습자를 대상으로 한 학습 효과는 평가하지 않았다.
