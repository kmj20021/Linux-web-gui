# 5. 적용 및 기대 효과

본 장에서는 4장까지 구현한 시스템을 학습에 적용했을 때 학습자가 거치는 과정을
정리하고, 실습 환경만 제공하는 방식과 비교했을 때 이 시스템의 구성이 어떻게
다른지를 설명한다. 이어서 활용할 수 있는 분야를 제시하고, 마지막으로 현재
시스템이 가진 한계를 밝힌다.

서술의 기준을 먼저 밝힌다. **본 연구는 실제 학습자를 대상으로 한 사용성 평가나
학습 효과 검증을 수행하지 않았다.** 따라서 이 장은 측정된 학습 효과를 보고하는
것이 아니라, 구현된 기능이 어떤 학습 경험을 가능하게 하는지를 구조적으로
설명하는 데 그친다. "향상되었다", "효과적이다"와 같은 표현 대신 "가능하다",
"의도했다"로 서술하며, 검증하지 않은 것은 5.4절에 한계로 명시한다.

## 5.1 학습자가 서버 상태를 이해하는 과정

### 5.1.1 실제 서버 자원의 간접 경험

Linux 서버 운영을 처음 배우는 학습자는 관리 권한을 가진 서버에 접근할 기회를
얻기 어렵다. 실습용 서버를 직접 구축하려면 설치와 네트워크 구성부터 익혀야 하고,
운영 중인 서버에 접근하는 것은 위험하다. 이 시스템은 학습자가 서버를 직접
구축하거나 소유하지 않아도 실제로 동작 중인 서버의 자원 상태를 관찰할 수 있는
경로를 제공한다.

학습자가 로그인 후 처음 보는 대시보드에는 실제 호스트에서 수집한 값이 표시된다.
CPU 항목에는 전체 사용률과 코어 수, 로드 평균이 표시되고, 메모리 항목에는
사용률과 사용 중·전체 용량, 여유 메모리가 표시된다. 프로세스 항목에는 CPU 사용률
상위 프로세스가 PID, 이름, CPU 사용률, 메모리 사용률의 네 개 열로 표시된다. <!-- 근거: frontend/src/pages/Dashboard.jsx:72-159 -->
이 값들은 5초 주기로 동작하는 백그라운드 수집기가 만든 스냅샷을 WebSocket으로
전달받아 갱신된다. <!-- 근거: backend/services/metrics_collector.py:22,53-66 -->

여기서 학습자가 관찰하는 것은 임의로 만들어 낸 예시 값이 아니라 실제 서버가
지금 사용하고 있는 자원이다. 값이 고정되어 있지 않고 시간에 따라 변한다는 점이
정지된 예시 화면과 다른 부분이며, 자원 사용량이 부하에 따라 어떻게 움직이는지를
관찰 대상으로 삼을 수 있다.

### 5.1.2 지표를 읽는 순서와 판단 기준

모니터링 화면은 학습자가 지표를 읽는 순서를 자연스럽게 따라가도록 구성했다.
현재 값을 먼저 보고, 시계열 그래프에서 추이를 확인하는 순서다.

| 확인 단계 | 제공 기능 | 학습자가 판단할 수 있는 것 |
|---|---|---|
| 지금 값 | 대시보드 카드, 5초 갱신 | 현재 자원 사용 수준 |
| 짧은 추이 | CPU 시계열 그래프 | 값의 변동 폭과 급격한 변화 여부 |

[표 5-1] 자원 지표 확인 단계별 제공 기능

시계열 그래프가 다루는 범위는 화면을 열어 둔 동안 수신한 값으로 한정된다. <!-- 근거: frontend/src/components/CPUChart.jsx:22,32 -->
더 긴 기간의 추이를 화면에서 확인하는 기능은 5.4.3절에서 한계로 다룬다.

메모리 지표는 수집 단계에서 버퍼와 캐시를 사용량에 합산하지 않고 별도 항목으로
유지한다. <!-- 근거: backend/routers/websocket.py:88-95 -->
Linux의 메모리 사용률을 처음 보는 학습자가 가장 자주 겪는 혼동이 캐시가 점유한
메모리를 부족한 상태로 오해하는 것인데, 수집 단계에서 두 값을 합산하면 이 구분을
이후 어디에서도 되살릴 수 없기 때문이다. 다만 현재 대시보드는 사용률과 사용
중·전체 용량, 여유 메모리만 표시하고 버퍼·캐시 항목은 화면에 렌더링하지 않는다. <!-- 근거: frontend/src/pages/Dashboard.jsx:101-128 -->
즉 구분이 가능한 데이터는 전달되지만 학습자가 화면에서 그 구분을 보지는 못하며,
이는 5.4.3절에서 한계로 다룬다.

또한 수집에 실패한 경우 빈 값이나 0을 반환하지 않고 실패한 자원을 명시한 오류로
응답하며, WebSocket 연결이 유지되고 있더라도 새 데이터가 도착하지 않으면 연결
상태 표시가 응답 없음으로 바뀐다. <!-- 근거: backend/routers/cpu.py:49-53, frontend/src/components/WebSocketStatus.jsx:50-61 -->
학습자가 화면에 남아 있는 마지막 값을 현재 상태로 오해하지 않도록 한 것이며,
"값이 0인 상태"와 "값을 알 수 없는 상태"를 구분하는 것 자체가 모니터링에서
익혀야 할 판단이다.

### 5.1.3 Linux 명령어 학습 경로

명령어 학습은 가상 Linux 실습을 통해 이루어진다. 학습자가 입력한 명령은 실제
시스템에서 실행되지 않고 세션에 저장된 가상 상태를 변경하는 입력으로만 쓰이며,
화면 상단에는 교육용 시뮬레이션이라는 고지가 항상 표시된다. <!-- 근거: frontend/src/pages/AITutor.jsx:167-172 -->

학습 시나리오는 서비스 장애 복구, 계정과 파일 권한 구성, 방화벽과 원격 접속
장애의 세 가지이며 각 시나리오에 두 개의 문제가 있다. <!-- 근거: backend/test/fixtures/ai_learning_scenarios.json scenarios -->
다루는 명령 계열은 서비스 관리, 계정 관리, 권한 관리, 방화벽, 상태 확인, 패키지
관리이다. <!-- 근거: fixture supported_commands -->

| 시나리오 | 문제 | 학습 대상 명령 계열 |
|---|---|---|
| Nginx 서비스 장애 복구 | 중지된 서비스 시작 / 재부팅 후 자동 시작 설정 | `systemctl` |
| 운영 계정과 파일 권한 구성 | 배포 사용자 생성 / 설정 파일 소유권·권한 제한 | `useradd`, `chown`, `chmod` |
| 방화벽과 원격 접속 장애 | 접속 차단 원인 진단 / 방화벽 규칙 복구 | `ufw`, `ss`, `systemctl` |

[표 5-2] 학습 시나리오와 대상 명령 계열

이 구성에서 학습자가 얻는 것은 명령어 문법의 암기가 아니라 **명령과 상태 변화의
대응 관계**다. 채점이 명령 문자열 일치가 아니라 최종 가상 상태를 기준으로 이루어지므로,
학습자는 정해진 한 줄을 맞히는 것이 아니라 목표 상태에 도달하는 여러 경로를
시도할 수 있다. <!-- 근거: backend/services/task_grader.py, fixture execution_policy.grading_principle = "final_state_first" -->

방화벽 시나리오는 이 구성이 왜 상태 기반이어야 하는지를 보여 준다. 가상 상태
엔진은 서비스 상태나 방화벽 규칙이 바뀔 때마다 원격 접속 가능 여부를 다시
계산하며, 이 값은 SSH 서비스가 실행 중이고 22번 포트가 허용되어 있을 때에만
참이 된다. <!-- 근거: backend/services/virtual_linux.py `_refresh_remote_access` -->
따라서 학습자가 방화벽 규칙만 열고 서비스를 실행하지 않으면 접속 가능 상태에
도달하지 못한다. 두 조건이 함께 충족되어야 한다는 사실을 설명으로 듣는 대신
상태 변화로 확인하게 된다.

실제 명령 실행 경험은 웹 터미널이 제공하지만, 웹 터미널 접속 티켓은 관리자
권한이 있어야 발급된다. <!-- 근거: backend/routers/auth.py:206-209 -->
반면 가상 Linux 학습 기능은 일반 사용자 권한으로 사용할 수 있다. <!-- 근거: backend/routers/ai_tutor.py:154,162,194,203,236,296,338,370,398,438 -->
즉 일반 학습자에게 열려 있는 명령어 학습 경로는 가상 실습이며, 실제 셸 실행은
운영자가 사용하는 별도 기능이다. 이는 실제 명령 실행이 시스템에서 가장 위험한
기능이라는 판단에 따른 것이며, 학습 범위를 제한하는 요인이기도 하므로 5.4절에서
다시 다룬다.

## 5.2 단순 실습 환경 제공과 AI 학습 제공의 차이

### 5.2.1 실습 환경만 제공할 때 남는 공백

가상 머신이나 컨테이너로 실습 환경만 제공하는 방식에서는 학습자가 막혔을 때
스스로 벗어나야 한다. 명령이 실패한 이유, 지금 상태가 목표와 무엇이 다른지,
다음에 무엇을 확인해야 하는지를 학습자가 판단해야 하고, 이 판단이 되지 않으면
실습이 중단된다. 초보 학습자에게 부족한 것이 바로 그 판단이므로, 환경만
주어져서는 학습이 이어지지 않는 구간이 생긴다.

일반적인 생성형 AI 도구에 질문하는 방식은 이 공백을 메우지만 다른 문제를
만든다. 대화 상대가 학습자의 현재 실습 상태를 모르기 때문에 학습자가 상황을
직접 설명해야 하고, 그 설명이 부정확하면 답도 어긋난다. 또한 모델이 성공
여부를 직접 판단하면 실제로는 목표에 도달하지 않았는데도 맞다고 말할 수 있다.

이 시스템은 두 방식 사이에서, 실습 환경과 설명 기능을 하나의 상태 위에서
연결하되 판정 권한은 설명 기능에 주지 않는 구성을 택했다.

### 5.2.2 학습 맥락을 공유하는 질의응답

학습자가 질문하면 서버는 먼저 현재 가상 상태를 규칙에 따라 채점해 판정을
확정한 뒤, 그 판정과 상태를 포함한 입력을 만들어 언어모델을 호출한다. <!-- 근거: backend/routers/ai_tutor.py:377-384 -->
언어모델에 전달되는 항목은 학습자 수준, 문제 정의, 현재 가상 상태, 서버가
확정한 판정 결과, 학습자의 입력, 최근 대화, 해당 세션의 최근 채점 이력이다. <!-- 근거: backend/services/bedrock.py:189-198 -->

그 결과 학습자는 자신이 처한 상황을 다시 설명하지 않아도 된다. "왜 안 되는지
모르겠다"고만 물어도 질문 시점의 가상 상태와 판정이 이미 입력에 포함되어 있다.
학습 중에 생긴 의문을 그 자리에서 자연어로 물을 수 있다는 점이 실습 환경만
제공하는 방식과의 첫 번째 차이다.

다만 명령을 성공적으로 처리한 결과에 대해서는 언어모델이 자동으로 논평하지 않는다.
학습자가 목표 상태에 도달했는지, 무엇이 부족한지에 대한 설명은 학습자가 질문하거나
힌트를 요청할 때만 생성된다. 학습자가 스스로 판단해 볼 기회를 남겨 두기 위한 것이며,
동시에 호출량을 학습자가 필요로 하는 시점으로 제한하는 효과도 있다.

예외는 시뮬레이터가 입력 자체를 처리하지 못한 경우다. 이때는 학습자가 요청하지 않아도
화면이 자동으로 설명을 요청해 참고용 설명을 도우미 패널에 덧붙인다. <!-- 근거: frontend/src/pages/AITutor.jsx:105-107 -->
이 경우에는 학습자가 스스로 판단할 근거 자체가 화면에 없기 때문이다. 명령이 처리된
경우와 달리 상태가 전혀 변하지 않아 무엇을 다시 시도해야 할지 알 수 있는 단서가 남지
않는다. 다만 이 설명 역시 확정된 상태나 판정을 바꾸지 않으며, 표시용이라는 사실이
화면 상단 고지에 함께 명시되어 있다. <!-- 근거: frontend/src/pages/AITutor.jsx:167-172 -->

### 5.2.3 시도 이력을 반영한 설명 조정

질문과 힌트 요청에는 해당 세션의 최근 채점 이력이 함께 전달된다. <!-- 근거: backend/services/bedrock.py:189-198 -->
같은 문제에서 반복해 실패한 학습자와 처음 시도하는 학습자에게 같은 깊이의
설명을 주면 한쪽에는 불충분하고 다른 쪽에는 과하므로, 설명의 깊이와 어조를
조정하는 근거로 사용한다. 이때 이력은 설명 조정에만 쓰이며 이미 확정된 판정을
바꾸는 데에는 쓰이지 않도록 프롬프트에 명시한다. <!-- 근거: backend/services/bedrock.py:199-211 -->

시도 횟수와 힌트 단계는 저장된 학습 상호작용 기록에서 계산해 화면에 진행 상황으로
표시한다. <!-- 근거: backend/routers/ai_tutor.py:75-102 -->
힌트는 개념, 명령 계열, 구문의 세 단계로 한 번에 한 단계씩만 공개된다. <!-- 근거: backend/services/curriculum.py:210-218 -->
학습자가 막혔을 때 답을 바로 보여 주는 대신 단계적으로 좁혀 가도록 한 것이다.

여기에는 분명한 경계가 있다. **학습자가 어떤 개념을 반복적으로 틀렸는지를
서버가 분류하는 기능은 구현하지 않았다.** 서버가 제공하는 것은 문제별 판정
이력이라는 구조화된 사실뿐이며, 그 이력에서 부족한 부분을 읽어 내는 해석은
언어모델이 수행한다. 따라서 이 부분의 품질은 서버가 보장하지 않는다.

### 5.2.4 판정과 설명을 분리한 구성의 차이

세 번째 차이는 역할 분리다. 성공·부분 성공·실패의 판정은 서버의 규칙 기반
채점기가 결정하고, 언어모델은 확정된 판정의 의미를 설명한다. 언어모델을
호출하는 지점은 질문, 힌트, 그리고 처리하지 못한 명령에 대한 설명 요청 세
곳이며, 명령 처리와 채점 자체는 호출하지 않는다. 세 지점 모두 규칙으로
확정된 사실이 만들어진 뒤에 호출된다는 순서는 같다. <!-- 근거: backend/routers/ai_tutor.py:356,381,413 -->

| 구분 | 실습 환경만 제공 | 일반 AI 대화 도구 | 본 시스템 |
|---|---|---|---|
| 실습 상태 | 학습자만 알고 있음 | 학습자가 설명해야 함 | 서버가 보관하고 입력으로 전달 |
| 성취 판정 | 없거나 명령 일치 | 모델이 판단 | 서버 규칙이 최종 상태로 판정 |
| 설명 제공 | 없음 | 있음 | 확정된 판정에 대해 제공 |
| 판정의 재현성 | — | 보장되지 않음 | 같은 입력에 같은 판정 |
| 모델 사용 불가 시 | — | 사용 불가 | 문제·명령·채점·규칙 힌트는 계속 동작 |

[표 5-3] 실습 환경 제공 방식과 본 시스템의 구성 비교

이 구성에서 얻는 것은 세 가지다. 첫째, 판정이 재현 가능하다. 규칙 엔진만
300회 반복 실행해 같은 입력에 같은 결과가 나오는 것을 확인했다. <!-- 근거: 4.8.3절, stage10 요약의 state_rule_benchmark -->
둘째, 언어모델의 응답이 형식 검증을 통과하지 못하거나 호출이 실패해도 규칙 기반
안내로 대체되어 학습이 중단되지 않는다. <!-- 근거: backend/services/bedrock.py:439-443 -->
셋째, 학습자가 프롬프트로 판정을 뒤집을 수 없다. 학습자의 입력은 지시가 아닌
데이터로 구분해 전달되고, 판정은 애초에 모델을 거치지 않고 결정되기 때문이다.

다만 [표 5-3]의 비교는 설계 구성의 차이를 정리한 것이며, 두 방식의 설명 품질을
실험으로 비교한 결과가 아니다. 본 연구는 그러한 비교 실험을 수행하지 않았다.

## 5.3 활용 가능성

### 5.3.1 Linux 서버 운영 입문 교육

첫 번째 활용 대상은 Linux 서버 운영을 처음 배우는 교육 과정이다. 실습 환경을
학습자 수만큼 준비하는 부담이 크고, 준비하더라도 초보 학습자가 서비스를 중지하거나
방화벽 규칙을 잘못 바꾸면 환경을 복구해야 한다.

이 시스템에서는 명령이 실제로 실행되지 않고 가상 상태만 바뀌므로 복구가 필요하지
않으며, 상태 초기화 요청 한 번으로 문제의 초기 상태로 되돌릴 수 있다. <!-- 근거: backend/routers/ai_tutor.py:203-234 -->
또한 학습자별 진도와 시도 이력이 세션에 기록되므로 교수자가 별도의 채점 도구를
쓰지 않아도 학습 진행 상황이 남는다. <!-- 근거: backend/core/models.py AI 관련 테이블 -->

다만 현재 문제 수는 세 시나리오에 여섯 문제이므로, 한 학기 분량의 교육 과정을
그대로 대체하기에는 부족하다. 학습 시나리오가 코드가 아닌 외부 정의 파일에
분리되어 있어 문제를 추가할 때 코드를 수정할 필요가 없다는 점이 확장의 전제가
된다. <!-- 근거: backend/test/fixtures/ai_learning_scenarios.json -->

### 5.3.2 클라우드 및 시스템 관리 학습

서비스 상태 확인, 계정과 권한 관리, 방화벽 규칙 구성은 클라우드 인스턴스를
다룰 때도 그대로 필요한 작업이다. 특히 방화벽 시나리오에서 다루는 "포트가
열려 있어도 서비스가 실행 중이지 않으면 접속되지 않는다"는 판단은 클라우드
환경에서 보안 그룹과 인스턴스 내부 설정을 함께 확인해야 하는 상황과 구조가
같다.

이 시스템 자체도 Amazon Bedrock을 사용하고 Docker Compose로 구성한 클라우드
기반 배포를 전제로 하므로, 시스템의 구성 자체를 학습 자료로 삼을 수 있다.

### 5.3.3 서버 모니터링 기초 학습과 개인 학습용 도구

세 번째는 모니터링 자체를 배우는 용도다. 자원 지표가 무엇을 의미하고 어떤
값이 정상 범위인지는 정지된 예시로는 익히기 어렵다. 이 시스템은 실제 값을
5초 간격으로 갱신해 보여 주므로, 고정된 예시 대신 부하에 따라 움직이는 값을
관찰 대상으로 삼을 수 있다. <!-- 근거: backend/services/metrics_collector.py:22, frontend/src/pages/Dashboard.jsx:34-43 -->

네 번째는 개인이 소유한 소규모 서버를 관리하는 용도다. 시스템 전체가 단일
호스트에서 Docker Compose로 기동되고 데이터베이스는 SQLite 파일 하나이므로
별도의 인프라 없이 설치할 수 있다. <!-- 근거: docker-compose.yml, backend/core/models.py -->
개인 서버의 자원 사용 추이를 웹 화면에서 확인하고, 필요할 때 계정을 추가해
공유할 수 있다. 다만 이 구성은 단일 인스턴스를 전제로 하므로 여러 대로 확장하는
용도에는 적합하지 않다(5.4.4절).

### 5.3.4 웹 개발과 생성형 AI 연동 교육 사례

마지막으로 이 시스템의 구현 자체를 교육 사례로 활용할 수 있다. 생성형 AI를
응용 프로그램에 연동할 때 실제로 결정해야 하는 문제들이 코드에 남아 있기
때문이다.

| 결정 사항 | 이 시스템의 처리 |
|---|---|
| 모델에 무엇을 입력할 것인가 | 구조화된 항목만 전달하고 실제 서버 자원은 제외 |
| 신뢰할 수 없는 입력의 취급 | 학습자 입력·대화를 별도 영역에 두고 데이터로 처리 |
| 응답을 어디까지 믿을 것인가 | 정해진 네 항목만 허용하고 그 외 항목이 있으면 응답 전체를 거부 |
| 모델이 실패했을 때 | 규칙 기반 안내로 대체하고 대체되었음을 화면에 표시 |
| 판정 권한 | 모델이 아닌 서버 규칙이 보유 |
| 호출량 | 사용자 단위 동시 요청·간격 제한 |

특히 응답 검증을 정의된 항목만 허용하는 방식으로 구성한 점, 그리고 호출 기록에

## 5.4 시스템의 한계

이 절은 현재 시스템이 하지 못하는 것과 검증하지 않은 것을 밝힌다. 여기 적은
항목은 6장의 향후 개선 방향과 대응한다.

### 5.4.1 학습자를 대상으로 평가하지 않았다

가장 큰 한계다. 실제 학습자를 대상으로 한 사용성 평가와 학습 효과 검증을
수행하지 않았다. 4.8절에서 확인한 것은 구현이 설계대로 동작하는지에 관한
것이며, 학습자가 이 시스템으로 더 잘 배우는지는 측정하지 않았다.

생성형 AI가 생성한 설명의 정확성도 평가하지 않았다. 응답 검증은 형식이
정해진 항목을 지키는지만 확인하며, 설명 내용이 사실인지는 검사하지 않는다. <!-- 근거: backend/services/bedrock.py:58-66,257-277 -->
힌트가 학습 단계에 적합한지에 대한 전문가 평가도 수행하지 않았다.

따라서 본 논문은 학습 효과나 응답 품질에 관한 어떠한 주장도 하지 않는다.
이 시스템은 그러한 평가를 수행할 수 있는 대상으로서 설계·구현된 단계에 있다.

### 5.4.2 생성형 AI를 완전히 통제한다고 볼 수 없다

이 시스템은 언어모델의 영향 범위를 제한하기 위해 여러 장치를 두었다. 판정
권한을 주지 않고, 호출 지점을 정해진 세 곳으로 한정하고, 학습자 입력을 데이터로
구분하고, 응답을 정의된 항목만 허용하도록 검증하고, 실패 시 규칙 기반 안내로
대체한다.

그러나 이 장치들이 보장하는 것은 **영향 범위**이지 **내용의 정확성**이 아니다.
형식 검증을 통과한 응답 안에 잘못된 설명이 들어 있으면 그대로 학습자에게
전달된다. 판정 자체는 규칙 엔진이 결정하므로 성공·실패가 뒤바뀌지는 않지만,
개념 설명의 오류는 현재 구조로 걸러지지 않는다.

이 한계는 개발 과정에서 실제로 관찰되었다. 처리하지 못한 명령을 설명하는
기능에서, 서버가 거부 사유를 명령 이름 때문인지 인자 때문인지 알려주지 않자
모델이 시뮬레이터가 지원하는 명령을 두고 존재하지 않는 명령이라고 설명한
사례가 있었다. 프롬프트에 해당 단정을 금지하는 지시를 추가해 대응했으나,
이는 확률적 완화이지 결정적 보장이 아니다. **서버가 알려주지 않은 사실을
모델이 스스로 메우려 할 때 그럴듯한 오답이 생긴다**는 점은 구조로 막을 수 있는
범위 밖에 있다. <!-- 근거: backend/services/bedrock.py:96-107, docs/re-progress.md AI-NARRATE-01 -->

프롬프트를 통한 우회 시도 역시 완전히 차단된다고 단정할 수 없다. 학습자 입력을
지시가 아닌 데이터로 취급하도록 명시했으나, 이는 모델이 그 지시를 따른다는
전제 위에 있다. 판정 경로가 애초에 모델을 거치지 않는다는 점이 실질적인 방어선이며,
설명 내용에 대해서는 같은 수준의 보장을 제공하지 못한다.

### 5.4.3 다룰 수 있는 학습 범위와 장애 유형이 제한된다

가상 상태 엔진이 표현하는 것은 서비스 실행 여부와 자동 시작 설정, 사용자와
비밀번호, 파일 소유권과 권한, 방화벽 규칙, 패키지 설치 상태, 그리고 이로부터
계산되는 원격 접속 가능 여부다. <!-- 근거: backend/services/virtual_linux.py -->
파일 시스템의 실제 내용, 프로세스 동작, 로그, 성능 저하, 자원 고갈처럼 상태
항목으로 표현되지 않는 대상은 다루지 않는다.

명령도 마찬가지다. 허용 목록에 정의된 명령과 인자 형태만 처리하며, 명령 연결과
파이프, 리다이렉션 같은 셸 문법은 거부한다. <!-- 근거: backend/services/command_parser.py -->
이는 안전성을 위한 의도된 제약이지만, 실제 서버 운영에서 흔히 쓰는 조합 명령을
연습할 수 없다는 뜻이기도 하다. 실제 셸 실행 경험은 웹 터미널이 제공하나 관리자
권한을 요구하므로 일반 학습자에게는 열려 있지 않다. <!-- 근거: backend/routers/auth.py:206-209 -->

따라서 **복잡한 서버 장애의 원인을 진단하는 학습은 이 시스템의 범위를 벗어난다.**
현재 시나리오가 다루는 것은 원인과 결과가 상태 항목으로 명확히 연결되는 유형의
문제다. 여러 요인이 얽힌 실제 장애는 이 방식으로 표현하기 어렵다.

한 가지 더 밝힐 것이 있다. **모니터링 지표에 대한 자연어 해설은 구현하지 않았다.**
생성형 AI의 설명 대상은 가상 실습 상태와 채점 결과로 한정되며, 모니터링 화면은
AI 기능과 연결되어 있지 않다. <!-- 근거: frontend/src/pages/Dashboard.jsx:1-4 (AI API 미사용), backend/routers/ai_tutor.py:382,414 -->
즉 학습자가 대시보드에서 특정 지표의 의미를 묻는 것은 현재 불가능하며, 지표의
해석은 학습자가 스스로 하거나 별도 자료에 의존해야 한다. 이는 2.1절에서 학습용
모니터링 시스템에 필요하다고 정리한 요구이므로, 6장의 개선 방향에 포함한다.

같은 맥락의 미완성 부분이 하나 더 있다. 5.1.2절에서 밝혔듯 버퍼와 캐시는 수집
단계에서 사용량과 분리되어 전달되지만 대시보드가 이를 표시하지 않으므로, 학습자가
가장 혼동하기 쉬운 구분이 화면에는 드러나지 않는다. <!-- 근거: backend/routers/websocket.py:88-95, frontend/src/pages/Dashboard.jsx:101-128 -->
데이터가 이미 전달되고 있어 표시 항목을 추가하는 것으로 해소할 수 있는 범위이나,
현재 구현에는 반영되어 있지 않다.

이력 조회도 같은 상태다. 스케줄러가 1분 간격으로 저장한 스냅샷을 기간별 집계와
원본 조회, 백분위수 통계의 세 경로로 조회할 수 있으나 이를 호출하는 화면은
구현하지 않았다. <!-- 근거: backend/routers/history.py:31,143,175, frontend/src/api/client.js:170-186 -->
따라서 학습자가 화면에서 볼 수 있는 추이는 화면을 열어 둔 동안 수신한 값으로
한정되며, 저장된 이력은 API로만 접근할 수 있다. 자원 사용의 반복되는 패턴이나
평상시 수준과 예외적 구간의 구분처럼 긴 기간을 놓고 판단해야 하는 학습은 현재
화면으로는 수행할 수 없다.

### 5.4.4 운영 환경 적용 시의 제약

이 시스템은 단일 인스턴스 학습용으로 설계했으며, 그 전제에서 나오는 제약이
남아 있다.

| 제약 | 내용 |
|---|---|
| 로그아웃 시 토큰 무효화 부재 | 서버 측 무효화 목록이 없어 유출된 토큰은 만료까지 유효하다 |
| 단일 프로세스 가정 | 셸 세션 한도, 마지막 관리자 보호, 티켓 저장소가 프로세스 메모리 기준이라 다중 인스턴스에서 보장되지 않는다 |
| 관측 가능성 부재 | 구조화 로그·메트릭·추적이 없어 운영 중 이상을 사후에 추적하기 어렵다 |
| 대상 하드웨어 미측정 | 동시 접속 측정이 개발 호스트 기준이며 배포 대상 성능 수치가 아니다 |
| 브라우저 수준 검사 미수행 | 실제 브라우저 조작이 필요한 검사 항목이 남아 있다 |

[표 5-5] 운영 적용 시 남은 제약 <!-- 근거: docs/re-evaluation.md §5, docs/re-progress.md Known Limitations -->

배포 환경에도 제약이 있다. 코드에는 운영 프로필에서 TLS 인증서가 없으면 기동을
중단하는 fail-closed 설계가 들어 있으나, 실제 배포 대상 인스턴스는 고정 IP만
할당받아 도메인 인증서를 발급할 수 없어 이 경로를 사용하지 못했다. <!-- 근거: docs/operations.md, frontend/start.sh -->
그 결과 실제 배포는 개발 프로필로 이루어졌고 통신이 암호화되지 않는다. 이는
구현의 결함이 아니라 배포 환경의 제약이지만, 현재 상태를 그대로 공개 서비스로
운영해서는 안 되는 이유다.

마지막으로, 앞의 제약들이 공통으로 가리키는 결론을 밝힌다. **실제 운영 환경에서
이 시스템의 AI 응답만을 근거로 조치를 수행해서는 안 된다.** 이 시스템의 설명
대상은 가상 실습 상태이지 운영 중인 실제 서버가 아니며, 설명 내용의 정확성도
검증되지 않았다. 이 시스템의 위치는 학습 지원이며, 운영 판단의 근거가 아니다.
