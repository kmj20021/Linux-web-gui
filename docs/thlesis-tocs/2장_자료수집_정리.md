## 2.1 Linux 서버 모니터링 시스템

### 논문에 담을 핵심 논지
- 서버 모니터링의 정의: 시스템 자원(CPU, 메모리, 디스크, 네트워크)과 프로세스 활동을 실시간 또는 시계열로 추적하여 병목·이상·장애 징후를 조기에 파악하는 활동.
- 각 자원의 의미:
  - **CPU**: 사용률, 코어별 부하, load average(1/5/15분 평균) — 물리 CPU가 과다/과소 활용되는지 판단하는 지표.
  - **메모리**: 전체/사용/여유 용량, swap, 그리고 **buffers/cached** — 초보자가 캐시 점유를 "메모리 부족"으로 오해하는 문제(3.2.1절 설계 근거와 직결). Linux는 여유 메모리를 페이지 캐시로 적극 활용하며, 이 영역은 필요 시 즉시 회수 가능함.
  - **디스크**: 파티션별 용량·사용률, I/O 읽기/쓰기 속도, 지연.
  - **네트워크**: 대역폭(수신/송신), 지연·패킷 손실, 열린 포트와 연결 상태.
- 모니터링의 필요성: 성능 병목의 조기 발견, 보안 이상 징후 탐지, 자원 관리 효율화, 다운타임 예방, 감사·규정 준수.

## 2.2 웹 기반 시스템 관리 도구

### 논문에 담을 핵심 논지
- 웹 기반 관리 인터페이스의 장점: OS 무관 접근성(브라우저만 필요), 원격 관리, 시각화(그래프·대시보드), 다중 사용자 동시 접근.
- 기존 도구의 주요 기능:
  - **Prometheus + Grafana**: 풀(pull) 기반 지표 수집 + 시계열 DB + 대시보드 시각화. 클라우드 네이티브 환경의 사실상 표준. 단, scrape 설정·PromQL·대시보드 구성 등 초기 설정 부담이 큼.
  - **Netdata**: 노드별 에이전트가 초 단위 지표를 수집, 설치 즉시 대시보드 제공.
  - **Zabbix / Nagios**: 전통적 엔터프라이즈 모니터링(가용성 점검·알림 중심).
  - **Cockpit**: Red Hat의 웹 기반 단일 호스트 관리 도구(가벼운 모니터링 포함).
- 초보 학습자 관점의 한계(본 논문의 문제의식):
  1) 수치·그래프를 **보여줄 뿐 의미를 설명하지 않음** — 학습자는 "CPU 90%"가 왜 문제인지 알 수 없음.
  2) 운영 전문가를 전제한 설정 복잡도(예: Prometheus 스택 구축).
  3) 학습 기능(과제·채점·피드백)의 부재.

## 2.3 시뮬레이션 기반 실습 환경

### 논문에 담을 핵심 논지
- **실제 서버 실습의 위험**: 초보자의 잘못된 명령(서비스 중지, 방화벽 오설정, rm 오용)이 시스템을 복구 불가능하게 만들 수 있고, 공유 서버에서는 다른 사용자에게 피해가 전파됨.
- **격리 방식 3종 비교** (3.6.1절 설계 근거와 직결):
  1) **가상머신**: OS 전체를 격리 → 가장 강한 격리, 그러나 학습자당 GB 단위 자원·긴 부팅 시간·높은 비용.
  2) **컨테이너**: 호스트 커널 공유 → 경량(MB 단위)·초 단위 기동·높은 밀도, 격리 강도는 VM보다 약함(커널 공유로 인한 탈출 위험).
  3) **상태 시뮬레이션**: 명령을 실행하지 않고 구조화된 가상 상태만 전이 → 학습자당 비용이 데이터 1건 수준, 위험 명령도 안전하게 학습 소재화 가능. 단, 실제 실행 경험은 제공하지 못함(→ 본 시스템은 샌드박스 터미널로 보완, 3.7.3절).
- **실행 방식 vs 상태 전이 방식**: KillerCoda·OverTheWire처럼 실제 격리 환경에서 명령을 실행하는 플랫폼과, 상태만 전이시키는 시뮬레이터의 차이.
- **성취 판정 기준**: 명령 문자열 일치 판정은 정답 암기를 유도하고 동일 목표의 다른 경로를 오답 처리함. 시스템 관리 과제 평가 연구는 "OS 전체(최종 상태)를 확인해야 한다"는 방향으로 발전해 왔음.

## 2.4 생성형 AI와 학습 지원 시스템

### 논문에 담을 핵심 논지
- 생성형 AI의 교육적 기능: 개념 설명, 오류 진단, 맞춤형 피드백, 즉시 질의응답, 학습자 수준별 설명 조정(스캐폴딩).
- 프로그래밍·IT 교육에서의 효과: 초보자의 개념 이해·디버깅 지원에 유효하다는 다수 보고. 단, 과의존과 자기주도 문제해결력 저하 우려도 함께 보고됨 → 단계별 힌트 설계(3.6.4절)의 근거.
- **정확성 검증의 필요성(본 논문의 핵심 논거)**:
  - LLM은 환각(hallucination)으로 잘못된 정보를 생성할 수 있고, 학습자에게 전달되기 전 검증이 필요함.
  - GPT-4 기반 튜터 피드백 연구에서 힌트의 35%가 지나치게 일반적이거나, 부정확하거나, 정답을 노출.
  - 환각이 포함된 피드백은 학습자를 오도하거나 낙담시킬 수 있음(L@S 2025 실증).
  - **해결 방향**: ITS가 확정한 구조화 정보(기대 답·풀이 단계)를 프롬프트에 포함하면 모델이 답을 "예측"할 필요가 없어져 오류 위험이 감소 — 이것이 곧 3.5.2절 "판정은 서버가, 설명은 모델이" 설계의 학술적 근거.

## 2.5 Amazon Bedrock

### 논문에 담을 핵심 논지
- **기본 구조**: 여러 AI 기업의 파운데이션 모델을 단일 API로 제공하는 완전 관리형(fully managed) 서비스. 모델 호스팅·확장을 AWS가 담당하고, 접근 제어는 IAM 권한 체계로 관리.
- **호출 방식**: 모델별 고유 형식의 `InvokeModel`과, 모든 대화형 모델에 일관된 인터페이스를 제공하는 **Converse API**(2024.5 출시). Converse는 모델별 파라미터 차이를 흡수해 "코드를 한 번 작성하고 여러 모델에 사용"할 수 있게 함 → 3.5.1절 "통합 대화 API로 모델 교체 시 변경 범위 축소" 설계의 직접 근거.
- **데이터 처리**: Bedrock은 사용자가 제공한 텍스트·이미지·문서를 저장하지 않고 응답 생성에만 사용(공식 API 문서 명시) — 학습 시스템의 프라이버시 서술에 활용 가능.
- **선택 이유(논문 관점)**: 모델 자체 운영 불필요, 자격 증명·권한을 클라우드 권한 체계(IAM)로 일원화, 통합 API로 모델 종속성 완화.

## 2.6 기존 연구와의 차별성

### 논문에 담을 논지별 대비 구도

| 차별점 | 기존 연구·도구의 상태 | 근거 자료(위 절 번호) |
|---|---|---|
| ① 기존 시스템은 상태 **시각화**에 집중 | Prometheus/Grafana/Netdata 등은 지표 수집·대시보드가 목적이며 지표의 의미 설명·학습 기능 없음 | 2.2-①②④ |
| ② 상태 **설명 + 학습 지원 결합** | LLM 피드백 연구(2.4-①②)는 존재하나 서버 모니터링 도구와 결합한 사례는 드묾. ITS grounding 원리를 서버 관리 도메인에 적용 | 2.4-①③ |
| ③ **초보자 중심 설명** | 기존 도구는 운영 전문가 전제(설정 복잡도, 전문 용어 대시보드) | 2.2-④⑤ |
| ④ **실행 없는 가상 상태 전이 실습** | Linux Luminarium·KillerCoda·OverTheWire는 실제(격리) 환경에서 명령을 **실행**하는 방식. 상태 전이만으로 실습을 구성해 위험 명령까지 소재화하는 접근은 차별점 | 2.3-①⑧⑨ |
| ⑤ **최종 상태 기준 채점** | 시스템 관리 과제 자동 채점 연구는 "OS 전체 상태 검사" 방향(라이브 VM 채점, LINSIM)으로 발전. 본 연구는 이를 가상 상태에 적용하고 명령 문자열 일치 판정을 지양 | 2.3-⑦, 2.3-① |

**집필 메모**: 차별성 절은 "기존 연구가 못했다"가 아니라 "기존 연구의 A축(시각화)·B축(실행형 실습)·C축(LLM 피드백)이 각각 발전해 왔고, 본 연구는 이를 초보 학습자용으로 **한 시스템에 통합하되 판정과 설명의 역할을 분리**했다"는 통합·재구성 프레임으로 쓰는 것이 심사에 유리하다.
