# 4. 시스템 구현

본 장에서는 3장에서 기술한 설계를 실제로 구현한 결과를 기능 단위로 기술한다. 각 절은
사용자가 화면에서 수행하는 동작이 어떤 API를 거쳐 어떤 처리로 이어지는지를 호출 흐름
중심으로 서술하고, 마지막 절에서 구현이 설계 의도대로 동작하는지 실행으로 확인한
결과를 정리한다.

서술의 기준은 두 가지다. 첫째, 여기 적은 동작은 모두 구현된 코드의 동작이며 계획이나
예정은 포함하지 않는다. 둘째, 실행해 확인하지 않은 것은 확인했다고 적지 않으며,
확인 범위와 그 한계를 4.8절에 함께 적는다.

서술 대상은 서버와 연동되는 기능으로 한정한다. 파일 조작 명령을 연습하는 화면과 네트워크
진단 명령의 출력 형태를 보여 주는 화면은 서버 API를 호출하지 않고 브라우저 안에서 결과를
만들어 내는 보조 학습 화면이므로 본 장에서 다루지 않는다. <!-- 근거: frontend/src/App.jsx:95-104,145-154, frontend/src/features/filesystem/filesystemModel.js:1-5, frontend/src/features/network-diagnostics/simulators.js:1-4 -->
4.4절의 가상 파일 탐색기는 이 화면들과 달리 실제 셸 세션의 홈 디렉터리를 읽는 기능이다.

## 4.1 사용자 인증 및 권한 관리

### 4.1.1 회원가입과 로그인

회원가입은 `POST /api/auth/register`로 처리한다. 사용자명은 영문자·숫자·밑줄 3~20자
로 제한하고 비밀번호는 8자 이상이며 확인 입력과 일치해야 한다. 세 조건은 요청 스키마
단계에서 검증하므로 라우터 본문에 도달하기 전에 거부된다. <!-- 근거: backend/routers/auth.py:32,74-94 -->
생성된 계정의 역할은 항상 `viewer`이고 활성 상태로 시작한다. 가입 API로는 관리자
계정을 만들 수 없으며, 관리자 계정은 4.1.3절의 관리 API로만 생성된다. <!-- 근거: backend/routers/auth.py:243-248 -->
비밀번호는 bcrypt 해시로만 저장하고 평문은 어디에도 남기지 않는다. <!-- 근거: backend/core/security.py:93-98 -->

로그인은 `POST /api/auth/login`이 처리한다. 처리 순서는 사용자 조회, 비밀번호 해시
검증, 활성 상태 확인이며, 세 경우 모두 같은 401 응답과 같은 문구를 반환한다.
비활성 계정에만 다른 응답을 주면 올바른 비밀번호를 가진 요청자가 그 사실만으로
자격 증명이 유효함을 확인할 수 있기 때문이다. <!-- 근거: backend/routers/auth.py:121-134 -->

인증에 성공하면 사용자명과 역할, 만료 시각을 담은 JWT를 발급한다. 기본 만료 시간은
15분이며 환경변수로 조정할 수 있다. <!-- 근거: backend/core/security.py:36, backend/routers/auth.py:136-140 -->
서명 키는 환경변수로만 주입하고, 값이 없거나 널리 알려진 예시 문자열이면 토큰을
만들지 않고 예외를 발생시킨다. <!-- 근거: backend/core/security.py:65-87 -->
로그인이 성공한 경우에 한해 사용자명·역할·접속 IP를 로그인 이력 테이블에 기록한다. <!-- 근거: backend/routers/auth.py:142-153 -->

로그아웃(`POST /api/auth/logout`)은 서버 상태를 바꾸지 않고 200만 반환하며, 토큰
삭제는 클라이언트가 수행한다. 서버 측 토큰 무효화 목록은 구현하지 않았고, 이는
4.8절과 6장에서 한계로 다룬다. <!-- 근거: backend/routers/auth.py:163-170 -->

### 4.1.2 요청마다 다시 확인하는 권한

보호된 REST 경로는 공통 의존성 `get_current_user`를 거친다. 이 함수는 토큰 서명과
만료를 검증한 뒤 **데이터베이스에서 사용자를 다시 조회해** 존재 여부와 활성 상태를
확인한다. 따라서 토큰 발급 이후 계정이 비활성화되면 토큰이 만료되기 전이라도 즉시
차단된다. <!-- 근거: backend/core/security.py:171-206 -->

관리자 전용 경로는 `get_current_admin`을 추가로 거치며, 역할 판정에 토큰의 `role`
클레임이 아니라 방금 조회한 데이터베이스의 현재 역할을 사용한다. 역할이 관리자가
아니면 403을 반환한다. <!-- 근거: backend/core/security.py:209-222 -->

응답 코드는 원인에 따라 구분한다. 인증 정보가 없거나 유효하지 않거나 계정이
비활성인 경우는 401, 인증은 되었으나 역할이 부족한 경우는 403이다. 특히 비활성
계정을 403이 아닌 401로 처리하는데, 프론트엔드의 공통 통신 계층이 401에서만 세션을
정리하기 때문이다. 403으로 응답하면 비활성화된 사용자의 화면이 토큰 만료 시점까지
남는다. <!-- 근거: backend/core/security.py:197-205 -->

프론트엔드에도 보호된 경로와 역할별 메뉴 노출이 있으나 이는 표시 목적이며, 실제
허용 여부는 위 두 의존성이 서버에서 판정한다. 이 분리가 실제로 성립하는지는 4.8.1절의
권한 행렬 검증으로 확인했다.

### 4.1.3 사용자 관리와 감사 로그 조회

관리자 기능은 `/api/admin` 아래에 있으며 모든 경로가 `get_current_admin`을 요구한다. <!-- 근거: backend/routers/admin.py:124-282 -->

| 경로 | 기능 | 추가 규칙 |
|---|---|---|
| `GET /api/admin/users` | 계정 목록 조회 | ID 오름차순 |
| `POST /api/admin/users` | 계정 생성 | 역할 지정 가능, 생성자 기록 |
| `PATCH /api/admin/users/{id}` | 역할·활성 상태 변경 | 자기 자신 불가, 마지막 관리자 보호 |
| `DELETE /api/admin/users/{id}` | 계정 삭제 | 자기 자신 불가, 마지막 관리자 보호 |
| `GET /api/admin/audit` | 로그인 이력 조회 | 최신순, 페이지당 1~500건 |

**[표 4-1] 관리자 API 구성**

계정 변경·삭제에는 두 가지 보호 규칙을 두었다. 첫째, 관리자는 자기 자신의 역할이나
활성 상태를 바꾸거나 자신을 삭제할 수 없다. 둘째, 활성 관리자가 한 명뿐일 때 그
계정을 일반 사용자로 강등하거나 비활성화하거나 삭제하는 요청은 거부한다. 두 번째
규칙은 조회와 변경 사이에 다른 요청이 끼어드는 것을 막기 위해 역할·활성 상태 변경과
계정 삭제 요청을 프로세스 단위 잠금으로 직렬화한 뒤 검사한다. <!-- 근거: backend/routers/admin.py:31,194-223,239-258 -->
관리자가 한 명도 남지 않아 시스템을 운영할 수 없게 되는 상태를 구조적으로 막기 위한
처리다.

로그인 이력 조회는 4.1.1절에서 기록한 로그인 성공 이벤트를 최신순으로 페이지 단위로
반환한다. 조회 항목은 사용자명, 역할, 접속 IP, 기록 시각이다. <!-- 근거: backend/routers/admin.py:80-86,266-282 -->

## 4.2 실시간 서버 자원 모니터링

### 4.2.1 단일 수집기와 5초 주기 공유

실시간 모니터링은 하나의 백그라운드 수집기를 중심으로 동작한다. 수집기는 애플리케이션
시작 시점에 기동되어 5초 간격으로 스냅샷 하나를 만들고, 새 스냅샷이 준비되면 대기 중인
모든 소비자를 한꺼번에 깨운다. <!-- 근거: backend/services/metrics_collector.py:22,53-89, backend/main.py:154-155 -->
WebSocket 연결은 스스로 수집하지 않고 이 공유 스냅샷을 기다렸다가 그대로 전송하므로,
연결 수가 늘어도 수집 횟수는 늘지 않는다. <!-- 근거: backend/routers/websocket.py:190,205-216 -->

수집 함수는 CPU 사용률 측정처럼 일정 시간 블로킹되는 호출을 포함하므로 별도 스레드로
옮겨 실행하고, 이벤트 루프는 그동안 다른 연결을 처리한다. <!-- 근거: backend/routers/websocket.py:59-65 -->
수집 중 예외가 발생하면 예외를 기록한 뒤 0으로 채운 기본 스냅샷을 반환하고, 주기 루프는
한 번의 실패로 종료되지 않고 다음 주기를 계속한다. <!-- 근거: backend/routers/websocket.py:125-137, backend/services/metrics_collector.py:84-89 -->

스냅샷 한 건에 담기는 항목은 [표 4-2]와 같다.

| 구분 | 항목 |
|---|---|
| CPU | 전체 사용률, 코어별 사용률, 물리 코어 수, 부하 평균 |
| 메모리 | 전체·사용·여유 용량, buffers, cached, 사용률 |
| 프로세스 | CPU 사용률 상위 30개(PID, 이름, CPU %, 메모리 %) |

**[표 4-2] 실시간 스냅샷 구성** <!-- 근거: backend/routers/websocket.py:74-124 -->

메모리는 buffers와 cached를 합산하지 않고 별도 항목으로 유지한다. 캐시가 점유한
메모리를 부족 상태로 오해하기 쉬운데, 수집 단계에서 합쳐 버리면 이후 어떤 계층에서도
둘을 구분할 수 없기 때문이다. 바이트 단위 값은 이 단계에서 기가바이트로 환산해
소수점 둘째 자리까지 정리한다. <!-- 근거: backend/routers/websocket.py:88-96 -->

### 4.2.2 WebSocket 연결과 인증

브라우저는 실시간 데이터를 받기 전에 먼저 `POST /api/auth/ws-tickets/monitor`로
일회용 티켓을 발급받는다. 응답에는 캐시 금지 헤더가 붙고 유효 시간은 60초다. <!-- 근거: backend/routers/auth.py:185-203, backend/core/security.py:37,42-48 -->
이어 접속 주소에 아무 인증 정보도 넣지 않은 채 `/ws/monitor`에 연결하고, 연결이
열리면 첫 메시지로만 티켓을 보낸다. <!-- 근거: frontend/src/api/client.js:204-206,231-237 -->

서버 측 처리 순서는 다음과 같다.

```
  1) 접속 주소에 token·ticket 질의 항목이 있으면 → 즉시 종료(4001)
  2) 연결 수락 후 5초 안에 {"type":"authenticate","ticket":…} 수신
  3) 티켓을 원자적으로 1회 소비 (용도가 monitor 인지 확인)
  4) 사용자명을 DB에서 재조회해 활성 상태 확인
  5) 위 단계를 모두 통과한 뒤에야 스냅샷 전송 시작
```

**[그림 4-1] 모니터링 WebSocket 인증 처리** <!-- 근거: backend/routers/websocket.py:34-57,163-186 -->

티켓은 조회와 동시에 저장소에서 제거되므로 재사용할 수 없고, 용도가 다르면(예:
모니터링 티켓으로 터미널 접속) 거부된다. <!-- 근거: backend/core/security.py:51-62 -->
인증이 끝나기 전에는 어떤 데이터도 전송하지 않는다.

### 4.2.3 시점 조회용 REST API

특정 시점의 값이나 조회 조건이 필요한 정보는 REST로 제공한다. 모든 경로는 로그인
사용자를 요구한다.

| 경로 | 반환 내용 |
|---|---|
| `GET /api/monitor/cpu` | 전체·코어별 사용률, 물리 코어 수, 부하 평균 |
| `GET /api/monitor/memory` | 전체·사용·여유·buffers·cached·사용률 |
| `GET /api/monitor/disks` | 파티션별 용량과 사용률 |
| `GET /api/monitor/disk?path=` | 지정 경로의 용량과 사용률 |
| `GET /api/monitor/processes` | CPU 상위 30개 프로세스 |

**[표 4-3] 자원 조회 REST API** <!-- 근거: backend/routers/cpu.py:24-56, backend/routers/memory.py:24-56, backend/routers/disk.py:24-93, backend/routers/process.py:28-66 -->

수집에 실패한 경우 빈 목록이나 0을 반환하지 않고 503과 함께 실패한 자원 이름을
구조화해 반환한다. 실제로 사용률이 0인 상태와 수집이 실패한 상태를 화면에서 구분할 수
있어야 하기 때문이다. <!-- 근거: backend/routers/cpu.py:48-55, backend/routers/network.py:13-19 -->
다만 디스크 목록에서 개별 파티션 접근이 거부된 경우는 그 파티션만 건너뛰고 나머지
결과를 유지한다. <!-- 근거: backend/routers/disk.py:47-50 -->
운영체제에 따라 존재하지 않는 항목(예: 일부 플랫폼의 buffers·cached, 부하 평균)은
부재를 명시적으로 0으로 처리해 수집 실패로 오인하지 않도록 했다. <!-- 근거: backend/routers/memory.py:39-41, backend/routers/cpu.py:35-37 -->

### 4.2.4 네트워크 조회

네트워크 기능은 네 개의 경로로 나뉜다. 인터페이스 조회는 이름, 상태, IPv4 주소, MAC
주소, MTU를 반환한다. 트래픽 조회는 누적 송수신 바이트와 함께 **직전 호출 대비
초당 전송량**을 계산해 KB/s 단위로 반환하며, 이전 측정값이 없는 첫 호출에서는 0을
반환하고 카운터가 초기화되어 음수 차이가 나오면 0으로 처리한다. 직전 값 캐시는 동시
요청에서 어긋나지 않도록 잠금으로 보호한다. <!-- 근거: backend/routers/network.py:109-159 -->
패킷 조회는 인터페이스별 송수신 패킷 수와 오류·드롭 수를 반환한다. <!-- 근거: backend/routers/network.py:162-184 -->

연결 상태 조회는 프로토콜, 로컬·원격 주소와 포트, 연결 상태, PID, 프로세스 이름을
로컬 포트 오름차순으로 반환한다. 이 경로만은 다른 세 경로와 달리 관리자 권한을
요구하는데, 연결 목록이 어떤 프로세스가 어디에 접속해 있는지를 드러내기 때문이다. <!-- 근거: backend/routers/network.py:187-244 -->

### 4.2.5 프로세스 조회와 종료

프로세스 목록은 CPU 사용률 기준 상위 30개를 반환한다. 종료 기능
(`POST /api/monitor/processes/{pid}/kill`)은 관리자만 호출할 수 있고, 그 위에 대상
제한을 둔다. PID 1과 서버 자신은 언제나 거부하며, **이 서버가 직접 실행해 관리 중인
학습용 데모 프로세스이면서 서버의 자식 프로세스인 경우에만** 종료를 허용한다. 세 조건
중 하나라도 어긋나면 403을 반환한다. <!-- 근거: backend/routers/process.py:69-126 -->
종료는 먼저 정상 종료 신호를 보내고 3초 안에 끝나지 않으면 강제 종료로 전환한다.
존재하지 않는 PID는 404다. <!-- 근거: backend/routers/process.py:128-143 -->
즉 이 기능은 임의의 시스템 프로세스를 종료하는 기능이 아니라, 학습용으로 서버가 띄운
프로세스에 한정된 실습 기능이다.

### 4.2.6 연결 상태 표시와 수집 실패 처리

프론트엔드는 WebSocket이 끊기면 3초 간격으로 최대 5회까지 자동 재연결을 시도하고,
매 시도마다 티켓을 새로 발급받는다. <!-- 근거: frontend/src/api/client.js:196-198,218-230,277-292 -->
연결 상태는 별도 컴포넌트가 화면에 항상 표시한다. 이 컴포넌트는 5초마다 마지막 수신
시각을 검사해 연결이 유지된 것처럼 보이더라도 10초 이상 데이터가 도착하지 않으면 응답
없음으로 표시하며, 재연결 시도 중에는 시도 횟수를 함께 보여준다. <!-- 근거: frontend/src/components/WebSocketStatus.jsx:50-61,92-99 -->
끊긴 상태에서 화면의 숫자가 마지막 수신 값에 멈춰 있는 것을 학습자가 현재 값으로
오인하지 않게 하기 위한 장치다.

## 4.3 모니터링 이력 조회

### 4.3.1 주기적 스냅샷 저장

이력 저장은 별도의 스케줄러가 담당한다. 1분 간격으로 실행되며, 직접 수집하지 않고
4.2.1절의 공유 스냅샷을 그대로 재사용한다. 따라서 이력 기능이 추가되어도 수집 횟수는
늘지 않는다. 실행이 밀린 경우에는 중첩 실행하지 않고 한 번만 수행한다. <!-- 근거: backend/services/scheduler.py:22-31,81-89 -->

저장 항목은 CPU 관련 4개, 메모리 관련 6개, 상위 프로세스 목록과 기록 시각이다.
디스크와 네트워크 정보는 스냅샷 테이블에 저장하지 않으며, 두 자원은 실시간 조회로만
제공한다. <!-- 근거: backend/services/scheduler.py:49-62 -->

### 4.3.2 기간·간격별 집계 조회

이력 조회는 세 가지 경로로 제공한다.

| 경로 | 질의 조건 | 반환 내용 |
|---|---|---|
| `GET /api/monitor/history` | 기간(1시간·6시간·24시간·7일), 간격(1분·5분·60분) | 구간별 CPU·메모리의 평균·최소·최대, 표본 수, 최신 상위 프로세스 |
| `GET /api/monitor/raw-history` | 개수(1~1000), 시작 위치 | 원본 스냅샷의 시각별 CPU·메모리 사용률 |
| `GET /api/monitor/stats` | 시간 범위(1~168시간) | CPU·메모리의 평균·최소·최대와 p50·p95·p99 |

**[표 4-4] 이력 조회 API** <!-- 근거: backend/routers/history.py:31-136,143-168,175-236 -->

집계는 조회 구간의 스냅샷을 간격 단위로 묶어 구간마다 통계를 계산하고, 각 구간에는
표본 수를 함께 반환한다. 표본 수를 함께 주는 이유는 같은 평균값이라도 몇 건의 측정에서
나온 값인지에 따라 해석이 달라지기 때문이다. 조회 구간에 데이터가 없으면 오류가 아니라
빈 결과와 총 건수 0을 반환한다. <!-- 근거: backend/routers/history.py:72-77,118-128 -->

다만 이 세 경로는 API로만 제공하며, 이를 호출하는 화면은 구현하지 않았다. <!-- 근거: frontend/src/api/client.js:170-186 (이력 경로 미포함) -->
4.2절의 대시보드에 있는 시계열 그래프는 저장된 이력을 조회한 것이 아니라 WebSocket으로
받은 값을 화면에서 누적한 것이므로, 화면을 다시 열면 이전 값은 남지 않는다. <!-- 근거: frontend/src/components/CPUChart.jsx:22,32 -->

### 4.3.3 보존 기간 정책

원본 스냅샷은 시간이 지날수록 단조 증가하므로 보존 기간을 7일로 정하고, 24시간마다
실행되는 정리 작업이 그보다 오래된 행을 삭제한다. 삭제는 행을 하나씩 조회해 지우지
않고 단일 질의로 처리하며 삭제된 행 수를 반환한다. 경계 시각과 정확히 같은 레코드는
남기도록 엄격한 부등호를 사용한다. <!-- 근거: backend/services/scheduler.py:19,91-100,114-136 -->
삭제 대상은 모니터링 스냅샷 테이블뿐이며, 사용자·로그인 이력·학습 관련 테이블에는
자동 삭제를 적용하지 않는다.

## 4.4 웹 터미널 기반 실습 환경

### 4.4.1 접속 인증과 세션 생성

웹 터미널은 브라우저의 터미널 화면과 서버에서 생성한 컨테이너의 셸을 연결한다.
접속 절차는 4.2.2절과 같은 일회용 티켓 방식을 쓰되 용도가 `shell`로 구분되며, 티켓
발급 단계에서 이미 관리자 권한을 요구한다. <!-- 근거: backend/routers/auth.py:206-211 -->
연결 후에도 서버는 티켓을 소비한 뒤 데이터베이스에서 사용자의 활성 상태와 **현재
역할**을 다시 확인하고, 관리자가 아니면 연결을 종료한다. <!-- 근거: backend/routers/shell.py:241-250 -->
접속 주소에 인증 정보가 포함되어 있으면 연결 수립 이전에 거부하는 것도 동일하다. <!-- 근거: backend/routers/shell.py:222-230 -->

세션 수에는 상한을 둔다. 한 사용자는 동시에 한 개의 셸 세션만 가질 수 있고, 시스템
전체로는 다섯 개까지 허용한다. 상한을 넘은 요청은 사유를 화면에 표시한 뒤 연결을
닫는다. <!-- 근거: backend/routers/shell.py:40-41,208-213,264-269 -->

### 4.4.2 컨테이너 격리

셸은 호스트가 아니라 세션마다 새로 만드는 컨테이너 안에서 실행된다. 컨테이너에
적용한 실행 옵션은 [표 4-5]와 같다.

| 옵션 | 값 | 목적 |
|---|---|---|
| 네트워크 | `none` | 외부 접속과 내부망 탐색 차단 |
| 루트 파일시스템 | 읽기 전용 | 시스템 영역 변조 방지 |
| 커널 권한 | 전부 제거 | 권한이 필요한 조작 자체를 불가능하게 함 |
| 권한 상승 | 금지 | setuid 등을 통한 상승 경로 차단 |
| 실행 사용자 | uid/gid 1000 | 관리자 권한으로 셸이 뜨지 않도록 함 |
| 임시 영역 | `/tmp` 64MB, `/run` 16MB, 실행 금지 | 임시 디렉터리를 이용한 바이너리 실행 차단 |
| 메모리 | 256MB | 자원 고갈 영향 제한 |
| CPU | 0.5 코어 | 위와 같음 |
| 프로세스 수 | 100 | 위와 같음 |
| 종료 시 | 컨테이너 자동 제거 | 세션 간 잔여물 제거 |

**[표 4-5] 셸 컨테이너 실행 옵션** <!-- 근거: backend/routers/shell.py:87-108 -->

쓰기가 가능한 영역은 사용자별 홈 디렉터리 한 곳으로 한정해 마운트한다. 컨테이너 이름은
세션 식별자로 결정되며, 이전에 같은 이름의 컨테이너가 남아 있으면 시작 전에 제거한다. <!-- 근거: backend/routers/shell.py:55,65-72,84-85,90 -->
백엔드는 호스트의 Docker 소켓에 직접 접근하지 않고, 필요한 API만 노출하는 프록시를
경유하도록 구성했다. <!-- 근거: docker-compose.yml:41,48,57-58 -->

### 4.4.3 입출력 중계와 정리

서버는 의사 터미널(PTY)을 열어 컨테이너의 표준 입출력에 연결하고, 브라우저에서 온
키 입력을 그대로 써 넣는다. 출력은 이벤트 루프에 등록한 읽기 콜백으로 받아 WebSocket
으로 내보내며, 셸이 보내는 작업 디렉터리 알림 시퀀스를 해석해 현재 경로를 화면에
갱신한다. 터미널 크기 변경 메시지는 실제 PTY 크기 조정으로 전달한다. <!-- 근거: backend/routers/shell.py:127-164,287-355 -->

컨테이너 시작과 정리는 블로킹 호출이므로 별도 스레드로 옮겨 실행하며, 정리는 잠금으로
보호되어 취소나 동시 호출이 있어도 정확히 한 번만 수행된다. 연결이 어떤 이유로
끝나든 컨테이너 제거와 세션 목록 정리는 항상 수행된다. <!-- 근거: backend/routers/shell.py:166-206,371-387 -->

### 4.4.4 가상 파일 탐색기와 초기화

`GET /api/shell/fs`는 셸 세션의 홈 디렉터리를 화면에서 탐색할 수 있게 한다. 관리자만
호출할 수 있고, 요청한 세션이 자신의 세션이 아니면 403을 반환한다. <!-- 근거: backend/routers/shell.py:390-409 -->
반환 범위는 한 디렉터리와 그 직계 자식으로 제한하며, 다음 제약을 적용한다. <!-- 근거: backend/services/file_tree.py:10-15,26-62 -->

* 요청 경로는 홈 기준 절대 경로여야 하고 `..`이나 `.`을 포함할 수 없다
* 경로를 해석한 결과가 홈 밖을 가리키면 거부한다
* 경로의 각 구성 요소를 링크 추적 없이 개별 검사해 심볼릭 링크를 따라가지 않는다
* 상대 깊이 16단계, 한 디렉터리 200개 항목, 직렬화 64KB, 처리 시간 0.25초를 상한으로 둔다

해석 결과 검사와 링크 검사를 모두 두는 이유는 역할이 다르기 때문이다. 전자는 경로가
허용 범위를 벗어나는 것을 잡고, 후자는 링크를 따라가는 것 자체를 불가능하게 한다. <!-- 근거: backend/services/file_tree.py:33-50,99-132 -->

실습 환경 초기화는 `DELETE /api/shell/reset`이 담당한다. 해당 사용자의 활성 세션을
모두 정리한 뒤 홈 디렉터리를 삭제하고 다시 만든다. 이 경로 역시 관리자 전용이며, 다른
사용자의 홈은 대상이 되지 않는다. <!-- 근거: backend/routers/shell.py:443-484 -->

## 4.5 가상 Linux 상태 기반 학습 시나리오

### 4.5.1 학습 세션과 가상 상태

학습은 세션 단위로 진행한다. `POST /api/ai/sessions`로 시나리오와 문제를 지정하면
해당 문제의 초기 상태를 정의 파일에서 읽어 세션에 복사하고 버전 1로 저장한다.
정의되지 않은 조합이면 422로 거부한다. <!-- 근거: backend/routers/ai_tutor.py:158-187 -->
가상 상태는 서비스 실행·자동 시작 여부, 사용자, 파일의 소유자·그룹·권한, 방화벽 규칙,
열린 포트, 패키지 설치 상태, 원격 접속 가능 여부 등을 담은 구조화된 데이터다. <!-- 근거: backend/services/virtual_linux.py:59-188 -->

세션의 모든 상태 변경 요청은 클라이언트가 알고 있는 버전 번호를 함께 보내고, 서버는
그 버전이 현재 버전과 같을 때만 변경을 적용한 뒤 버전을 1 올린다. 다르면 409를
반환한다. 같은 세션에 대한 요청이 엇갈려 상태가 덮어써지는 것을 막기 위한 처리다. <!-- 근거: backend/routers/ai_tutor.py:79-81,308-316 -->

### 4.5.2 명령 처리: 실행하지 않는 실습

`POST /api/ai/sessions/{id}/commands`가 학습자의 명령을 처리한다. 이 경로는 언어모델을
호출하지 않으며, 명령의 결과 출력도 결정적인 시뮬레이터가 만든다. <!-- 근거: backend/routers/ai_tutor.py:299-302 -->

처리는 [그림 4-2]의 순서를 따른다.

```
   입력 명령
      │
      ▼
 ┌────────────────────┐  셸 메타문자 포함?   ── 예 ──▶ unsupported_syntax
 │  구문 검사          │  (; && || | ` $( > >> < 2> 개행)   (상태 변경 없음)
 └─────────┬──────────┘
           │ 아니오
           ▼
 ┌────────────────────┐  명령 이름이 허용 목록에?  ── 아니오 ──▶ unsupported_syntax
 │  허용 목록·인자 검사 │  인자 형태가 규칙에 맞는가?
 └─────────┬──────────┘
           │ 예
           ▼
 ┌────────────────────┐  적용할 전이 규칙이 있는가? ── 아니오 ──▶ unsupported_syntax
 │  상태 전이 적용     │                                        (전이 전 상태 반환)
 └─────────┬──────────┘
           │ 예
           ▼
   전이된 상태 + 출력 문자열
```

**[그림 4-2] 명령 처리 흐름** <!-- 근거: backend/services/command_parser.py:34-75, backend/services/virtual_linux.py:45-56 -->

구문 검사는 명령 연결(`;`, `&&`, `||`), 파이프, 명령 치환(`` ` ``, `$(`), 리다이렉션
(`>`, `>>`, `<`, `2>`), 개행을 포함한 입력을 먼저 거부한다. <!-- 근거: backend/services/command_parser.py:22 -->
학습 시나리오 정의 파일이 거부 대상으로 명시한 문법은 여덟 종류이며, 모두 상태를
변경하지 않는 것으로 기대 동작이 함께 기술되어 있다. <!-- 근거: backend/test/fixtures/ai_learning_scenarios.json의 rejected_shell_syntax -->

통과한 입력은 셸을 거치지 않고 토큰으로 분해한 뒤 허용 목록과 대조한다. 하위 동작을
갖는 명령은 `systemctl`, `ufw`, `apt` 세 가지이고, 단독 명령은 `useradd`, `userdel`,
`usermod`, `passwd`, `chmod`, `chown`, `ls`, `cat`, `ss`, `curl`, `ping` 열한 가지다. <!-- 근거: backend/services/command_parser.py:26-31 -->
허용된 명령이라도 인자 형태를 개별적으로 검증한다. 예를 들어 목록 조회는 인자가 없거나
`/`로 시작하는 절대 경로 하나만, 포트 확인은 정해진 문자 집합으로 이루어진 단일 옵션
문자열만, HTTP 확인은 미리 정해 둔 두 형태만 허용한다. <!-- 근거: backend/services/command_parser.py:61-73 -->
금지 목록이 아니라 허용 목록을 쓴 이유는, 금지 목록은 새로운 우회 표현이 나타날 때마다
항목을 추가해야 하지만 허용 목록은 정의되지 않은 것이 모두 거부되기 때문이다.

상태 전이는 원본이 아니라 **복사본** 위에서 수행한다. 지원하지 않는 문법이거나 적용할
규칙이 없으면 전이 이전 상태를 그대로 반환하므로, 진행 중이던 실습 상태가 훼손되지
않는다. 또한 데이터베이스의 상태는 결과 코드가 성공인 경우에만 갱신된다. <!-- 근거: backend/services/virtual_linux.py:45-56, backend/routers/ai_tutor.py:308-313 -->

주요 전이 규칙은 [표 4-6]과 같다.

| 명령 계열 | 상태 변화 |
|---|---|
| `systemctl start`·`restart`·`stop` | 서비스의 실행 여부 변경 |
| `systemctl enable`·`disable` | 서비스의 자동 시작 여부 변경 |
| `useradd`·`userdel`·`passwd` | 사용자 추가·삭제, 비밀번호 설정 표시 |
| `chown`·`chmod` | 파일의 소유자·그룹·권한 모드 변경 |
| `ufw allow`·`deny` | 22번 포트 방화벽 규칙 변경 |
| `apt install`·`remove` | 패키지 설치 상태 변경 |
| `ss`, `ufw status`, `ping` | 상태를 바꾸지 않고 진단 기록만 남김 |

**[표 4-6] 명령별 상태 전이** <!-- 근거: backend/services/virtual_linux.py:59-180 -->

서비스 실행 여부나 방화벽 규칙이 바뀌면 원격 접속 가능 여부를 함께 다시 계산한다.
SSH 서비스가 실행 중이고 22번 포트가 허용된 경우에만 접속 가능으로 표시되므로, 학습자는
두 조건이 함께 충족되어야 한다는 점을 상태 변화로 확인하게 된다. <!-- 근거: backend/services/virtual_linux.py:183-188 -->
정의 파일에 없는 경로를 조회하는 경우에는 경로 문자열에서 결정적으로 만들어 낸 목록을
한 번 생성해 상태에 보관하므로, 같은 경로를 다시 조회해도 결과가 달라지지 않는다. <!-- 근거: backend/services/virtual_linux.py:21-34,137-149 -->

명령 시도는 결과와 무관하게 모두 기록한다. 저장 항목은 명령 문자열, 결과 코드, 출력,
실행 전 상태와 실행 후 상태다. <!-- 근거: backend/routers/ai_tutor.py:303-307 -->

### 4.5.3 시나리오 구성

학습 내용은 코드가 아니라 외부 정의 파일에 둔다. 문제, 초기 상태, 목표 상태, 채점 규칙,
힌트, 정답 예시가 모두 이 파일에 기술되어 있으며 코드는 읽기만 한다. <!-- 근거: backend/services/curriculum.py:11,19-21 -->

| 시나리오 | 학습 목표 | 문제 수 |
|---|---|---:|
| Nginx 서비스 장애 복구 | systemd 서비스 상태를 진단하고 안전하게 복구한다 | 2 |
| 운영 계정과 파일 권한 구성 | 사용자를 만들고 소유권과 최소 파일 권한을 설정한다 | 2 |
| 방화벽과 원격 접속 장애 | 열린 포트와 방화벽 규칙을 확인하고 원격 접속 차단을 복구한다 | 2 |

**[표 4-7] 학습 시나리오 구성** <!-- 근거: backend/test/fixtures/ai_learning_scenarios.json의 scenarios -->

각 문제에는 3단계 힌트가 정의되어 있다. 커리큘럼 목록에는 여섯 문제 뒤에 복습 라운드

### 4.5.4 최종 상태 기준 채점

채점은 `POST /api/ai/sessions/{id}/grade`가 수행하며 언어모델을 호출하지 않는다.
판정은 성공, 부분 성공, 실패 순서로 규칙을 대조해 **처음 일치하는 결과를 채택**한다. <!-- 근거: backend/services/task_grader.py:44-54 -->
각 규칙은 세 가지 조건을 조합해 기술한다.

* 반드시 만족해야 하는 상태 조건
* 여러 후보 중 하나만 만족하면 되는 상태 조건
* 특정 명령 계열을 사용한 적이 있는지 보는 조건

세 번째 조건은 진단 학습처럼 상태 변화 없이 확인 행위 자체가 학습 목표인 경우에
사용하며, 이때도 허용 목록 파서를 통과한 명령만 사용한 것으로 인정한다. <!-- 근거: backend/services/task_grader.py:75-106,150-158 -->
상태 조건은 점으로 구분한 경로로 기술하는데, 키 자체에 점이 들어 있는 항목(예:
`22/tcp` 같은 방화벽 규칙 키)도 올바르게 찾도록 경로 해석을 별도로 구현했다. <!-- 근거: backend/services/task_grader.py:124-147 -->

채점 대상은 명령 문자열이 아니라 명령 처리 후의 최종 상태다. 따라서 서로 다른 명령으로
같은 목표 상태에 도달하면 모두 정답으로 인정된다. 예를 들어 중지된 서비스를 시작하는
문제에서는 시작 명령과 재시작 명령이 모두 성공으로 판정되며, 이는 정의 파일에도 정답
예시와 대체 정답으로 함께 기술되어 있다. <!-- 근거: backend/services/virtual_linux.py:82-85, fixture의 answer_examples.alternative -->
반대로 자동 시작만 설정하고 서비스를 켜지 않은 상태는 부분 성공으로 구분된다. <!-- 근거: fixture service_recovery_01의 grading.partial -->

성공한 규칙에도, 알려진 실패 규칙에도 해당하지 않는 상태는 실패로 처리하되 일치 조건
기록은 비워 둔다. 근거 없는 판정 사유를 만들어 내지 않기 위한 처리다. <!-- 근거: backend/services/task_grader.py:51-54 -->

성공하면 다음 문제와 그 초기 상태로 세션을 전환하고, 더 이상 남은 문제가 없으면 세션을
완료 상태로 표시한다. 성공하지 못하면 같은 문제와 현재 상태를 유지한다. 채점 결과는
매번 감사 기록으로 남는다. <!-- 근거: backend/routers/ai_tutor.py:414-443 -->
`POST /api/ai/sessions/{id}/reset`은 현재 문제의 초기 상태를 다시 써넣어 실습을
처음부터 시작하게 한다. <!-- 근거: backend/routers/ai_tutor.py:199-229 -->

## 4.6 생성형 AI 질의응답 및 설명 생성

### 4.6.1 호출 지점과 프롬프트 구성

언어모델을 호출하는 경로는 학습자의 질문(`POST /{id}/chat`)과 힌트 요청
(`POST /{id}/hints`) 두 곳뿐이다. 4.5절의 명령 처리와 채점은 언어모델을 호출하지
않는다. <!-- 근거: backend/routers/ai_tutor.py:333-358,361-398 -->

질문 처리의 순서는 다음과 같다. 먼저 현재 문제 정의를 읽고, 현재 가상 상태를 규칙
기반으로 채점해 판정을 확정한다. 그다음 그 판정과 상태를 포함한 입력을 만들어 모델을
호출한다. 즉 **판정이 먼저 끝나고 설명이 뒤따르며, 순서는 역전되지 않는다.** <!-- 근거: backend/routers/ai_tutor.py:340-347 -->

모델에 전달하는 항목은 [표 4-8]의 일곱 가지다.

| 항목 | 내용 |
|---|---|
| 학습자 수준 | 세션에 기록된 난이도 |
| 문제 정의 | 정의 파일의 현재 문제 |
| 가상 상태 요약 | 현재 세션의 가상 Linux 상태 |
| 확정 판정 | 규칙 기반 채점기가 결정한 성공·부분 성공·실패 |
| 학습자 입력 | 질문 문장(힌트 요청에서는 규칙 기반 힌트 문구) |
| 최근 대화 | 최근 4건 |
| 채점 이력 | 이 세션의 최근 채점 결과 5건 |

**[표 4-8] 프롬프트 입력 항목** <!-- 근거: backend/services/bedrock.py:129-138, backend/routers/ai_tutor.py:344-347,376-378 -->

실제 서버의 CPU·메모리 사용량은 이 입력에 포함되지 않는다. 설명의 대상은 가상 실습
상태와 채점 결과이며, 실제 자원 사용량은 4.2절의 모니터링 화면이 수치와 그래프로
제공한다.

프롬프트는 자연어 문장에 값을 끼워 넣지 않고 구조화된 데이터로 담아 전달한다. 학습자
입력과 이전 대화처럼 신뢰할 수 없는 텍스트는 별도 구획 안에 넣고, 그 구획의 내용을
지시가 아니라 인용된 데이터로 취급하라고 명시한다. 아울러 상태와 확정 판정이 변경
불가능한 사실임을 밝히고, 모델이 명령을 실행했다고 주장하거나 판정을 뒤집는 것을
금지한다. 채점 이력은 설명의 깊이와 어조를 조절하는 데만 쓰고 판정을 바꾸는 데는 쓰지
말라고 지시한다. <!-- 근거: backend/services/bedrock.py:139-151 -->
학습자 입력 2,000자, 문제 정의 4,000자, 상태 요약 6,000자, 전체 프롬프트 16,000자의
상한을 두어 과도한 입력이 호출 비용과 오류로 이어지지 않게 했다. <!-- 근거: backend/services/bedrock.py:36-39,152-153 -->

호출은 Amazon Bedrock의 통합 대화 API를 사용한다. 리전과 모델은 코드에 고정되어 있고
호출 파라미터는 [표 4-9]와 같다.

| 항목 | 값 |
|---|---|
| 리전 | `us-east-1` |
| 모델 | `us.anthropic.claude-haiku-4-5-20251001-v1:0` |
| 최대 출력 토큰 | 1,024 |
| temperature | 0.1 |
| 연결·응답 타임아웃 | 3초 / 20초 |
| 최대 시도 횟수 | 2 |

**[표 4-9] 언어모델 호출 파라미터** <!-- 근거: backend/services/bedrock.py:28-34,99-109,208-215 -->

SDK 자체의 재시도는 1회로 고정해 두고 재시도 여부는 애플리케이션이 판단한다. 타임아웃,
처리량 초과, 5xx 계열 오류는 짧게 대기한 뒤 한 번 더 시도하고, 권한 없음·요청 형식
오류·리소스 없음은 재시도해도 결과가 같으므로 즉시 중단한다. <!-- 근거: backend/services/bedrock.py:42-53,238-251,352-373 -->
호출은 블로킹 방식이므로 별도 스레드에서 실행해 이벤트 루프를 막지 않는다. <!-- 근거: backend/routers/ai_tutor.py:64 -->

### 4.6.3 응답 검증과 대체 응답

모델의 응답은 그대로 쓰지 않고 정해진 형식으로 검증한 뒤에만 화면에 전달한다. 허용
필드는 터미널 출력 예시, 설명, 힌트 단계, 추천 개념 네 가지이며 각각 길이와 범위 제한이
있다. 정의되지 않은 필드가 하나라도 있으면 응답 전체를 거부한다. <!-- 근거: backend/services/bedrock.py:58-66 -->
응답 형식은 하나의 JSON 객체이거나 코드 블록 하나에 담긴 JSON 객체만 인정하고, 텍스트
에서 중괄호를 찾아 추출하는 방식은 쓰지 않는다. 형식이 어긋난 응답을 억지로 해석하면
의미가 왜곡된 채 학습자에게 전달되기 때문이다. <!-- 근거: backend/services/bedrock.py:157-177 -->
호출 전후로 입력값 사본을 비교해 호출 과정에서 입력이 변형되었으면 성공 응답이라도
사용하지 않는다. <!-- 근거: backend/services/bedrock.py:196,227-231 -->

검증에 실패했거나 호출 자체가 실패한 경우에는 예외를 화면으로 올리지 않고, 성능 저하
상태임을 명시한 대체 응답을 돌려준다. 대체 응답에는 실패 사유 코드와 재시도 가능 여부가
담기고, 학습자에게는 규칙 기반 안내로 대체되었음을 알리는 고정 문구가 표시된다. <!-- 근거: backend/services/bedrock.py:255-279 -->
따라서 언어모델을 쓸 수 없는 상황에서도 문제 제시, 명령 처리, 채점, 규칙 기반 힌트는
그대로 동작한다.

호출 기록에는 프롬프트 본문, 모델 응답 원문, 학습자 입력을 남기지 않는다. 대신 프롬프트를
해시한 짧은 식별자와 지연 시간, 시도 횟수, 실패 사유, 요청 식별자만 기록해 동일 요청
여부는 추적하면서 내용은 노출되지 않게 했다. <!-- 근거: backend/services/bedrock.py:281-302 -->

### 4.6.4 호출량 제한과 대화 이력

호출량은 사용자 단위로 제한한다. 한 사용자의 요청이 동시에 두 건 이상 진행되지 않게
하고, 직전 호출이 끝난 뒤 2초의 대기 시간을 둔다. 제한에 걸린 요청에는 재시도까지 남은
시간을 헤더에 담아 429로 응답하며, 화면은 이를 "몇 초 후 다시 시도" 안내로 표시한다. <!-- 근거: backend/services/ai_rate_limit.py:8-29, backend/routers/ai_tutor.py:55-61, frontend/src/pages/AITutor.jsx:38-41 -->

대화는 세션 단위로 저장한다. 학습자 질문과 모델 응답, 규칙 기반 힌트 문구가 각각 역할을
구분해 기록되며, 다음 호출의 최근 대화 입력은 이 기록에서 최근 4건을 시간순으로 읽어
구성한다. <!-- 근거: backend/routers/ai_tutor.py:101-106,348-350 -->
`GET /api/ai/sessions/{id}/history`는 명령 시도, 대화, 상호작용 감사 기록을 하나의
목록으로 합쳐 시간순으로 반환한다. <!-- 근거: backend/routers/ai_tutor.py:232-288 -->

### 4.6.5 화면 구성

AI 학습 화면은 커리큘럼 목록, 문제 카드, 터미널 패널, AI 도우미 패널로 구성된다.
터미널 패널과 AI 도우미 패널을 나눈 것은 의도적이다. 명령 실행 결과는 결정적 시뮬레이터의
출력이고 도우미 패널의 내용은 언어모델의 생성물이므로, 두 출처를 한 흐름에 섞으면
학습자가 무엇이 확정된 사실인지 구분하기 어렵다. 화면 상단에는 명령이 실제로 실행되지
않으며 채점은 서버의 규칙이 결정한다는 고지를 항상 표시한다. <!-- 근거: frontend/src/pages/AITutor.jsx:146-152,214-258 -->
대체 응답이 표시될 때는 해당 메시지에 "규칙 기반" 표시가 붙어 언어모델의 설명이
아님을 드러낸다. <!-- 근거: frontend/src/pages/AITutor.jsx:243 -->

## 4.7 학습자 맞춤형 피드백

### 4.7.1 단계별 힌트

힌트는 `POST /api/ai/sessions/{id}/hints`로 요청한다. 서버는 먼저 현재 상태를 채점해
이미 성공한 문제이면 힌트를 주지 않고 409로 거부한다. <!-- 근거: backend/routers/ai_tutor.py:368-371 -->
이어 이 문제에 대해 지금까지 열린 힌트 단계를 감사 기록에서 조회해 다음 단계를
계산하되 3단계를 넘지 않는다. <!-- 근거: backend/routers/ai_tutor.py:90-98,372-373 -->

각 단계의 힌트 문구는 정의 파일에 고정되어 있고, 단계는 개념, 명령 계열, 구문 순으로
구성된다. 처음부터 구문을 알려주면 학습자가 스스로 판단할 기회가 사라지므로 필요한
만큼만 여는 구조다. <!-- 근거: backend/services/curriculum.py:210-218, fixture의 hints -->

| 단계 | 종류 | 예 |
|---|---|---|
| 1 | 개념 | 설치 여부와 현재 서비스 상태를 먼저 확인합니다 |
| 2 | 명령 계열 | `systemctl status`와 `start` 계열을 사용합니다 |
| 3 | 구문 | `systemctl start nginx` |

**[표 4-10] 힌트 단계 구성** <!-- 근거: fixture service_recovery_01의 hints -->

여기서 언어모델의 역할은 힌트를 만드는 것이 아니다. 서버는 확정된 힌트 문구를 학습자
입력 위치에 넣어 모델을 호출하고, 모델은 그 문구에 대한 부연 설명만 생성한다. 화면에는
규칙 기반 힌트와 모델의 부연 설명이 각각 별도 항목으로 표시된다. <!-- 근거: backend/routers/ai_tutor.py:374-380, frontend/src/pages/AITutor.jsx:110-113 -->

### 4.7.2 시도 이력과 오답 이력

학습 이력은 세 종류의 기록으로 남는다.

| 기록 | 남기는 시점 | 내용 |
|---|---|---|
| 명령 시도 | 명령 입력마다 | 명령 문자열, 결과 코드, 출력, 실행 전후 상태 |
| 상호작용 감사 | 채점·힌트마다 | 동작 종류, 시나리오·문제, 판정 결과, 시도 수와 힌트 단계 |
| 대화 | 질문·힌트마다 | 역할과 내용 |

**[표 4-11] 학습 이력 기록** <!-- 근거: backend/routers/ai_tutor.py:303-307,379-383,437-442 -->

현재 문제의 시도 횟수는 감사 기록 중 채점 동작의 수로 계산하고, 현재 힌트 단계는 힌트
동작에 기록된 단계의 최댓값으로 계산한다. 두 값은 명령 실행·질문·힌트·채점 응답에
모두 포함되어 화면에 현재 진행 상황으로 표시된다. <!-- 근거: backend/routers/ai_tutor.py:90-98,71-76 -->

### 4.7.3 진도 관리와 다음 문제 선택

다음 문제 선택은 결정적 규칙을 따른다. 채점 결과가 성공일 때만 정의 파일의 다음 순서로
넘어가고, 그렇지 않으면 같은 문제에 머문다. 무작위 선택이나 모델의 판단은 개입하지
않는다. <!-- 근거: backend/services/curriculum.py:161-207 -->

커리큘럼의 마지막 칸은 복습 라운드로, 앞서 완료한 문제 중 하나를 다시 제시한다. 이때
선택은 세션 식별자를 난수 시드로 사용하므로 같은 세션에서 반복 조회해도 같은 문제가
유지되고, 세션이 다르면 다른 문제가 선택된다. 복습 문제는 원래 문제와 구분되는
식별자로 제시되어 진도·이력 추적이 원래 시도와 섞이지 않는다. <!-- 근거: backend/services/curriculum.py:14-16,153-158,200-206 -->
복습 라운드까지 성공하면 세션이 완료 상태가 되고 화면에 완료 안내가 표시된다. <!-- 근거: backend/routers/ai_tutor.py:416,429-431, frontend/src/pages/AITutor.jsx:125-127 -->

### 4.7.4 이력을 반영한 설명

반복해서 틀리는 학습자에게 설명을 조절하는 방식은 다음과 같이 구현했다. 질문과 힌트
요청 시 이 세션의 최근 채점 결과 5건(문제 식별자와 판정)을 프롬프트에 함께 넣고,
프롬프트 지시문에서 이 이력을 **설명의 깊이와 어조를 조정하는 데만 쓰고 판정을 바꾸는
데는 쓰지 말라고** 명시한다. <!-- 근거: backend/routers/ai_tutor.py:109-115,347,375, backend/services/bedrock.py:137,143-146 -->

다만 어떤 개념을 반복해서 틀렸는지 서버가 분류해 지정하는 로직은 구현하지 않았다.
서버가 제공하는 것은 문제별 판정 이력이라는 구조화된 사실이며, 그로부터 부족한 부분을
짚어 설명하는 일은 모델이 수행한다. 이 차이는 5장과 6장에서 기대 효과와 한계를 나눌 때
다시 다룬다.

## 4.8 구현 검증

본 절은 구현이 설계대로 동작하는지 실제로 실행해 확인한 결과다. 각 항목은 실행한 검사와
그 범위를 함께 적으며, 실행하지 않은 것은 4.8.6절에 따로 정리한다.

### 4.8.1 권한 행렬 전수 검증

권한 판정이 서버에서 실제로 이루어지는지 확인하기 위해, 인증 의존성을 대체하지 않은
상태로 애플리케이션 전체를 기동해 검증했다. 메모리 상의 격리된 데이터베이스에 합성
계정을 만들고 로그인 API로 실제 토큰을 발급받은 뒤, 보안 계약에 정의된 21개 경로를
미인증·일반 사용자·관리자·비활성 사용자 네 조건으로 호출했다. 로그인 응답이 계정
상태를 드러내지 않는지 확인하는 검사 두 건을 포함해 **86건이 모두 통과했다.** <!-- 근거: backend/tests/test_authorization_matrix_e2e.py:1-16,77-125,229-289 -->

기존 권한 테스트는 인증 의존성을 대체물로 바꿔 두고 "라우트가 올바른 의존성을 선언
했는가"만 확인할 수 있었다. 이 검증은 그 대체를 모두 제거했으므로, 토큰 해석부터
데이터베이스 재조회와 역할 확인까지 이어지는 실제 경로가 요청을 거부한다는 것을
보인다.

### 4.8.2 동시 접속 실측

실제 서버 프로세스를 띄우고 모니터링 WebSocket 동시 연결을 측정했다. **50개 연결이
모두 수립되었고 첫 데이터 수신까지 5.2초가 걸렸다.** 연결이 유지된 상태에서 REST 요청도
정상 응답했다. <!-- 근거: docs/re-progress.md Validation Log의 RELEASE-01 #3·4·8 행 -->
같은 실행에서 티켓 계약도 함께 확인했다. 캐시 금지 헤더와 60초 유효 시간, 최초 사용
수락, **재사용 거부**, 모니터링 티켓으로 터미널에 접속하려는 시도의 거부, 인증 메시지
이전의 데이터 미전송이 모두 확인되었다.

이 측정은 개발용 Windows 호스트에서 수행했으므로 배포 대상 하드웨어의 성능 수치로
쓸 수 없다. 확인한 것은 "연결 수가 늘어도 서비스가 유지되는가"이지 응답 시간의
절대값이 아니다.

### 4.8.3 상태 규칙 엔진의 결정성 확인

4.5절의 상태 전이와 채점이 같은 입력에 대해 항상 같은 결과를 내는지 확인하기 위해
규칙 엔진만 **300회 반복 실행**했다. 결과는 **결정성 1.0**이고, 1회 처리 시간은 중앙값
0.065ms, 95백분위 0.093ms였다. 이 측정은 언어모델을 거치지 않고 규칙 엔진만 실행한
것이다. <!-- 근거: docs/benchmarks/stage10 요약의 state_rule_benchmark (samples 300, determinism_rate 1.0) -->

### 4.8.4 인증 정보의 로그 비노출 확인

로그에 인증 정보가 남지 않는지는 패턴 추정이 아니라 실제 발급값 대조로 확인했다.
검증 실행 중 실제로 발급된 접근 토큰 2개와 WebSocket 티켓 2개의 **원문 문자열**이
서버 로그 전체에 존재하는지 대조해 **4건 모두 부재**를 확인했고, 접속 주소의 질의
항목과 인증 헤더 값도 나타나지 않았다. 프록시의 접근 로그에 대해서도 같은 방식으로
대조해 노출 0건을 확인했다. <!-- 근거: docs/re-progress.md Validation Log의 RELEASE-01 #2 두 행 -->

### 4.8.5 셸 격리 우회 차단 확인

파일 탐색기의 격리는 실제 파일시스템에 심볼릭 링크를 만들어 검증했다. 허용 루트 밖을
가리키는 링크의 제외, 링크 대상 자체의 거부, 순환 링크 제외를 포함한 7건이 통과했다. <!-- 근거: docs/re-progress.md Validation Log의 RELEASE-01 #6 행, backend/tests/test_shell_file_tree.py -->

컨테이너 격리는 4.4.2절과 동일한 실행 옵션으로 컨테이너를 띄운 뒤 내부에서 18개 항목을
직접 확인했다. 외부 통신(ping·DNS·HTTP)이 모두 차단되고 네트워크 인터페이스가 루프백
하나뿐이며, Docker 소켓과 CLI가 존재하지 않고, 시스템 디렉터리 쓰기가 거부되며 임시
영역에서 스크립트가 실행되지 않고, 커널 권한 집합이 비어 있고 권한 상승이 차단되며,
메모리와 프로세스 수 상한이 지정한 값으로 적용되어 있음을 확인했다. **18항목 모두
통과했다.** <!-- 근거: docs/re-progress.md Validation Log의 RELEASE-01 #5 행 -->

### 4.8.6 확인하지 않은 것

검증의 경계를 분명히 하기 위해 실행하지 않은 항목을 함께 적는다.

* 실제 브라우저를 사람이 조작해야 하는 검사 3건은 수행하지 않았다. 접근성 관련 자동
  검사는 통과한 상태이나 실제 브라우저에서의 초점 순서와 화면 낭독은 확인하지 않았다. <!-- 근거: docs/re-progress.md의 DEC-BROWSER-SKIP, Known Limitations -->
* 성능 수치는 개발 호스트에서 측정한 값이며 배포 대상 하드웨어에서 측정하지 않았다. <!-- 근거: docs/re-progress.md Known Limitations -->
* 셸 컨테이너 격리는 격리 속성 자체를 확인한 것이고, 브라우저에서 시작해 컨테이너까지
  이어지는 세션 전체 흐름은 검증 환경의 제약으로 확인하지 않았다. <!-- 근거: docs/re-progress.md Validation Log의 RELEASE-01 #5 행 -->
* 활성 상태에서 티켓을 받은 직후 계정이 비활성화된 경우의 WebSocket 연결 경로는 실제
  구동으로 확인하지 않았고 단위 검증 범위에 있다. <!-- 근거: docs/re-progress.md Known Limitations -->

또한 언어모델 응답의 품질이나 학습 효과는 본 연구의 검증 대상이 아니다. 본 절이 확인한
것은 시스템이 설계한 대로 동작하는지이며, 사람을 대상으로 한 학습 효과 평가는 수행하지
않았다.

## 4.9 요약

본 장에서는 3장의 설계가 실제 구현에서 어떻게 동작하는지를 기능별로 기술했다.

인증은 요청마다 데이터베이스에서 사용자 상태와 역할을 다시 확인하는 방식으로 구현
했으며, 그 강제가 실제로 이루어짐을 21개 경로 전수 검증으로 확인했다. 모니터링은
하나의 백그라운드 수집기가 5초마다 만든 스냅샷을 모든 연결이 공유하는 구조로 구현해
연결 수와 수집 횟수를 분리했다. 학습 기능에서 입력한 명령은 허용 목록 검사를 거쳐
가상 상태의 복사본에만 적용되며, 지원하지 않는 입력은 상태를 바꾸지 않는다. 성취
판정은 명령 문자열이 아니라 최종 상태를 기준으로 하는 규칙이 수행하고, 언어모델은
이미 확정된 상태와 판정을 설명하는 두 지점에서만 호출된다. 언어모델 호출이 실패하면
사유를 명시한 대체 응답으로 전환되고 학습 흐름 자체는 유지된다.

이렇게 구현한 시스템이 학습 상황에서 어떻게 활용될 수 있는지는 5장에서 다룬다.
