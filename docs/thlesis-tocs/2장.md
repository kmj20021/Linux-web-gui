# 2. 관련 연구 및 기술 배경

본 장에서는 본 연구가 다루는 세 가지 배경 기술과 선행 연구를 정리한다. 서버 자원 모니터링,
웹 기반 시스템 관리 도구, 시뮬레이션 기반 실습 환경, 생성형 AI를 활용한 학습 지원 순으로
살펴본 뒤, 본 시스템이 사용하는 Amazon Bedrock의 구조를 설명하고, 마지막으로 기존 연구와
본 연구의 차이를 정리한다.

## 2.1 Linux 서버 모니터링 시스템

서버 모니터링은 시스템의 자원 사용량과 프로세스 활동을 실시간 또는 시계열로 추적하여 성능
저하나 장애의 징후를 미리 파악하는 활동이다. 모니터링의 목적은 성능 병목의 조기 발견, 보안
이상 징후 탐지, 자원 관리의 효율화, 서비스 중단의 예방 등으로 정리된다[1].

모니터링에서 다루는 주요 자원과 그 의미는 다음과 같다.

**CPU**는 사용률과 코어별 부하, 그리고 load average로 관찰한다. load average는 실행 중이거나
실행을 기다리는 프로세스 수의 1분, 5분, 15분 평균이며, CPU 코어 수와 함께 보아야 과부하
여부를 판단할 수 있다[2]. **메모리**는 전체 용량, 사용량, 여유 용량과 swap 사용량으로
관찰한다. 여기서 초보 학습자가 흔히 오해하는 지점이 있다. Linux는 사용되지 않는 메모리를
파일 캐시(buffers, cached)로 적극 활용하며, 이 영역은 응용 프로그램이 메모리를 요구하면 즉시
회수된다[2]. 따라서 캐시가 점유한 용량을 부족한 메모리로 해석하면 잘못된 판단에 이른다.
**디스크**는 파티션별 사용률과 읽기·쓰기 속도, 지연 시간으로 관찰하며, **네트워크**는 송수신
대역폭, 패킷 손실, 열린 포트와 연결 상태로 관찰한다[1].

Linux 환경에서 이러한 지표는 전통적으로 `top`, `vmstat`, `free`와 같은 명령행 도구로
확인해 왔다[1][2]. 프로그램에서 지표를 수집할 때는 `/proc` 파일 시스템을 직접 읽거나 이를
감싼 라이브러리를 사용한다. 본 시스템이 사용하는 psutil은 CPU, 메모리, 디스크, 네트워크,
프로세스 정보를 한 인터페이스로 제공하는 라이브러리이며, CPU 사용률 측정처럼 일정 시간의
경과를 필요로 하는 호출이 포함되어 있다[3]. 이 특성은 수집 작업을 요청 처리 흐름과 분리해야
하는 이유가 되며, 3장의 상태 수집 구조에서 다시 다룬다.

## 2.2 웹 기반 시스템 관리 도구

웹 기반 관리 인터페이스는 브라우저만 있으면 운영체제와 무관하게 접근할 수 있고, 원격에서
관리할 수 있으며, 수치를 그래프와 대시보드로 시각화하고, 여러 사용자가 동시에 접근할 수
있다는 장점이 있다. 이 때문에 오늘날 서버 모니터링 도구 대부분이 웹 화면을 기본 인터페이스로
제공한다.

대표적인 도구는 다음과 같다. Prometheus는 대상 시스템의 지표 노출 지점을 주기적으로
가져오는 풀(pull) 방식으로 수집하고, 이를 시계열 데이터베이스에 저장하며, 규칙에 따라 알림을
발생시킨다[4]. Grafana는 여러 데이터 소스를 연결하여 대시보드로 시각화하는 도구로, 흔히
Prometheus와 함께 사용된다[5]. Netdata는 노드마다 에이전트를 두어 초 단위로 지표를 수집하고
설치 직후부터 사전 구성된 대시보드를 제공한다[6]. Cockpit은 단일 호스트를 웹에서 관리하도록
설계된 도구로 가벼운 모니터링 기능을 포함한다[7]. 이 밖에 Zabbix, Nagios와 같이 가용성
점검과 알림에 중점을 둔 전통적인 엔터프라이즈 모니터링 도구도 널리 사용된다.

| 도구 | 주된 목적 | 지표 시각화 | 별도 구성 요소 | 학습 지원 기능 |
|---|---|---|---|---|
| Prometheus + Grafana | 지표 수집·저장·시각화 | 있음 | 수집기, 시계열 DB, 대시보드 분리 | 없음 |
| Netdata | 노드별 실시간 지표 관찰 | 있음 | 노드별 에이전트 | 없음 |
| Cockpit | 단일 호스트 웹 관리 | 있음(기본 수준) | 호스트 내장 | 없음 |
| Zabbix, Nagios | 가용성 점검·알림 | 있음 | 서버, 에이전트 | 없음 |

[표 2-1] 기존 웹 기반 모니터링 도구의 기능 범위

이 도구들은 운영 업무에서 충분히 검증되어 있다. 다만 본 연구가 상정하는 사용자는 서버를
운영하는 전문가가 아니라 Linux 서버 운영을 처음 배우는 학습자이며, 대상 사용자가 다르기
때문에 다음과 같은 한계가 드러난다.

첫째, 이 도구들은 지표의 값을 보여 주지만 그 값의 의미를 설명하지 않는다. 화면에 "CPU 90%"가
표시되어도 학습자는 그것이 정상적인 작업 부하인지 문제 상황인지 판단할 근거를 얻지 못한다.
둘째, 도구를 사용할 수 있는 상태로 만드는 데 필요한 사전 지식이 적지 않다. 예를 들어
Prometheus와 Grafana를 함께 구성하려면 수집 대상 설정, 질의 언어, 대시보드 구성을 알아야
한다[4][5]. 셋째, 학습을 위한 기능, 즉 과제 제시와 성취 판정, 피드백에 해당하는 기능이 없다.
이는 결함이 아니라 설계 목적의 차이이지만, 학습자가 이 도구들만으로 서버 운영을 익히기는
어렵다는 것을 의미한다.

## 2.3 시뮬레이션 기반 실습 환경

Linux 서버 운영은 명령을 직접 실행해 보아야 익힐 수 있지만, 초보 학습자가 실제 서버에서
실습하는 데에는 위험이 따른다. 서비스를 중지하거나, 방화벽을 잘못 설정하거나, 파일을 잘못
삭제하는 명령 하나로 시스템을 복구하기 어려운 상태로 만들 수 있고, 여러 사람이 함께 쓰는
서버라면 피해가 다른 사용자에게까지 확산된다. 가상 실습 환경에 관한 연구들은 이론과 실습의
연계, 반복 수행 가능성, 확장성, 비용 절감과 함께 학습자의 안전 확보와 위험한 실험의 수행
가능성을 공통된 이점으로 제시한다[8].

실습 환경을 격리하는 방식은 크게 세 가지로 나눌 수 있다.

| 방식 | 학습자당 비용 | 격리 강도 | 실제 실행 경험 |
|---|---|---|---|
| 가상머신 | 높음(GB 단위 자원, 긴 기동 시간) | 강함(운영체제 단위 격리) | 제공 |
| 컨테이너 | 낮음(경량, 초 단위 기동) | 중간(호스트 커널 공유) | 제공 |
| 상태 시뮬레이션 | 매우 낮음(데이터 1건 수준) | 실행 자체가 없음 | 제공하지 않음 |

[표 2-2] 실습 환경 격리 방식의 비교

가상머신은 운영체제 전체를 격리하므로 격리 강도가 가장 높지만 학습자마다 상당한 자원과
기동 시간이 필요하다. 컨테이너는 호스트 커널을 공유하여 자원 소모가 작고 기동이 빠르며
동시에 많은 인스턴스를 운영할 수 있으나, 커널을 공유하는 만큼 격리 강도는 가상머신보다
약하다[9][10][11]. 상태 시뮬레이션은 명령을 실제로 실행하지 않고 구조화된 가상 상태만
전이시키는 방식으로, 학습자당 비용이 데이터 한 건 수준이고 서비스 중지나 방화벽 차단처럼
위험한 명령도 안전하게 학습 소재로 삼을 수 있다. 대신 명령을 실제로 실행해 보는 경험은
제공하지 못한다.

실습 플랫폼은 이 가운데 실제 실행 방식을 채택한 사례가 많다. Linux Luminarium은 브라우저에서
Linux 학습 과제를 제공하는 플랫폼으로, 공개 이후 만 명 단위의 학습자가 다수의 과제를 해결한
운영 사례를 보고하였다[12]. KillerCoda는 브라우저에서 실제 Linux 및 Kubernetes 환경을
제공하며[13], OverTheWire의 Bandit은 단계별 과제를 해결해 다음 단계로 진행하는 방식으로
Linux 기초를 가르친다[14]. 웹에서 가상 Linux 인스턴스로 시스템 관리를 실습하게 하는 초기
가상 실습실 연구도 같은 계보에 있다[15].

학습 과제의 성취를 판정하는 기준도 중요한 논점이다. 학습자가 입력한 명령 문자열이 정답과
일치하는지 확인하는 방식은 구현이 간단하지만, 같은 목표를 다른 명령이나 다른 순서로 달성한
경우를 오답으로 처리하고 정답 문자열의 암기를 유도한다. 시스템 관리 과제의 자동 채점을 다룬
연구들은 과제의 성취를 파일 하나가 아니라 운영체제 전체의 상태로 확인해야 한다는 문제의식
아래 실행 중인 가상머신의 상태를 검사하는 방향으로 발전해 왔다[16]. 앞서 언급한 실습
플랫폼들 역시 특정 명령의 입력이 아니라 과제가 요구하는 상태에 도달했는지를 기준으로 진행을
판정한다[12][14]. 본 연구는 이 최종 상태 기준의 판정을 가상 상태에 적용한다.

## 2.4 생성형 AI와 학습 지원 시스템

생성형 AI는 개념 설명, 오류 진단, 즉시 질의응답, 학습자 수준에 맞춘 설명 조정과 같은 기능을
통해 학습을 지원할 수 있다. 프로그래밍 교육 분야의 체계적 문헌고찰은 최근 연구 대부분이
생성형 AI를 다루고 있으며 실시간 학습 보조가 주요 기여로 보고된다고 정리하면서, 동시에
초보 학습자에게는 구조화된 안내가 필요하다는 점을 함께 지적한다[17]. ChatGPT를 활용한
프로그래밍 교육 연구들도 맞춤형 튜터링과 즉시 피드백, 오류 식별과 수정 제안에서 효과를
보고하는 한편, 과도한 의존과 비판적 사고 저하의 우려를 함께 제시한다[18][19]. 이는 정답을
바로 제시하기보다 단계적으로 안내하는 힌트 구조가 필요한 이유가 된다.

한편 생성형 AI를 학습에 활용할 때 가장 주의해야 할 문제는 응답의 정확성이다. 대규모
언어모델은 사실과 다른 내용을 그럴듯하게 생성하는 환각(hallucination) 문제를 가지고
있다[20]. 지능형 튜터링 시스템에 언어모델 피드백을 결합한 연구에서는 생성된 힌트 가운데
상당수가 지나치게 일반적이거나, 부정확하거나, 정답을 그대로 노출하는 문제를 보였다고
보고한다[21]. 또한 환각이 포함된 피드백이 학습자의 학습 성과와 혼란 정도, 과제 수행 시간,
시스템에 대한 신뢰에 부정적 영향을 준다는 실증 연구도 제시되어 있다[22]. 학습자는 대체로
설명의 옳고 그름을 스스로 판별할 능력이 부족한 상태이므로, 잘못된 설명은 일반 사용자보다
학습자에게 더 큰 피해를 준다.

이에 대한 대응으로 제시되는 방향은 언어모델이 판단해야 할 범위를 줄이는 것이다. 튜터링
시스템이 이미 확정한 구조화된 정보, 예컨대 기대하는 답이나 풀이 단계를 프롬프트에 함께
제공하면 모델이 정답을 추정할 필요가 없어져 사실 오류의 위험이 감소한다[21]. 환각 완화
기법을 정리한 연구도 외부 지식을 프롬프트에 주입하는 접근이 사실성 향상에 기여한다고
보고한다[20]. 따라서 학습 지원에 생성형 AI를 도입할 때에는 성취 판정과 같은 사실의 확정은
결정적인 규칙에 맡기고, 생성형 AI는 확정된 사실을 설명하는 역할에 한정하는 구조가 요구된다.
이것이 3장에서 제시하는 설계 원칙의 근거이다.

## 2.5 Amazon Bedrock

Amazon Bedrock은 여러 기업이 제공하는 파운데이션 모델을 하나의 API로 사용할 수 있게 하는
완전 관리형 서비스이다. 모델의 호스팅과 확장은 서비스 제공자가 담당하며, 응용 프로그램은
모델을 직접 운영하지 않고 API 호출로 사용한다. 모델 접근 권한은 AWS의 권한 관리 체계인
IAM으로 통제한다[23].

모델 호출 방식에는 모델별 고유 형식을 사용하는 `InvokeModel`과, 대화형 모델에 일관된
인터페이스를 제공하는 Converse API가 있다[23][24]. Converse API는 2024년 5월에 공개되었으며,
모델마다 다른 요청 형식과 파라미터의 차이를 흡수하여 한 번 작성한 코드로 여러 모델을 사용할
수 있도록 하고, 대화 이력을 구조화된 형태로 전달하도록 설계되었다[25][26]. 이는 사용하는
모델을 교체할 때 응용 프로그램의 변경 범위를 줄여 준다. 또한 공식 API 문서는 제공된 입력
콘텐츠를 저장하지 않고 응답 생성에만 사용한다고 명시하고 있다[24].

본 시스템이 Bedrock을 선택한 이유는 세 가지이다. 첫째, 모델을 직접 운영하지 않아도 되므로
학습 지원 기능의 설계와 구현에 집중할 수 있다. 둘째, 모델 접근 자격 증명을 별도로 관리하지
않고 클라우드의 권한 체계로 일원화할 수 있다. 셋째, 통합 대화 API를 사용하면 특정 모델에
대한 종속을 줄일 수 있다. 다만 모델 라인업과 리전별 지원 범위는 수시로 변경되므로, 본 논문에
기술한 내용은 문서 확인 시점을 기준으로 한다.

## 2.6 기존 연구와의 차별성

앞 절에서 살펴본 연구와 도구는 각각 서버 상태의 시각화, 실제 실행 기반의 실습 환경, 생성형
AI를 활용한 학습 피드백이라는 서로 다른 축에서 발전해 왔다. 본 연구는 이 세 축을 초보
학습자를 대상으로 하나의 시스템에 통합하되, 판정과 설명의 역할을 분리했다는 점에서 차이를
가진다.

| 구분 | 기존 연구·도구 | 본 연구 |
|---|---|---|
| 서버 상태의 제시 | 지표 수집과 대시보드 시각화가 목적이며 값의 의미는 설명하지 않음[4][5][6][7] | 상태 시각화와 자연어 설명, 학습 지원을 하나의 시스템으로 결합 |
| 대상 사용자 | 운영 전문가를 전제한 구성과 용어[4][5] | 초보 학습자를 전제한 설명 중심 구성 |
| 실습 방식 | 격리된 실제 환경에서 명령을 실행[12][13][14] | 명령을 실행하지 않고 가상 상태를 전이시켜 실습을 구성하고, 실제 실행 경험은 별도의 격리된 터미널로 보완 |
| 성취 판정 | 명령 문자열 일치 또는 실행 중인 시스템의 상태 검사[16] | 최종 가상 상태를 기준으로 판정하여, 명령이 달라도 같은 목표 상태에 도달하면 인정 |
| 생성형 AI의 역할 | 모델이 피드백의 내용과 정오 판단을 함께 생성[21][22] | 판정은 서버의 규칙이 수행하고, 생성형 AI는 확정된 결과의 설명만 담당 |

[표 2-3] 기존 연구·도구와 본 연구의 차이

특히 마지막 두 항목은 2.3절과 2.4절에서 정리한 선행 연구의 문제의식을 그대로 반영한 것이다.
최종 상태 기준의 판정은 정답 문자열의 암기를 피하기 위한 것이고, 판정과 설명의 역할 분리는
생성형 AI의 환각이 학습자에게 잘못된 성취 판단으로 전달되는 것을 막기 위한 것이다. 다음
장에서는 이러한 배경 위에서 설계한 시스템의 구조를 설명한다.
