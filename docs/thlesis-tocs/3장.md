# 3. 시스템 설계

본 장에서는 제안 시스템의 설계를 기술한다. 2장에서 정리한 문제의식, 즉 초보 학습자가
실제 서버를 조작하다 발생하는 위험과 기존 모니터링 도구가 상태를 보여줄 뿐 그 의미를
설명하지 않는다는 한계를 설계 수준에서 어떻게 다루었는지를 중심으로 서술한다.

설계 전반을 관통하는 원칙은 두 가지다. 첫째, **판정의 권한은 서버가 갖는다.** 학습자의
성취 여부와 시스템 상태는 결정적인 규칙으로 서버가 계산하며, 생성형 AI는 이미 확정된
값을 설명할 뿐 그 값을 만들거나 바꾸지 못한다. 둘째, **AI 학습 기능의 실습은 실제
시스템에 도달하지 않는다.** 학습자가 학습 화면에서 입력한 명령은 호스트에서도 컨테이너
에서도 실행되지 않고, 서버 내부의 가상 상태를 전이시키는 입력으로만 사용된다. 실제 명령을
실행해 보는 경험은 이와 분리된 웹 터미널이 격리된 컨테이너 안에서 제공하며, 두 기능의
관계는 3.7.3절에서 다룬다. 이 두 원칙이 이후 각 절의 설계 판단을 결정한다.

## 3.1 전체 시스템 구조

시스템은 브라우저에서 동작하는 프론트엔드, 요청을 중계하는 리버스 프록시, 응용 로직을
담당하는 백엔드, 상태를 보관하는 데이터베이스, 그리고 외부 언어모델 서비스로 구성된다.
전체 구조는 [그림 3-1]과 같다.

```
                        브라우저 (React 18 + Vite)
                                  │
                                  │ HTTPS
                                  ▼
                        ┌───────────────────┐
                        │       Nginx       │  TLS 종료, 정적 파일 서빙,
                        └─────────┬─────────┘  보안 헤더, 요청 수 제한
                                  │
                   /api/* (REST)  │  /ws/* (WebSocket)
                                  ▼
                        ┌───────────────────┐
                        │ FastAPI + Uvicorn │  내부 포트만 사용
                        └─────────┬─────────┘  (호스트에 직접 공개하지 않음)
                                  │
        ┌─────────────────────────┼─────────────────────────┐
        ▼                         ▼                         ▼
┌───────────────┐    ┌─────────────────────┐    ┌──────────────────────┐
│    SQLite     │    │  가상 상태 엔진      │    │   Amazon Bedrock     │
│  사용자·이력  │    │  규칙 기반 채점기    │    │  (설명 텍스트 생성)   │
│  학습 세션    │    │  (결정적, 서버 내부) │    └──────────────────────┘
└───────────────┘    └─────────────────────┘
        │
        ▼
┌──────────────────────┐    ┌──────────────────────┐
│  docker-socket-proxy │───▶│    셸 컨테이너        │
│  (제한된 Docker API) │    │  network: none        │
└──────────────────────┘    │  read-only rootfs     │
                            │  cap-drop ALL         │
                            └──────────────────────┘
```

**[그림 3-1] 전체 시스템 구조**

브라우저는 Nginx하고만 통신하며, 백엔드 포트는 호스트에 공개하지 않는다. Nginx는 TLS를
종료하고 경로에 따라 REST 요청과 WebSocket 연결을 백엔드로 전달한다. 백엔드는 호스트의
Docker 소켓에 직접 접근하지 않고 필요한 API만 노출하는 프록시를 거친다. 이는 웹 터미널
기능이 침해되더라도 그 영향이 호스트 전체로 확대되지 않도록 하기 위한 구조적 제약이며,
자세한 격리 정책은 3.7절에서 다룬다.

데이터 흐름은 기능에 따라 세 갈래로 나뉜다. 첫째는 **모니터링 경로**로, 호스트에서 수집한
실제 자원 사용량이 WebSocket과 REST를 통해 브라우저로 전달된다. 둘째는 **학습 경로**로,
학습 화면에서 입력한 명령이 서버 내부의 가상 상태를 전이시키고 그 결과가 규칙 기반으로
채점된 다음, 확정된 가상 상태와 채점 결과가 프롬프트로 변환되어 언어모델에 전달되고
자연어 설명이 되돌아온다. 이 경로 안에서 판정은 서버가, 설명은 언어모델이 맡으며 그 순서는
역전되지 않는다. 설명 단계는 채점 단계에 의존하지만 그 역은 성립하지 않으므로, 언어모델
호출이 실패하더라도 상태 전이와 채점은 그대로 성립한다. 설명의 대상은 가상 실습 상태이며,
모니터링 경로에서 수집한 호스트의 자원 사용량은 프롬프트에 포함하지 않고 모니터링 화면에서
직접 제시한다. 셋째는 **실행 경로**로, 웹 터미널에 입력한 명령이 호스트가 아니라 격리된
셸 컨테이너 안에서 실제로 실행된다. 이 경로는 앞의 두 경로와 상태를 공유하지 않는다.

시스템이 관리하는 영속 데이터는 [표 3-1]과 같이 8개 테이블로 구성된다.

| 구분 | 테이블 | 저장 내용 |
|---|---|---|
| 모니터링 | `monitor_snapshots` | 주기적으로 저장한 자원 사용량 스냅샷 |
| 인증 | `web_users` | 계정, 비밀번호 해시, 역할, 활성 여부 |
| 인증 | `login_logs` | 로그인 시도 이력(감사 로그) |
| 학습 | `ai_learning_sessions` | 학습 세션, 현재 시나리오와 문제, 학습자 수준 |
| 학습 | `ai_virtual_states` | 세션별 가상 Linux 상태 |
| 학습 | `ai_command_attempts` | 명령 시도 이력, 실행 결과 코드, 참고용 설명 |
| 학습 | `ai_chat_messages` | 질의응답 대화 이력 |
| 학습 | `ai_interaction_audits` | 채점·힌트 등 상호작용 감사 기록 |

**[표 3-1] 데이터베이스 테이블 구성**

모니터링 계열과 학습 계열을 분리한 이유는 두 데이터의 수명과 성격이 다르기 때문이다.
모니터링 스냅샷은 시간이 지나면 가치가 떨어지고 양이 계속 늘어나므로 보존 기간을 두고
자동으로 삭제한다(3.2절). 반면 학습 이력은 학습자별 피드백의 근거가 되므로 세션 단위로
유지한다(3.5절).

## 3.2 서버 상태 데이터 수집 구조

### 3.2.1 수집 대상

수집 대상은 학습자가 서버 운영에서 처음 마주하는 네 가지 자원이다. CPU는 전체 사용률,
코어별 사용률, 물리 코어 수, 부하 평균(load average)을 수집한다. 메모리는 전체·사용·여유
용량에 더해 buffers와 cached를 별도 항목으로 수집한다. 초보 학습자는 캐시가 점유한
메모리를 부족 상태로 오해하기 쉬운데, 수집 단계에서 이를 합산해 버리면 이후 어떤 계층에서도
둘을 구분할 수 없다. 따라서 표시 여부와 무관하게 수집·저장 단계에서는 구분을 보존하도록
했다. 디스크는 파티션별 용량과 사용률을, 네트워크는 인터페이스
정보, 초당 트래픽, 패킷 통계, 연결 상태를 수집한다. 여기에 프로세스 목록을 더해 자원을
소비하는 주체를 함께 보여준다.

### 3.2.2 단일 수집기와 공유 fan-out

수집 구조에서 가장 중요한 설계 판단은 **수집 주체를 하나로 고정한 것**이다. 접속한
사용자마다 또는 WebSocket 연결마다 자원을 수집하면, 연결 수에 비례해 수집 횟수가 늘고
모니터링 도구 자체가 관측 대상 서버의 부하가 된다. 학습용 시스템은 여러 학습자가 동시에
접속하는 상황을 전제하므로 이 문제를 피해야 한다.

이를 위해 하나의 백그라운드 수집기가 일정 주기로 스냅샷 한 개를 만들고, 모든 소비자가
그 최신 스냅샷을 공유받는 구조를 택했다. 소비자는 수집을 요청하지 않고 갱신을 기다리며,
수집이 끝나면 대기 중인 모든 소비자가 함께 깨어난다. 이 구조에서 수집 횟수는 연결 수와
무관하게 주기에만 의존한다.

```
                 ┌──────────────────────────┐
   (주기마다 1회) │   백그라운드 수집기       │
        ─────────▶│   snapshot 생성·교체      │
                 └────────────┬─────────────┘
                              │ 갱신 통지(공유 스냅샷)
          ┌───────────────────┼───────────────────┐
          ▼                   ▼                   ▼
   WebSocket 연결 1    WebSocket 연결 2    저장 스케줄러
```

**[그림 3-2] 단일 수집기와 공유 fan-out 구조**

자원 수집 함수는 CPU 사용률 측정처럼 일정 시간 블로킹되는 호출을 포함한다. 이를 그대로
비동기 이벤트 루프에서 호출하면 측정 시간 동안 다른 요청 처리가 멈춘다. 따라서 블로킹
호출은 별도 스레드로 옮겨 실행하고, 이벤트 루프는 그동안 다른 연결을 처리하도록 했다.

수집이 실패하는 경우에도 스트림 자체는 끊지 않는다. 수집 함수는 예외를 기록한 뒤 0으로
채운 기본 스냅샷을 반환하며, 주기 루프는 한 번의 실패로 종료되지 않고 다음 주기를
계속한다. 일시적인 수집 실패가 전체 모니터링 중단으로 이어지지 않게 하기 위한 설계다.

### 3.2.3 이력 저장과 보존 기간

실시간 스트림과 별개로, 스케줄러가 일정 간격마다 최신 스냅샷을 데이터베이스에 저장해
자원 사용 추이를 남긴다. 이때도 스케줄러는 직접 수집하지 않고 공유 스냅샷을 재사용하므로,
이력 저장 기능이 추가되었다고 해서 수집 횟수가 늘지 않는다.

스냅샷은 시간이 지날수록 단조 증가하므로 보존 기간을 두었다. 별도의 정리 작업이 주기적
으로 실행되어 보존 기간이 지난 원본 스냅샷을 일괄 삭제한다. 삭제는 행을 하나씩 조회해
지우지 않고 단일 질의로 처리하며, 경계 시각과 정확히 같은 레코드는 보존하도록 엄격한
부등호를 사용해 경계에서의 동작을 명확히 했다.

## 3.3 백엔드 및 데이터 전달 구조

### 3.3.1 전달 방식의 분리

백엔드는 데이터의 성격에 따라 전달 방식을 나눈다. 지속적으로 변하며 즉시성이 중요한
데이터는 WebSocket으로 밀어 보내고, 요청 시점의 값이나 조회 조건이 필요한 데이터는 REST로
제공한다. [표 3-2]는 그 구분을 정리한 것이다.

| 방식 | 대상 | 성격 |
|---|---|---|
| WebSocket `/ws/monitor` | CPU·메모리·상위 프로세스 스냅샷 | 주기적 푸시, 연결 유지 |
| WebSocket `/ws/shell` | 웹 터미널 입출력 | 양방향 스트림 |
| REST `/api/monitor/*` | CPU, 메모리, 디스크, 이력 | 요청·응답, 조회 조건 필요 |
| REST `/api/network/*` | 인터페이스, 트래픽, 패킷, 연결 | 요청·응답 |
| REST `/api/ai/sessions/*` | 학습 세션, 명령, 채점, 힌트, 대화 | 상태 변경을 동반하는 요청 |
| REST `/api/admin/*` | 사용자 관리, 감사 로그 | 관리자 전용 |

**[표 3-2] 데이터 전달 방식의 분리**

학습 기능을 WebSocket이 아닌 REST로 설계한 것은 의도적이다. 명령 실행과 채점은 서버의
상태를 바꾸는 조작이므로, 요청 하나에 결과 하나가 대응하고 실패 시 상태 코드로 원인을
구분할 수 있어야 한다. 또한 각 요청이 독립적이어야 재시도와 감사 기록이 단순해진다.

### 3.3.2 가공과 전달

백엔드는 수집한 원시 값을 그대로 내보내지 않고 화면이 바로 사용할 수 있는 형태로
가공한다. 바이트 단위 메모리 값은 기가바이트로 환산해 소수점 이하를 정리하고, 네트워크
누적 바이트는 이전 값과의 차이를 시간으로 나눠 초당 전송량으로 변환한다. 프로세스 목록은
자원 사용량 기준으로 정렬해 상위 일부만 전달한다. 이렇게 하는 이유는 두 가지다. 하나는
브라우저의 계산 부담과 전송량을 줄이는 것이고, 다른 하나는 단위 환산과 속도 계산을 서버
한 곳에 모아 표현을 통일하는 것이다. 후자가 없으면 같은 자원을 쓰는 화면마다 계산이 따로
들어가 표시 값이 어긋날 수 있다.

응답 형식은 스키마로 명시해 검증한다. 수집 실패로 값이 없는 경우에도 형식을 유지한 채
실패를 표현하므로, 프론트엔드는 응답 형태를 매번 분기하지 않고 표시 상태만 전환한다.

## 3.4 프론트엔드 구조

### 3.4.1 화면 구성

프론트엔드는 컴포넌트 기반 단일 페이지 애플리케이션으로 구성했다. 공통 레이아웃과
사이드바가 화면 전환을 담당하고, 각 기능은 독립된 페이지로 분리된다. 페이지는 성격에 따라
세 묶음으로 나뉜다. 실제 서버 상태를 보여주는 모니터링 화면(대시보드, 네트워크, 프로세스),
학습자가 직접 조작하는 실습 화면(웹 터미널, 파일 탐색기, AI 학습), 그리고 관리자 전용
화면(사용자 관리, 감사 로그)이다.

권한이 필요한 페이지는 보호된 경로로 감싸 비인가 접근 시 로그인 화면으로 보낸다. 다만 이
처리는 사용자 경험을 위한 것이며 권한의 근거가 아니다. 권한은 모든 요청에 대해 서버가
다시 판정하며, 프론트엔드의 화면 제어는 표시 목적으로만 사용된다. 이 원칙은 3.7절에서
다시 다룬다.

### 3.4.2 상태 표현과 연결 상태의 가시화

자원 사용률의 시간에 따른 변화는 꺾은선 그래프로, 사용량 대비 여유는 비율 막대와 수치를
함께 써서 표현해 학습자가 "지금 값"과 "변화 추세"를 함께 읽도록 했다. 대시보드는 사용률,
사용량 대비 전체 용량, 여유 용량을 한 화면에 배치해 같은 자원을 세 가지 관점으로 동시에
보게 한다.

실시간 화면에서 중요한 설계 요소는 **연결 상태를 숨기지 않는 것**이다. WebSocket이 끊기면
화면의 숫자는 마지막으로 받은 값에서 멈추는데, 이때 아무 표시가 없으면 학습자는 정지된
과거 값을 현재 상태로 오인한다. 이는 학습 상황에서 잘못된 판단으로 이어지므로, 별도
컴포넌트가 연결 여부를 항상 화면에 노출하고 재연결 상태를 알린다.

같은 맥락에서 시뮬레이션 기반 화면은 그것이 시뮬레이션임을 화면에 항상 표시한다.
학습자가 가상 결과를 실제 서버의 상태로 오해하지 않도록 하기 위한 조치다.

### 3.4.3 AI 학습 인터페이스

AI 학습 화면은 하나의 화면 안에 문제 제시, 명령 입력, 상태 표시, 설명 영역을 함께 둔다.
학습자가 명령을 입력하면 그 결과로 바뀐 가상 상태와 채점 결과가 같은 화면에서 갱신되고,
자연어 설명이 이어 붙는다. 학습 중 생긴 의문을 별도 도구로 옮겨 가지 않고 그 자리에서
질문할 수 있게 하는 것이 이 배치의 목적이다.

화면은 규칙 기반으로 확정된 정보(상태, 채점 결과, 힌트)와 언어모델이 생성한 설명을 구분해
표시한다. 언어모델 호출이 실패한 경우에도 앞의 정보는 그대로 표시되며, 설명 영역만 대체
안내로 바뀐다.

## 3.5 생성형 AI 연동 구조

### 3.5.1 모델 선택과 호출 방식

설명 생성에는 Amazon Bedrock을 사용한다. 관리형 서비스를 택한 이유는 모델 자체를 직접
운영하지 않고 자격 증명과 접근 권한을 클라우드의 권한 체계로 관리할 수 있기 때문이다.
호출은 모델별 고유 형식 대신 통합 대화 API를 사용해, 모델을 교체하더라도 호출 코드의
변경 범위가 좁아지도록 했다.

언어모델을 호출하는 지점은 학습자의 질문, 힌트 요청, 그리고 시뮬레이터가 처리하지 못한
명령에 대한 설명 요청 세 곳이다. 명령 처리와 채점은 언어모델을 호출하지 않고 서버
내부에서만 수행하며, 명령 실행 결과의 출력 역시 결정적인 시뮬레이터가 생성한다. 호출
지점을 좁힌 것은 설명이 필요한 순간에만 모델을 사용하고, 학습의 필수 경로가 외부 서비스의
가용성에 묶이지 않게 하기 위해서다.

세 지점은 모두 규칙으로 결정된 사실이 확정된 뒤에 호출된다. 질문과 힌트 요청에서는 채점
결과가 먼저 확정되고, 설명 요청에서는 입력이 처리되지 않았다는 사실과 그 시점의 가상
상태가 먼저 확정된다. 설명 요청은 명령의 결과 코드가 성공이 아닐 때만 사용하며, 생성된
설명은 화면에 표시하고 시도 기록에 남길 뿐 가상 상태와 채점에는 관여하지 않는다. 명령
처리 경로 자체에 모델을 넣지 않고 처리 이후의 별도 요청으로 분리한 이유가 여기에 있다.
실습의 상태 전이는 모델의 응답 여부와 무관하게 완결되어야 하기 때문이다.

호출 파라미터는 [표 3-3]과 같이 고정한다.

| 항목 | 값 | 근거 |
|---|---|---|
| 최대 출력 토큰 | 1,024 | 설명 길이를 학습 화면에 맞게 제한 |
| temperature | 0.1 | 같은 상태에 대해 설명이 크게 흔들리지 않도록 낮게 고정 |
| 연결 타임아웃 | 3초 | 응답 없는 호출이 화면을 오래 붙잡지 않도록 제한 |
| 응답 타임아웃 | 20초 | 위와 같음 |
| 최대 시도 횟수 | 2 | 일시적 오류만 한 번 더 시도 |

**[표 3-3] 언어모델 호출 파라미터**

재시도는 오류를 분류한 뒤에만 수행한다. 처리량 초과나 일시적 서버 오류처럼 다시 시도할
가치가 있는 오류는 짧은 대기 후 한 번 더 호출하고, 권한 없음이나 요청 형식 오류처럼
재시도해도 결과가 같은 오류는 즉시 중단한다. 구분 없이 재시도하면 실패가 확정된 요청에
비용과 지연만 더해지기 때문이다.

### 3.5.2 상태의 프롬프트 변환

프롬프트는 자연어 문장에 값을 끼워 넣는 방식이 아니라, 확정된 데이터를 구조화된 형식으로
담아 전달하는 방식으로 구성한다. 전달되는 항목은 학습자 수준, 문제 정의, 현재 가상 상태
요약, 서버가 확정한 채점 결과, 학습자 질문, 최근 대화, 그리고 학습 이력이다.

여기서 채점 결과를 **확정된 사실로 함께 전달하는 것**이 이 설계의 핵심이다. 언어모델에게
성취 여부를 판단하게 하지 않고, 이미 규칙으로 결정된 판정을 주면서 그것을 설명하도록
역할을 한정한다. 프롬프트의 지시문은 상태와 채점 결과가 변경 불가능한 사실임을 명시하고,
모델이 명령을 실제로 실행했다고 주장하거나 판정을 뒤집는 것을 금지한다.

학습자가 입력한 내용과 이전 대화처럼 신뢰할 수 없는 텍스트는 지시문과 섞이지 않도록
별도의 데이터 구획 안에 넣고, 그 구획의 내용을 지시가 아닌 인용된 데이터로 취급하라고
명시한다. 학습자가 프롬프트를 조작하려는 문장을 입력하더라도 그것이 시스템의 지시로
해석되지 않게 하기 위한 구조다. 아울러 학습자 입력, 문제 정의, 상태 요약, 전체 프롬프트에
각각 길이 상한을 두어 과도한 입력이 호출 비용과 오류로 이어지지 않도록 제한했다.

처리하지 못한 명령에 대한 설명 요청은 별도의 프롬프트를 사용한다. 전달 항목은 학습자
수준, 문제 정의, 명령 실행 직전의 가상 상태, 명령 문자열, 그리고 입력이 거부된 유형이며,
채점 결과는 포함하지 않는다. 이 요청의 목적이 성취 여부를 설명하는 것이 아니라 입력이
처리되지 않은 이유를 알리는 것이기 때문이다.

거부 유형은 두 가지로 나눈다. 셸 메타문자를 포함해 시뮬레이터가 언제나 거부하는 입력과,
문법은 정상이지만 현재 문제에서 지원하지 않는 입력이다. 두 유형에 서로 다른 지시문을
붙이는데, 전자에는 실행 결과를 지어내지 말고 거부 이유만 설명하도록 지시하고, 후자에는
거부 사유가 명령 이름 때문인지 인자 때문인지 서버가 알려주지 않았음을 명시한 뒤 구체적인
기술적 사유를 단정하지 말도록 지시한다. 후자의 지시는 **서버가 알려주지 않은 사실을
모델이 스스로 메우려 할 때 그럴듯한 오답이 생긴다**는 점을 고려한 것이다. 프롬프트 설계에서
무엇을 전달할지 못지않게 무엇을 단정하지 못하게 할지가 함께 필요하다는 의미다.

### 3.5.3 응답 검증과 실패 처리

모델의 응답은 그대로 사용하지 않고 정해진 스키마로 검증한 뒤에만 화면에 전달한다.
허용하는 필드는 터미널 출력 예시, 설명, 힌트 단계, 추천 개념 네 가지이며, 정의되지 않은
필드가 있으면 응답 전체를 거부한다. 응답 형식은 하나의 JSON 객체이거나 하나의 코드 블록
안에 담긴 JSON 객체만 인정하고, 텍스트에서 중괄호를 찾아 추출하는 식의 관대한 해석은
사용하지 않는다. 형식이 어긋난 응답을 억지로 해석하면 의미가 왜곡된 채 학습자에게
전달되기 때문이다.

설명 요청 경로에는 다른 방식의 검증을 적용했다. 응답 형식을 프롬프트 문장으로 요청하는
대신 호출 자체에 도구 정의를 붙이고 모델이 반드시 그 도구를 호출하도록 지정하는 방식이다.
도구의 입력 스키마에는 화면에 표시할 문자열 하나만 정의되어 있고 정의되지 않은 필드는
허용하지 않으므로, 모델이 만들어 낼 수 있는 값이 그 문자열 하나로 한정된다. 앞의 방식이
형식 준수를 모델의 협조에 의존하는 것과 달리, 이 방식은 형식을 호출 규약의 제약으로
옮긴다. 다만 이 방식은 나중에 추가한 설명 요청 경로에만 적용했고 질문·힌트 경로는 기존
방식을 유지하고 있다(6.2절).

검증을 통과하지 못했거나 호출 자체가 실패한 경우에는 예외를 화면으로 올리지 않고,
**성능 저하 상태(degraded)를 명시한 대체 응답**을 반환한다. 대체 응답은 실패 사유 코드와
재시도 가능 여부를 함께 담으며, 학습자에게는 규칙 기반 안내로 대체되었음을 알리는 고정
문구를 표시한다. 이 설계에 따라 언어모델을 사용할 수 없는 상황에서도 문제 제시, 명령
실행, 채점, 규칙 기반 힌트는 정상적으로 동작한다. 즉 **AI는 학습 흐름의 필수 경로가
아니라 설명을 덧붙이는 계층**이다.

호출량은 사용자 단위로 제한한다. 한 사용자의 요청이 동시에 두 건 이상 진행되지 않도록
하고, 직전 호출이 끝난 뒤 짧은 대기 시간을 두어 연속 호출을 막는다. 세 호출 지점이 같은
제한기를 공유하므로 자동으로 발생하는 설명 요청도 학습자의 질문·힌트 요청과 같은
상한 안에서 처리된다.

제한에 걸렸을 때의 처리는 요청의 성격에 따라 다르다. 학습자가 직접 보낸 질문과 힌트
요청에는 재시도까지 남은 시간을 알리는 오류로 응답해 학습자가 다시 시도할 수 있게 한다.
반면 화면이 자동으로 보내는 설명 요청은 학습자가 재시도할 방법이 없으므로 오류를 돌려주지
않고 대체 응답으로 조용히 처리한다. 요청을 누가 보냈는지에 따라 실패를 알릴 대상이
있는지가 달라지기 때문이다.

호출 기록은 운영 점검을 위해 남기되, 프롬프트 본문과 모델 응답 원문, 학습자 입력은 남기지
않는다. 대신 프롬프트를 해시한 짧은 식별자와 지연 시간, 시도 횟수, 실패 사유만 기록해
동일 요청 여부는 추적하면서 내용은 노출되지 않게 했다.

## 3.6 가상 Linux 상태 엔진 및 채점 구조

### 3.6.1 실행하지 않는 실습

AI 학습 화면에서 학습자가 입력한 명령은 어떤 계층에서도 실제로 실행되지 않는다. 명령은
서버 내부에 보관된
가상 상태를 전이시키는 입력으로만 사용되며, 상태는 서비스, 사용자, 파일 소유권과 권한,
방화벽 규칙, 열린 포트, 패키지, 원격 접속 가능 여부 같은 항목을 담은 구조화된 데이터다.

이 방식을 택한 이유는 2장에서 정리한 실습 환경의 비용·안전성 문제 때문이다. 학습자마다
가상 머신이나 컨테이너를 할당하면 자원 비용이 크고, 잘못된 명령이 환경을 복구 불가능한
상태로 만들 수 있다. 반면 상태 전이만 다루면 학습자별 환경은 데이터 한 건이고, 초기화는
초기 상태를 다시 쓰는 것으로 끝난다. 무엇보다 서비스 중지나 방화벽 차단처럼 **실제로
실행하면 위험한 명령을 학습 소재로 안전하게 다룰 수 있다.**

### 3.6.2 명령 해석과 거부 문법

명령 처리는 [그림 3-3]의 순서를 따른다.

```
   입력 명령
      │
      ▼
 ┌──────────────────┐  셸 메타문자 포함?  ──── 예 ──▶ unsupported_syntax
 │  구문 검사        │                                (상태 변경 없음)
 └────────┬─────────┘
          │ 아니오
          ▼
 ┌──────────────────┐  허용 목록에 있는가? ─── 아니오 ─▶ unsupported_syntax
 │  허용 목록 대조   │  인자 형태가 맞는가?             (상태 변경 없음)
 └────────┬─────────┘
          │ 예
          ▼
 ┌──────────────────┐  적용 규칙이 있는가? ─── 아니오 ─▶ unsupported_syntax
 │  상태 전이 적용   │                                 (상태 변경 없음)
 └────────┬─────────┘
          │ 예
          ▼
   전이된 상태 + 출력
```

**[그림 3-3] 명령 해석과 상태 전이 흐름**

구문 검사 단계에서는 명령 연결(`;`, `&&`, `||`), 파이프, 명령 치환, 리다이렉션 같은 셸
메타문자를 포함한 입력을 먼저 거부한다. 이어 명령 이름을 허용 목록과 대조하고, 허용된
명령이라도 인자의 형태를 개별적으로 검증한다. 예를 들어 목록 조회 명령은 절대 경로 인자
하나만 허용하고, 포트 확인 명령은 정해진 형태의 옵션 문자열만 허용한다. 허용 목록 방식을
택한 것은, 금지 목록은 새로운 우회 표현이 나타날 때마다 항목을 추가해야 하지만 허용 목록은
정의된 것 외에는 모두 거부되기 때문이다.

여기서 중요한 설계 규칙은 **거부된 입력이 상태를 바꾸지 않는다**는 점이다. 명령 처리는
상태의 사본 위에서 수행되고, 구문이 지원되지 않거나 적용할 규칙이 없으면 전이 이전 상태를
그대로 반환한다. 따라서 학습자가 지원하지 않는 명령을 입력해도 진행 중이던 실습 상태가
훼손되지 않으며, 같은 입력은 언제나 같은 결과를 만든다.

### 3.6.3 최종 상태 기준 채점

채점은 학습자가 특정 명령 문자열을 입력했는지가 아니라, **명령 처리 후의 최종 가상 상태가
목표 상태를 충족하는지**로 판정한다. 이 판단이 제안 시스템의 학습 설계에서 가장 중요한
선택이다. 명령 문자열을 대조하는 방식은 정답 명령을 암기하게 만들지만, 최종 상태를 보는
방식은 서로 다른 경로로 같은 결과에 도달한 시도를 모두 정답으로 인정한다. 실제 서버 운영
에서도 같은 목표에 이르는 방법은 여러 가지이므로, 후자가 학습 목표에 부합한다.

판정은 성공, 부분 성공, 실패 순서로 규칙을 대조해 처음 일치하는 결과를 채택한다. 규칙은
세 가지 조건을 조합해 기술한다. 반드시 만족해야 하는 상태 조건, 여러 후보 중 하나만
만족하면 되는 상태 조건, 그리고 특정 명령 계열을 사용한 적이 있는지를 보는 조건이다.
마지막 조건은 진단 학습처럼 상태 변화 없이 확인 행위 자체가 학습 목표인 경우에 사용한다.

부분 성공을 별도 등급으로 둔 것은 피드백의 해상도를 위해서다. 예를 들어 서비스를 실행
상태로 만들었으나 자동 시작 설정을 하지 않은 경우, 이를 단순 실패로 처리하면 학습자는
무엇이 부족한지 알 수 없다. 부분 성공은 방향은 맞되 조건 하나가 남았음을 알리는 신호로
기능한다.

성공한 규칙에 도달하지 못했고 알려진 실패 조건에도 해당하지 않는 상태는 실패로 처리하되,
일치한 조건 기록은 비워 둔다. 근거 없는 판정 사유를 만들어내지 않기 위한 처리다.

### 3.6.4 채점과 학습 진행의 분리

채점기는 등급 판정만 담당하고, 다음에 어떤 문제를 낼지, 힌트를 어느 단계까지 열지,
학습 진도를 어떻게 갱신할지는 별도 모듈이 담당한다. 두 책임을 분리한 이유는 판정 규칙과
학습 정책의 변경 주기가 다르기 때문이다. 문제를 추가하거나 진행 방식을 바꾸는 일은
빈번하지만, 상태 판정 규칙은 그보다 안정적이다.

학습 진행 정책은 다음과 같다. 문제는 미완료 문제 중 첫 번째를 선택하며 무작위나 모델
판단에 맡기지 않는다. 성공한 경우에만 다음 문제로 넘어가고, 그렇지 않으면 같은 문제에
머문다. 힌트는 개념, 명령 계열, 구문의 세 단계로 구성되며, 실패할 때마다 다음 단계를
제안하되 최대 단계를 넘지 않는다. 처음부터 구문을 알려주면 학습자가 스스로 판단할 기회가
사라지므로, 단계를 나누어 필요한 만큼만 열도록 했다. 커리큘럼의 마지막 순서는 복습
라운드로, 앞서 완료한 문제 중 하나를 다시 제시한다. 이때 선택은 세션 식별자를 기준으로
이루어져 같은 세션에서는 반복 조회해도 같은 문제가 유지된다.

문제, 초기 상태, 목표 상태, 채점 규칙, 힌트는 코드가 아니라 외부 정의 파일에 둔다. 학습
내용을 추가하거나 수정할 때 판정 로직을 건드리지 않아도 되며, 같은 정의 파일을 테스트의
입력과 기대값으로도 사용할 수 있다.

## 3.7 인증 및 실습 환경 격리 설계

### 3.7.1 인증과 권한

인증은 토큰 기반으로 설계했다. 로그인에 성공하면 만료 시간이 포함된 토큰을 발급하고,
이후 요청은 인증 헤더로 이를 전달한다. 비밀번호는 단방향 해시로만 저장한다. 토큰 서명
키는 환경변수로 주입하며, 값이 없거나 널리 알려진 예시 값이면 애플리케이션이 시작되지
않는다. 기본값을 두면 배포 환경에서 그대로 남을 위험이 있으므로, 설정 누락을 실행 중
오류가 아니라 기동 실패로 드러내는 편이 안전하다고 판단했다.

권한은 일반 사용자와 관리자로 구분하며, **판정은 전적으로 서버에서 수행한다.** 프론트엔드
의 메뉴 노출이나 경로 보호는 표시 목적일 뿐 권한의 근거가 아니다. 요청마다 토큰을 검증
하고 데이터베이스에서 사용자의 현재 상태와 역할을 다시 조회하므로, 토큰 발급 이후 계정이
비활성화되거나 역할이 바뀐 경우에도 즉시 반영된다.

응답 코드는 원인을 구분해 사용한다. 인증 정보가 없거나 유효하지 않거나 계정이 비활성화된
경우는 인증 실패로, 인증은 되었으나 역할이 부족한 경우는 권한 부족으로 응답한다. 특히
비활성 계정을 권한 부족이 아닌 인증 실패로 처리하는데, 프론트엔드가 인증 실패에서만
세션을 정리하기 때문이다. 이를 권한 부족으로 응답하면 비활성화된 사용자의 화면이 토큰
만료 시점까지 남는다.

### 3.7.2 WebSocket 인증

WebSocket은 요청 헤더를 자유롭게 지정하기 어려워 접속 주소에 토큰을 실어 보내는 방식이
흔히 쓰이지만, 주소는 서버 접근 로그와 프록시 로그, 브라우저 기록에 남는다. 본 시스템은
이를 피하기 위해 [그림 3-4]와 같은 일회용 티켓 방식을 사용한다.

```
  1) 클라이언트 ── REST(인증 헤더) ──▶ 용도별 티켓 발급 요청
  2) 서버      ── 짧은 수명의 일회용 티켓 발급 (저장하지 않음, 캐시 금지)
  3) 클라이언트 ── WebSocket 연결 (주소에 인증 정보 없음)
  4) 클라이언트 ── 첫 메시지로만 티켓 전송
  5) 서버      ── 티켓을 원자적으로 1회 소비 → 사용자 활성 상태·역할 재확인
  6) 인증 성공 후에만 데이터 전송 또는 입력 처리 시작
```

**[그림 3-4] WebSocket 일회용 티켓 인증 절차**

티켓은 짧은 수명을 가지며 한 번 사용하면 즉시 소멸한다. 용도가 구분되어 있어 모니터링용
티켓으로 터미널에 접속할 수 없다. 서버는 접속 주소에 인증 관련 항목이 포함되어 있으면
연결 수립 이전에 거부하고, 연결 수립 후에도 첫 메시지가 정해진 시간 안에 도착하지 않으면
연결을 종료한다. 인증이 끝나기 전에는 어떤 데이터도 전송하지 않고 어떤 입력도 처리하지
않는다.

### 3.7.3 웹 터미널 샌드박스 격리

웹 터미널은 실제 셸을 제공하므로 시스템에서 가장 위험한 기능이다. 따라서 호스트가 아니라
매 세션마다 생성되는 격리된 컨테이너에서 실행하며, 그 컨테이너에 [표 3-4]의 제약을
적용한다.

| 제약 | 목적 |
|---|---|
| 네트워크 없음 | 외부로의 접속과 내부 망 탐색을 차단 |
| 읽기 전용 루트 파일시스템 | 시스템 영역 변조 방지 |
| 모든 커널 권한(capability) 제거 | 권한이 필요한 조작 자체를 불가능하게 함 |
| 권한 상승 금지 | setuid 등을 통한 상승 경로 차단 |
| 비특권 사용자로 실행 | 관리자 권한으로 셸이 뜨지 않도록 함 |
| 쓰기 가능 임시 영역에 실행 금지 옵션 | 임시 디렉터리를 이용한 바이너리 실행 차단 |
| 메모리·CPU·프로세스 수 상한 | 자원 고갈로 인한 서비스 영향 제한 |
| 세션 종료 시 컨테이너 제거 | 세션 간 잔여물이 남지 않도록 함 |

**[표 3-4] 웹 터미널 컨테이너 격리 정책**

쓰기가 필요한 영역은 사용자별 홈 디렉터리로 한정한다. 접근 권한은 관리자 역할로 제한하며,
자신의 세션에만 접근할 수 있고 사용자당 동시 세션 수에도 상한을 둔다. 앞서 3.1절에서
기술한 것처럼 백엔드는 호스트의 Docker 소켓에 직접 접근하지 않고 필요한 기능만 노출하는
프록시를 경유한다. 컨테이너 실행 권한 자체가 침해 시 호스트 장악으로 이어질 수 있는 강력한
권한이기 때문이다.

여기서 3.6절의 가상 실습과 이 절의 샌드박스가 서로 다른 목적을 갖는다는 점을 밝혀 둔다.
샌드박스 터미널은 실제 명령을 실행해 보는 경험을 제공하되 그 영향을 격리된 컨테이너
안으로 제한하고, 가상 상태 엔진은 실행 자체를 하지 않는 대신 서비스 장애나 접속 차단처럼
컨테이너 안에서도 재현하기 어려운 운영 상황을 학습 소재로 다룬다. 두 방식은 대체 관계가
아니라 학습 단계에 따라 함께 쓰이는 보완 관계다.

### 3.7.4 비밀 정보의 비노출

토큰, 티켓, 비밀번호, 서명 키 같은 값은 로그와 오류 메시지에 남기지 않는다. WebSocket
처리 기록에는 요청 식별자와 처리 결과만 남기고 인증 값 자체는 기록하지 않으며, 언어모델
호출 기록 역시 3.5.3절에서 기술한 대로 내용 대신 해시 식별자만 남긴다. 티켓은 발급 응답에
캐시 금지 헤더를 붙이고 서버에도 영속 저장하지 않는다.

## 3.8 요약

본 장에서는 제안 시스템의 설계를 일곱 개 관점에서 기술했다. 핵심 설계 판단을 정리하면
다음과 같다.

첫째, 자원 수집은 단일 수집기가 만든 스냅샷을 모든 소비자가 공유하는 구조로 설계해 접속
수와 수집 횟수를 분리했다. 둘째, AI 학습 기능에서 학습자의 명령은 실제로 실행하지 않고
가상 상태를 전이시키며, 지원하지 않는 입력은 상태를 변경하지 않는다. 셋째, 성취 판정은 명령 문자열이
아니라 최종 상태를 기준으로 하는 결정적 규칙으로 수행한다. 넷째, 생성형 AI는 이미 확정된
상태와 판정, 그리고 입력이 처리되지 않았다는 사실을 설명하는 역할로 한정되며, 호출이
실패해도 학습 흐름은 유지된다. 다섯째,
권한은 서버에서만 판정하고, 실제 셸을 제공하는 기능은 최소 권한 컨테이너로 격리한다.

이 설계에 따라 구현한 기능의 구체적인 동작은 4장에서 기술한다.
