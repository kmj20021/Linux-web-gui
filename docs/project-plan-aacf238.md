## 1. 프로젝트 개요

### 1.1 한 줄 정의

복잡한 실습 환경 구축 없이 **웹 브라우저만으로** 서버 자원 상태를 관찰하고, 실제 환경에서는
위험한 명령까지 안전하게 반복 실습하며, 생성형 AI에게 즉시 질문할 수 있는
**Linux 운영 학습 지원 시스템**이다.

### 1.2 왜 이 시스템이 필요한가

Linux는 서버·클라우드·정보보안 분야의 필수 기술이지만, 입문 학습자는 세 가지 벽에 부딪힌다.

| # | 문제 | 구체적으로 |
|---|---|---|
| 1 | **실습 환경 구축이 학습보다 먼저 무너뜨린다** | 가상머신 설치와 네트워크 설정 같은 사전 작업이 진입 장벽이 된다. 제한된 수업 시간은 대부분 여기서 소모된다 |
| 2 | **정작 중요한 명령일수록 실습에서 빠진다** | `systemctl stop ssh`, `ufw deny 22`, 설정 파일 삭제처럼 반복 연습이 가장 필요한 명령은 잘못 실행하면 환경을 복구해야 하므로 실습 대상에서 제외된다 |
| 3 | **결과를 해석할 기준이 없다** | 화면에 뜬 출력이 정상인지 오류인지 판단할 기준이 아직 없다. 오타·권한·경로·서비스 구성 오류의 원인을 구별하지 못한다 |

문제 1은 현재 구현이 이미 답을 갖고 있다. 브라우저에서 접속하는 격리 Docker 웹 터미널과
실시간 모니터링 대시보드가 동작한다(`README.md` 주요 기능).

문제 2와 3은 아직 답이 없다. 위험한 명령을 실행할 수 있는 곳이 없고, 출력을 해석해 주는
장치도 없다.

> 근거: `docs/ai-plan.md` §4.2(시뮬레이션 대상 명령 예시), §5(학습 흐름과 3단계 힌트)

### 1.3 생성형 AI를 그냥 붙이는 것으로는 해결되지 않는 이유

대규모 언어모델은 **이전 대화를 기억해 서버 상태를 추측한다.** 연속으로 명령을 입력하면
앞에서 만든 상태와 모순되는 결과를 그럴듯하게 만들어 내고, **학습자는 그 설명이 맞는지
판별할 능력이 아직 없다.** 틀린 설명이 걸러지지 않고 그대로 전달되면 학습에 해가 된다.

그래서 이 프로젝트는 "AI가 터미널을 흉내 내게 한다"가 아니라
**"상태와 채점은 코드가 소유하고, AI는 확정된 사실을 설명만 한다"** 를 설계 전제로 둔다.

> 근거: `docs/ai-plan.md` §10 첫 문단, §2(핵심 설계 결정 6·8), §9.6(모델이 할 수 없는 일 목록)

### 1.4 완성할 시스템의 세 요소

| 요소 | 내용 | 대응 문제 | 현재 상태 |
|---|---|---|---|
| **관찰** | 실제 동작 중인 서버의 자원 사용량을 주기적으로 수집해 웹 화면에 제공한다 | 문제 1 | **구현됨** |
| **가상 실습** | 입력한 명령을 실제로 실행하지 않고 **서버가 보관하는 가상 Linux 상태를 전이**시킨다. 실패해도 복구할 것이 없다 | 문제 2 | **없음** |
| **AI 설명** (판정과 설명의 분리) | 명령 결과와 성취 판정 같은 **사실 확정은 결정론적 규칙**이 맡고, 생성형 AI는 **확정된 사실을 설명하는 일만** 담당한다 | 문제 3 + LLM 환각 | **없음** |

세 번째 요소가 이 프로젝트의 핵심 주장이다. 채점은 "정답 명령어와 문자열이 같은가"가 아니라
**"최종 가상 상태가 목표 상태에 도달했는가"** 로 판정한다. 순서나 명령이 달라도 같은 상태에
도달하면 정답이며, 학습자가 익히는 것은 문법 암기가 아니라 **명령과 상태 변화의 대응 관계**다.

AI에게 질문할 때 시스템이 현재 가상 상태와 확정된 판정을 함께 입력으로 넘기므로, 학습자가 자기
상황을 다시 설명할 필요가 없고 **AI가 실행 결과를 지어내거나 합격 여부를 뒤집을 수 없다.**

> 근거: `docs/ai-plan.md` §6(상태 관리 원칙), §10(가상 상태 엔진), §16.1(비교 설계)

### 1.5 사용자

| 구분 | 대상 | 시스템에서 하는 일 | 현재 권한 |
|---|---|---|---|
| 학습자 (viewer) | Linux 입문 단계의 대학생, 서버 운영 초급자 | 대시보드 열람, (예정) AI 튜터 시나리오 수행 | 모니터링 조회만. **웹 터미널 사용 불가** |
| 관리자 (admin) | 시스템 운영자 | 위 전부 + 사용자 관리, 감사 로그, 연결 목록, 교육용 프로세스 종료, 웹 터미널 | 전체 |

**현재 셸(웹 터미널)은 admin 전용이다.** `POST /api/auth/ws-tickets/shell`이
`get_current_admin`에 걸려 있고(`backend/routers/auth.py:206-209`), `/api/shell/*` 세 경로도
같다(`backend/routers/shell.py:390,428,443`). 계약 문서도 viewer 403으로 못박아 두었다
(`docs/contracts/security-contract.md` §2).

즉 **지금 구조에서는 학습자가 터미널을 전혀 쓸 수 없다.** 이것은 보안 리팩토링의 결과이고
그 자체로는 옳은 결정이었지만, 학습 기능을 붙이는 순간 정면으로 충돌한다(§3 P2).

### 1.6 이번 과제의 성격

`aacf238` 시점에서 **보안·구조 리팩토링은 끝났다.** `docs/re-plan.md`의 Phase 0~9가 전부
DONE/PASS이고(`docs/re-progress.md` Task Status), 동일 배점 재평가에서 시니어 46 → 78,
학습자 63 → 84를 확보했다(`docs/re-evaluation.md` §1).

따라서 이번 과제는 이전 계획서와 갈래가 다르다.

1. **AI 학습 기능 신규 구현** — §1.4의 세 요소 중 아직 없는 **가상 실습과 AI 설명**을 만든다.
   `docs/ai-plan.md`(1198줄)에 설계가 있으나 **코드는 한 줄도 없다**(§2.3).
2. **AI 도입이 건드리는 경계 재정비** — 학습자의 터미널 접근, 배포 환경 HTTPS 제약,
   토큰 수명처럼 "지금은 문제가 아니지만 학습자가 들어오는 순간 문제가 되는" 항목.
3. **잔여 위험 해소** — 재평가가 우선순위와 함께 남긴 7건(`docs/re-evaluation.md` §5).

**AI 기능을 먼저 동작시키는 것을 1차 목표(M1)** 로 둔다. "AI 튜터링이 동작하는 프로젝트"라는
결과물의 정체성이 먼저 서야 나머지 작업의 우선순위를 판단할 수 있기 때문이다.

## 3. 문제점 및 개선 필요성

각 항목은 `현상 → 왜 문제인가 → 근거` 순으로 적는다. 근거는 전부 `aacf238`의 실제 파일이다.

### P1. AI 학습 지원 기능이 없다 — 이번 과제의 핵심

- **현상:** §1.4의 세 요소 중 **관찰만 구현되어 있고, 가상 실습과 AI 설명은 존재하지 않는다.**
  라우터·서비스·화면·테이블·SDK가 전부 없다(§2.3).
- **왜 문제인가:** 현재 상태는 "잘 만든 모니터링 도구 + 격리된 관리자 터미널"이지 학습 지원
  시스템이 아니다. 학습자는 여전히 위험한 명령을 연습할 곳이 없고(문제 2), 출력을 해석해 줄
  장치도 없다(문제 3).
- **근거:** `backend/routers/`, `backend/services/`, `frontend/src/pages/`, `core/models.py`,
  `backend/requirements.txt`

### P2. 학습자가 명령을 입력할 경로 자체가 없다 — P1의 선행 조건

- **현상:** 셸 ticket 발급과 셸 REST 3경로가 모두 `get_current_admin`이다
  (`backend/routers/auth.py:206-209`, `backend/routers/shell.py:390,428,443`).
  계약 문서도 viewer 403으로 확정해 두었다(`docs/contracts/security-contract.md` §2).
- **왜 문제인가:** AI 학습 기능을 만들어도 **그것을 쓸 사용자가 시스템 안에 없다.**
  회원가입은 viewer로 고정되므로, 새로 가입한 학습자는 대시보드만 볼 수 있다. 반대로
  학습자에게 admin을 주면 사용자 관리·감사 로그·프로세스 종료 권한까지 함께 열린다.
- **근거:** `docs/ai-plan.md` §13이 이 충돌을 이미 지적하고 `learner` 역할 추가를 권고한다.

### P3. 배포 환경에서 운영 HTTPS 프로필을 실행할 수 없다

- **현상:** 대상 EC2는 인프라 관리자에게 권한을 받아 쓰는 계정이고 **고정 공인 IP만** 할당받았다.
  Let's Encrypt는 IP에 인증서를 발급하지 않는다. 운영 프로필은 인증서가 없으면 기동을 거부하므로
  (`frontend/start.sh:17-21`), 실질적 배포 모드는 개발 override(`APP_ENV=development`)를 붙인
  **HTTP 프로필**이다(`frontend/start.sh:13-15`).
- **왜 문제인가:** **로그인 자격증명·JWT·WebSocket ticket이 평문으로 전송된다.**
  이것은 "검증하지 않았다"가 아니라 "실행 불가"다. 리팩토링이 닫아 놓은 토큰 노출 경로가
  네트워크 계층에서 다시 열린다. 여기에 학습자 계정과 AI 대화 기록이 얹히면 노출 범위가 커진다.
- **근거:** `docs/re-progress.md` Known Limitations의 **DEPLOY-ENV** 항목,
  `frontend/start.sh:13-24`

### P4. 운영 토큰 수명이 코드 기본값의 96배다

- **현상:** 코드 기본값은 15분인데(`backend/core/security.py:36`), 운영 compose는
  `ACCESS_TOKEN_EXPIRE_MINUTES=1440`(24시간)으로 덮어쓴다(`docker-compose.yml:40`).
  그리고 **로그아웃은 서버 측에서 토큰을 무효화하지 않는다**(`docs/re-evaluation.md` §5-1).
- **왜 문제인가:** P3과 겹치면 **평문으로 오가는, 하루 동안 유효한, 취소할 수 없는 토큰**이 된다.
  세 조건이 각각은 감당 가능하지만 합쳐지면 실사용자 투입의 차단 사유다.
- **근거:** `docker-compose.yml:40`, `backend/core/security.py:36`, `backend/routers/auth.py:163`

### P5. 관측 가능성이 없다 — AI 도입 시 즉시 비용 문제가 된다

- **현상:** 구조화 로그, 메트릭 익스포트, 추적, 오류 집계가 없다.
- **왜 문제인가:** 지금은 "운영 중 문제를 사후에 파악할 수단이 부족하다" 수준이지만,
  Bedrock 호출이 들어오면 **호출 수·지연·throttle·폴백 비율·토큰 수·비용을 아무도 모른다.**
  학교 공용 AWS 계정을 쓰는 이상 이것은 관측 문제가 아니라 승인 조건이다.
- **근거:** `docs/re-evaluation.md` §5-3, `docs/ai-plan.md` §9.5(측정할 운영 지표 목록)

### P6. 단일 프로세스 가정이 곳곳에 박혀 있다

- **현상:** WebSocket ticket 저장소가 모듈 전역 dict다(`backend/core/security.py:38-39`).
  셸 세션 한도도 프로세스 메모리 기준이고(`backend/routers/shell.py:38-41`,
  사용자당 1개 / 전체 5개), 마지막 활성 admin 보호는 module-level `asyncio.Lock`이다.
- **왜 문제인가:** worker를 늘리거나 인스턴스를 2대로 만드는 순간 **ticket 검증이 무작위로
  실패하고 세션 한도가 무의미해진다.** AI 학습 세션이 늘어 수평 확장을 고민하는 시점이
  정확히 이 가정이 깨지는 시점이다.
- **근거:** `docs/re-evaluation.md` §5-2, `docs/re-progress.md` Known Limitations

### P7. 라우터 import 실패를 삼키고 "정상 기동"한다

- **현상:** `backend/main.py:18-49`가 라우터 import를 `try/except ImportError`로 감싸고,
  실패하면 경고 한 줄만 남긴 뒤 서버를 띄운다(`main.py:87-102`).
- **왜 문제인가:** Windows 개발 호스트에서 `shell.py`가 POSIX 전용 모듈(`fcntl`·`termios`·`tty`)
  때문에 import에 실패해 **셸 기능 전체가 빠진 채 "정상 기동"으로 보인다.** 화면은 ticket
  발급까지 성공한 뒤 연결 단계에서 실패한다. 재평가가 정확성 항목의 감점 사유로 직접 적었다.
- **근거:** `backend/main.py:18-49,87-102`, `docs/re-evaluation.md` "정확성과 안정성" 감점 사유,
  `docs/re-progress.md` Known Limitations

### P8. 큰 파일 2개가 남아 있고, AI 기능이 여기에 얹힌다

- **현상:** `backend/routers/shell.py` 484줄이 PTY·Docker 실행·라우트·세션 한도를 한 파일에서
  다룬다. `frontend/src/pages/Network.jsx` 492줄.
- **왜 문제인가:** AI 시뮬레이션 모드는 **같은 터미널 UI를 재사용**하는 설계이므로
  (`docs/ai-plan.md` §2-3, §12), 두 입력 경로가 이 파일들에 함께 들어온다. 지금 분리하지 않으면
  "실제 모드 입력이 시뮬레이션 경로로 새는" 종류의 결함이 생기고 테스트로 좁히기 어렵다.
- **근거:** `docs/re-evaluation.md` "구조와 유지보수성" 감점 사유

### P9. 학교 AWS 사용 조건이 아직 확인되지 않았다 — 외부 의존

- **현상:** 이 프로젝트는 개인 AWS 계정이 아니라 학교 관리형 계정을 쓴다. IAM 역할, 모델/리전
  승인, 쿼터, 비용 한도가 전부 관리자 결정이며, 백엔드 컨테이너의 실제 IAM principal도
  확인되지 않았다.
- **왜 문제인가:** **권한 정책만 적용되고 실제 백엔드 호출이 실패하는 상황이 흔하다.**
  이 항목은 코드로 해결할 수 없고, 승인 대기 시간이 일정 전체의 임계 경로가 된다.
- **근거:** `docs/ai-plan.md` §1.1, §9.1~9.3, §14.1(필수 요청 11항목)

### 6.2 AI 요청 흐름 (신규 구현 대상)

```
학습자가 명령 입력 (시뮬레이션 모드)
   |
   v
명령 파싱 (services/command_parser.py)                          <- AI 호출 없음
   |  허용 목록 + 인자 검증
   +- 미지원/복합 문법(;, &&, 파이프, 리다이렉트) -> 상태 변경 없이 거부
   |
   v
가상 상태 전이 (services/virtual_linux.py)                      <- AI 호출 없음
   |  state_json 갱신 + version 증가 + 시도 기록
   |
   v
규칙 기반 채점 (services/task_grader.py)                        <- AI 호출 없음
   |  최종 가상 상태 vs 목표 상태 대조
   v
성공 / 부분 성공 / 실패  +  다음 문제 진도 (services/curriculum.py)
   |
   v (선택적 · 실패해도 학습에 영향 없음)
AI 설명 요청 (services/bedrock.py)
   |  입력 = 학습자 수준 + 현재 문제 + 가상 상태 요약 + 직전 판정
   |  Pydantic 스키마 검증 · 호출량 제한 · read timeout
   |  실패(AccessDenied / Throttling / Timeout) -> degraded 표시 + 규칙 기반 안내
   v
AI 도우미 패널에 설명 추가  ([SIMULATION] 배지 상시 표시)
```

**핵심 설계:** 상태 전이와 채점은 AI를 거치지 않는다. AI는 설명·힌트만 담당한다.
따라서 AI가 실패해도 학습 진행 자체는 결정론적으로 계속된다(§1.4 세 번째 요소).
전체 채팅 기록을 매번 넘기지 않고 요청마다 필요한 정보만 구성한다(`ai-plan.md` §6).

| 단위 | AI 어댑터(프롬프트 구성·파싱·실패 분류) | pytest with mock. 실제 호출 없이 검증 | 매 커밋 (CI) |
| 통합 | AI 학습 API 전 경로 (401·403·404·409·422 포함) | pytest | 매 커밋 (CI) |
| 격리 | 두 사용자의 학습 세션·가상 상태 상호 접근 | pytest | 매 커밋 (CI) |
| 보안 | 프롬프트·로그에 비밀 문자열이 섞이지 않는지 | pytest + `scripts/security_scan.py` | 매 커밋 (CI) |
| 보안 | 셸 주입 문자열이 실행 경로에 도달하지 않는지 | pytest 음성 검사 | 매 커밋 (CI) |
| 권한 | 보호 경로 × 역할(미인증·학습자·admin·비활성) 전수 | `test_authorization_matrix_e2e.py`에 AI 경로 추가. 실제 토큰 발급 | 매 커밋 (CI) |
| 프론트 | 화면 렌더·모드 분리·오류 표시·접근성 | Vitest + axe | 매 커밋 (CI) |
| 실환경 | Bedrock 실호출, IMDS 차단 | 배포 환경 수동 실행 | 마일스톤마다 |
| 성능·비용 | 호출 지연 p50/p95, 토큰, 폴백률 | 실제 호출 30회 이상 | W13, M3 |

### 9.2 작업 완료 게이트

각 작업은 아래를 **전부** 통과해야 완료로 표시한다. 기준은 `docs/re-plan.md` §3.2와 같고,
실행기는 `scripts/gate.sh`다.

```
1. 실패 테스트를 먼저 작성했고, 구현 전에 실제로 실패하는 것을 확인했다
2. 해당 작업의 focused 테스트 통과
3. backend 전체 테스트 통과
4. frontend 전체 테스트 + lint + build 통과
5. 보안 스캐너 검출 0건
6. docker compose 설정 검증 통과 (운영·개발 두 프로필)
7. 공백 검사 통과 (추적 diff + 미추적 신규 파일)
8. 문서를 함께 갱신했다 (코드만 바꾸고 문서를 두지 않는다)
```

**1번이 핵심이다.** 실패를 먼저 재현하지 않으면 "고쳤다"를 증명할 수 없다.
리팩토링 과정에서 **기존 테스트는 통과하는데 실제로는 뚫려 있던 권한 결함 3건**이 나온 이유가
정확히 이것이었다(`docs/re-evaluation.md` §4). AI 경로에서도 같은 함정이 반복될 수 있으므로,
의존성을 override한 테스트는 "라우트가 올바른 의존성을 선언했는가"까지만 증명한다고 본다.

### 9.3 M3 최종 수동 검증

| # | 항목 | 통과 기준 |
|---|---|---|
| 1 | 권한 전수 검증 | AI 경로 포함 전 경로가 계약대로 401/403/200 |
| 2 | 토큰 비노출 | 실제 발급 토큰·ticket 원문을 서버·Nginx·브라우저 로그에서 grep → 0건 |
| 3 | 셸 격리 | 셸 컨테이너에서 네트워크·Docker 소켓·**AWS 자격증명(IMDS)** 접근 불가 |
| 4 | 비활성 사용자 차단 | 계정 비활성화 즉시 차단 (REST 401, ticket 발급 401) |
| 5 | 기동 거부 | `SECRET_KEY`가 없거나 placeholder면 서버가 시작하지 않음 |
| 6 | 기동 가시성 | 라우터 import가 실패하면 그 사실이 조용히 묻히지 않음 |
| 7 | AI 실호출 | 학습자 계정으로 6문제 완주, `degraded=false` 확인 |
| 8 | **AI 실패 내성** | 자격증명을 일부러 무효화 → 서비스가 죽지 않고 규칙 기반으로 계속 진행 |
| 9 | AI 안전성 | 미지원·위험 문법 입력에 **실행된 것처럼 보이는 응답이 나오지 않음**. 모델이 만든 명령이 자동 실행되지 않음 |
| 10 | 상태 일관성 | 연속 명령 20회 이상에서 앞선 상태 변경이 뒤에 일관되게 유지됨 |
| 11 | 세션 복원 | 새로고침·재로그인 후 자신의 학습 이력과 가상 상태가 복원됨 |
| 12 | 수집 실패 구분 | 수집 실패가 0값이 아니라 503으로 반환 |
| 13 | 재기동 | 배포 서버 재기동 후 전 기능 정상 (Alembic 마이그레이션 포함) |

**8번을 반드시 한다.** AI 실패가 조용히 흡수되는 것이 이 시스템의 가장 큰 위험이므로,
"실패해도 안 죽는다"와 "실패했는지 알 수 있다"를 둘 다 확인해야 한다.

## 10. 완료 기준 및 기대 효과

### 10.1 완료 정의 (Definition of Done)

- [ ] 배포된 서버에서 **학습자 계정으로** AI 학습 시나리오 6문제를 처음부터 끝까지 완주할 수 있다
- [ ] 사용자에게 터미널 UI가 **하나만** 보이고, 두 모드가 화면에서 명확히 구분된다
- [ ] 시뮬레이션 명령이 실제 Docker나 호스트에서 실행되지 않는다
- [ ] 상태를 변경한 뒤 후속 명령에서 변경 결과가 일관되게 유지된다
- [ ] 문제 성공 여부를 규칙 기반으로 판정하며, 명령·순서가 달라도 같은 상태면 정답이다
- [ ] AI 응답이 실제 모델 호출로 반환되고, 그 사실을 응답 필드로 확인할 수 있다
- [ ] AI가 실패해도 규칙 기반 대체로 학습이 계속되고, 실패했다는 사실이 드러난다
- [ ] 채팅·명령 시도·힌트·수행 결과가 DB에 저장되고 재로그인 후 복원된다
- [ ] 학습자와 관리자 권한이 분리되어 있고 권한 행렬 전수 검증을 통과한다
- [ ] 셸 컨테이너에서 AWS 임시 자격증명에 접근할 수 없다
- [ ] AI 호출의 수·지연·오류·폴백·토큰을 로그로 집계할 수 있다
- [ ] 로그아웃한 토큰으로는 보호 경로를 호출할 수 없다
- [ ] 리전·모델·쿼터·비용·로그 정책이 문서화되어 있다
- [ ] CI가 테스트·lint·빌드·compose 검증·보안 스캔을 상시 통과한다
- [ ] `docs/evaluation.md`와 동일 기준의 재평가 점수를 확보했다
- [ ] 해결하지 못한 한계가 목록으로 문서화되어 있고, 각각 개선 방향이 적혀 있다
- [ ] 30초/1분/3분 설명과 시연 스크립트가 준비되어 있고 리허설 2회를 마쳤다

### 10.2 기대 효과

| 관점 | 효과 | 근거 |
|---|---|---|
| 학습자 | 실제 서버를 망가뜨릴 위험 없이 서비스 복구·권한 설정·방화벽 진단을 연습한다. **명령 문자열이 아니라 최종 상태로 채점**되므로 다른 순서·다른 명령으로 목표에 도달해도 인정된다 | §1.4 가상 실습, AI-04 |
| 학습자 | 미지원 명령을 입력해도 "왜 안 되는지" 설명을 받는다. 막힌 지점에서 학습이 끊기지 않는다 | AI-05, AI-07 |
| 학습자 | 환경 구축 없이 브라우저만으로 시작하고, 자기 학습 이력이 남는다 | §1.2 문제 1, AI-02 |
| 시스템 | AI 장애가 학습 진행을 막지 않는다. 상태·채점이 AI와 분리되어 있기 때문이다 | §6.2, 검증 9.3-8 |
| 시스템 | 학습자를 들이면서도 관리 권한은 열리지 않는다 | ROLE-01, 검증 9.3-1 |
| 공학적 | LLM 환각을 "모델을 더 좋게 만든다"가 아니라 **책임 분리**로 다룬 사례가 코드와 테스트로 남는다 | §1.3, §6.3 |
| 공학적 | 문제 → 원인 → 실패 재현 → 수정 → 검증의 절차가 저장소에 기록으로 남는다 | §9.2 완료 게이트 |

### 10.3 완료 후에도 남는 한계 (숨기지 않고 기록한다)

| 한계 | 왜 남기는가 | 개선 방향 |
|---|---|---|
| 배포 환경에 도메인이 없어 HTTPS 미적용 | 도메인 확보가 통제 밖이며 IP에는 인증서를 발급받을 수 없다. 코드의 TLS fail-closed 설계는 그대로 두고 이 환경에서 못 쓸 뿐이다 | 도메인 확보 시 운영 프로필로 전환. 그 전까지 인바운드 IP `/32` 제한 |
| 모니터링 지표를 AI에게 질의하는 기능 없음 | 관찰과 AI 실습이 한 시스템에 있지만 아직 연결되지 않았다 | 지표 스냅샷을 AI 입력에 포함시키는 경로 신설 |
| 단일 프로세스 가정 | ticket 저장소·셸 세션 한도·마지막 admin 보호가 프로세스 메모리 기준이다. 학습용 단일 인스턴스에서는 분산 저장이 과설계 | 워커 증설 시 DB 또는 외부 저장소 기반으로 전환 |
| Git 이력에 과거 blob 잔존 | 이력 재작성은 별도 결정·승인이 필요하다 | 필요 시 별도 결정 후 이력 재작성 |
| 지원 명령 범위가 좁다 | 복합 셸 문법·임의 스크립트·전체 파이프는 MVP 범위 밖이다. 넓히면 결정론성이 무너진다 | 시나리오별로 필요한 명령만 점진 확대 |
| 사람 대상 학습 효과 검증 없음 | 참여자 모집과 연구윤리 절차가 범위 밖이다 | 시스템 정확성·일관성으로 결론 범위를 제한하고, 학습 효과는 향후 과제 |
| 대상 하드웨어 성능 미측정 | 부하 판단이 개발 호스트 기준이다(측정된 REST 지연 1,109ms는 판정 근거로 쓸 수 없다) | 배포 환경에서 동일 절차로 재측정 |
| 번들 500kB 초과 단일 chunk | `recharts`·`@xterm/xterm` 때문이며 학습용 단일 인스턴스에서 체감 효과가 작다 | 코드 분할 |

**이 표를 발표 자료에 그대로 넣는다.** 한계를 먼저 말하는 쪽이 질의응답에서 유리하다.
